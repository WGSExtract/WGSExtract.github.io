Distribution packaging

WGS Extract GUI ships one Tauri desktop app, built natively on each OS:

  • macOS → .app, .dmg, and a signed updater archive (<App>_<arch>.app.tar.gz)
  • Linux → .deb, .rpm, Arch Linux .pkg.tar.zst, and .AppImage
  • Windows → NSIS installer .exe

Local commands#

Build distributables for the current host into out/release/tauri/:

make package           # macOS / Linux
powershell -ExecutionPolicy Bypass -File .\make.ps1 package     # Windows

make package-windows-cross builds the Windows x64 NSIS installer on macOS or Linux (into out/release/tauri-windows), cross-compiled with cargo-xwin and NSIS as Tauri documents for non-Windows hosts. It needs cargo-xwin, makensis, LLVM's clang-cl/llvm-rc/lld-link on PATH, and the x86_64-pc-windows-msvc Rust target, and checks for them first. The installer is unsigned; the WGS Extract install lab uses it to test the Windows app from a Mac.

On Linux, Tauri does not provide a native Arch bundle target, so the Arch package installs the generated AppImage under /opt/<package> with a pacman-managed launcher and desktop entry.

Embedded bundle and app identity#

Packaged releases default to the bundled WGSExtract app while generic distribution mode is still pending. To use a different embedded bundle, set these in .devconfig.toml:

[packaging]
embedded_bundle_path = "examples/WGSExtract"
app_name = "WGSExtract"

The branded name is used for the app bundle name, installer/DMG name, and native window title. If you omit app_name, packaging falls back to the bundle directory name. TAURI_PRODUCT_SUFFIX appends a suffix (for example Ubuntu WebUI) for side-by-side test builds.

Packaging reads version from the bundle's manifest.json and uses it as the app version. For example, the bundled WGSExtract manifest currently sets "version": "0.8.10", so installers are named with 0.8.10 instead of WGS Extract GUI's own version. Bundle-authored JSON files support // and /* ... */ comments. Use SemVer-compatible values because Tauri/NSIS and macOS marketing versions reject arbitrary tags. Set app_version in .devconfig.toml or PACKAGE_APP_VERSION / EMBEDDED_APP_VERSION to override the manifest version.

Embedded bundle scripts can be split by platform under scripts/windows, scripts/macos, scripts/linux, scripts/linux/<distro>, and scripts/posix. Runtime resolution chooses the most specific folder for the host and falls back to posix for POSIX platforms. Every platform folder present in a bundle must include the full referenced script set, otherwise bundle validation fails.

Bundles can define uninstall.steps with the same step shape as setup.steps. The app exposes those as uninstall hooks for cleaning runtime state that lives outside normal app binaries or cannot be safely handled by deleting the bundle workspace alone.

Signing and notarization#

macOS#

Tauri signs the app when a signing identity is available, from (in order) TAURI_MACOS_SIGNING_IDENTITY, APPLE_SIGNING_IDENTITY, or .devconfig.toml:

[apple.signing]
signing_identity = "Developer ID Application: Your Name (YOURTEAMID)"

uv run python scripts/dev.py signing autosetup detects your Xcode team and keychain identities and writes that section. It also reports expired identities; remove them from the keychain search list with uv run python scripts/dev.py signing delete-expired-identities (--dry-run to preview).

Tauri notarizes when it finds notarization credentials in the environment: either an App Store Connect API key (APPLE_API_KEY, APPLE_API_ISSUER, APPLE_API_KEY_PATH) or an Apple ID (APPLE_ID, APPLE_PASSWORD, APPLE_TEAM_ID). See Tauri's macOS signing guide.

Linux and Windows#

No signing is required to build the Linux packages or the Windows NSIS installer.

Windows installer lifecycle test#

The repository's .github/workflows/gui-tauri-installer.yml builds the NSIS installer, silently installs it, launches the packaged app, runs bundle setup, runs bundle uninstall hooks, runs the native uninstaller, and checks cleanup. Run the same check locally on Windows with pwsh -File scripts\validate-windows-tauri-lifecycle.ps1 -AutomatedAdmin after powershell -ExecutionPolicy Bypass -File .\make.ps1 package.

Window close must stop both the app and all matched app processes within -ShutdownTimeoutSeconds (30 seconds by default). The harness waits for asynchronous descendant cleanup without killing or ignoring survivors; it logs their PIDs, parent PIDs, names, and command lines when waiting or failing.

CI / release automation#

The repository's .github/workflows/gui-distribution.yml builds the Tauri app on macOS, Linux, and Windows runners. Run it by hand (gh workflow run gui-distribution.yml --ref BRANCH) for unsigned artifacts (pull requests that change packaging build them too); the release workflow (release.yml) calls it for each vX.Y.Z release, which ships the CLI and the app together (see docs/releasing.md at the repository root).

The macOS job signs and notarizes when these secrets are present (releases fail without them):

  • APPLE_CERTIFICATE_P12, APPLE_CERTIFICATE_PASSWORD, APPLE_SIGNING_IDENTITY
  • notarization, either:
    • an App Store Connect API key (preferred; no Apple ID password or 2FA): APPLE_API_KEY_P8 (the .p8 file's contents), APPLE_API_KEY_ID, APPLE_API_ISSUER_ID; or
    • APPLE_ID, APPLE_APP_SPECIFIC_PASSWORD and APPLE_TEAM_ID.

The workflow maps those onto the variables Tauri reads. Notarization fails (HTTP 403) until the account holder has accepted Apple's current Program License Agreement.

To set the certificate secrets from a Mac that has the Developer ID identity, run tools/packaging/posix/upload_apple_signing_secrets.sh. It exports only that identity directly with Apple's Security framework (macOS asks to allow the export), encrypts it with a random password, and uploads APPLE_CERTIFICATE_P12, APPLE_CERTIFICATE_PASSWORD and APPLE_SIGNING_IDENTITY without printing them. No unrelated private keys are exported. Xcode Command Line Tools are required for the Swift export helper. Use --keychain PATH to select a custom keychain; otherwise the user's keychain search list is used. Selection uses the valid certificate's SHA1 fingerprint, so an expired certificate with the same name does not interfere with renewal. Rerun it when the certificate is renewed.

GitHub updates secrets individually. If an upload fails, the matching certificate and password remain in a private out/apple-signing.* directory. Retry with --resume <directory> and the same --repo OWNER/NAME; this uploads the same pair rather than generating a new password. Do not run GUI distribution until the retry succeeds. Successful uploads remove the local recovery files; otherwise remove those specific files once recovery is complete.

The macOS release builds natively on an Apple Silicon runner and an Intel runner, producing separate arm64 and x64 apps, DMGs, and updater archives.

Bundling a new WGSExtract CLI release#

scripts/bump-wgsextract-cli.py vX.Y.Z points the WGSExtract bundle at another wgsextract-cli release: the tag setup installs, the bundle version that names the installers, and the tests that pin both. Release assembly updates the changelog; see the release process. The bump script changes nothing if any file can't be updated. The root's scripts/bump_version.py X.Y.Z runs it with the CLI's own version bump, since the app and the CLI it bundles ship in the same release; the release workflow refuses a tag the bundle doesn't pin.

The script also generates examples/WGSExtract/scripts/pixi-minimum-version.txt from the root pixi.toml's requires-pixi. Rerunning it with the current tag refreshes this requirement without bumping the release. Setup checks existing Pixi versions on POSIX and Windows and stops with update instructions if one is too old; it never upgrades the user's Pixi automatically. A missing Pixi is installed as before.

Self-updates#

The app uses Tauri's v2 updater plugin with GitHub Releases as the release source of truth. Release builds enable updater metadata when TAURI_UPDATER_PUBKEY is present and create signed updater artifacts when TAURI_SIGNING_PRIVATE_KEY is present.

Generate a Tauri updater keypair once and store the private key in GitHub Actions secrets:

npm --prefix app run tauri -- signer generate -w ~/.tauri/wgsextract-gui.key

Configure release automation with:

  • TAURI_UPDATER_PUBKEY repository variable or secret containing the generated public key.
  • TAURI_SIGNING_PRIVATE_KEY secret containing the private key content or path.
  • optional TAURI_SIGNING_PRIVATE_KEY_PASSWORD secret.
  • optional TAURI_UPDATER_ENDPOINTS / .devconfig.toml [tauri.updater] endpoint = "..."; the default endpoint is https://github.com/WGSExtract/wgsextract-cli/releases/latest/download/latest.json (the app ships in each vX.Y.Z release of this repository; see docs/releasing.md at the repository root).

When updater signing is configured, Tauri emits .sig files next to the macOS .app.tar.gz, the Windows NSIS installer, and the Linux AppImage. Packaging renames the macOS archive to <App>_<arch>.app.tar.gz so the feed can tell architectures apart. Release publishing replaces spaces with dots in asset names.

The app checks the configured endpoint when it starts, unless the user turns on Privacy mode (Settings, Standard UI Options), and shows an update button in the sidebar when a newer release is available. A startup check that fails (when offline, say) leaves nothing on screen. GFC_TAURI_AUTO_UPDATE=0 turns the startup check off for tests that must stay offline. The app also includes a Check for Updates... menu item in the File menu. It checks the configured endpoint, prompts before installing, verifies the Tauri signature, installs the update, and restarts the app.

GitHub Release feed generation#

For a release, gui-distribution.yml downloads the packaged artifacts and passes the build matrix's target list as EXPECTED_TARGETS (a JSON array). Before uploading assets to the vX.Y.Z GitHub Release, it runs:

python3 gui/tools/packaging/generate_update_feeds.py \
  --repo "$GITHUB_REPOSITORY" \
  --tag "$RELEASE_TAG" \
  --version "${RELEASE_TAG#v}" \
  --expected-targets "$EXPECTED_TARGETS" \
  --artifacts-root release-artifacts \
  --output-dir updater-feed

It writes latest.json with windows-x86_64, linux-x86_64, and darwin-aarch64/darwin-x86_64 entries for the release targets. Each must have exactly one updater artifact with a nonempty .sig beside it. A missing or ambiguous artifact or signature fails the job before it uploads anything, so it cannot replace an existing feed with a partial one. Release builds set PACKAGE_APP_VERSION from the tag name so the packaged apps and the feed agree on the update version.

Artifact-only workflow runs (without a release tag) skip feed generation. For local development, replace --expected-targets ... with --allow-unsigned to write entries only for the signed platforms present, or no feed if none are signed. Use a clean output directory for an unsigned build so an old feed cannot be mistaken for a new one. This mode still rejects ambiguous artifacts.

For end-to-end update testing before a production release, build the app with TAURI_UPDATER_ENDPOINTS pointed at a test release's latest.json instead of the latest URL. On Windows, scripts/validate-windows-tauri-update.ps1 installs an older release and drives the update.
