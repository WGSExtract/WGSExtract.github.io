Confidence labels on rare and clinical variants

A ClinVar "pathogenic" match or an allele missing from gnomAD is only as good as the variant call under it. A 30x genome still has stretches at 5x, collapsed duplications where reads map ambiguously, and strand-specific artifacts, and the rarest variants in any genome are disproportionately calling errors. So vcf clinvar, vcf gnomad --max-af, vcf pharmcat and the analyze SNP/indel discovery report label every call they report. (Structural-variant and CNV calls are not labelled: these rules read short-variant evidence.)

LabelMeaning
highThe reads support the call well on every available measure.
moderateSupported, but some evidence is thin (depth or genotype quality between the low and high thresholds, a skewed allele balance) or missing from the VCF.
lowAt least one measure says the call may be wrong: too few reads, low genotype quality, reads far off the expected allele balance, ambiguous mapping, strand bias, or a caller FILTER.

A label is about the technical support for the call in this sequencing run, never about whether the variant causes disease. Even a high finding is a research result: before acting on it, confirm it with an accredited clinical laboratory (in the US a CLIA/CAP-certified test, ideally on a new sample). A first run through these commands is a technical check, not a clinical result.

Inspect the reads#

In the desktop app, open Genome viewer or choose View reads beside an indexed BAM/CRAM input. Enter the variant's 1-based position as chromosome:position-position, then zoom out to check strand balance, clipping, mapping quality and coverage. Use the built-in viewer guide for local reference and index requirements. You do not need desktop IGV or an online genome service. A visual check does not replace clinical confirmation.

Where the labels appear#

ClinVar review evidence is not sequencing confidence#

vcf clinvar requires a matching indexed FASTA (--ref, or the resolved reference library). It normalizes working copies of both inputs with bcftools norm -f and splits multiallelics before matching. Incompatible sample REF bases or contig lengths fail rather than being silently corrected. Original alleles and sample fields remain in WGSE_ORIGINAL (URL-encoded JSON), alongside OLD_MULTIALLELIC provenance. Originals are not rewritten. Shared VCF and allele-table annotation uses this normalization when a reference is resolved.

Complete normalized resources are reused in WGS Extract's persistent cache, ~/.cache/wgsextract/normalized-resources/ (under XDG_CACHE_HOME when set). The key uses the original resource, FASTA/index file identities, conversion schema and bcftools version, not a run's temporary copies. Changed inputs invalidate the cache; temporary-work cleanup does not remove it. Canonical CADD SNV, REVEL and AlphaMissense tables instead use tabix lookups at the normalized query's SNV positions, avoiding whole-table scans; selected resource records still undergo REF validation. Composition indexes only query records overlapping candidate MNV spans.

The known UCSC hg19 Yoruba chrM (16,571 bases) versus GRCh37 ClinVar rCRS MT (16,569 bases) incompatibility excludes resource mitochondrial records with a counted annotation_mito_reference_incompatible warning, so compatible autosomal findings remain available.

A resource record whose REF base differs from the FASTA (ANNOVAR's REVEL table keeps hg19 REF bases, about 1% of which differ on GRCh38) is excluded, so it can never annotate a call, with a counted annotation_ref_mismatch_excluded warning once per resource per command, including when the same resource is used in multiple workflow steps. vcf chain-annotate forwards its steps' annotation_* warnings. Counts come from records before splitting, so each multiallelic record counts once. A resource where more than half of at least 20 checked records differ is refused as built for another genome build. Fields refreshed from the resource are cleared first, so pre-existing scores on unmatched calls cannot pass a score filter. Allele tables (REVEL, CADD, AlphaMissense, PharmGKB) are checked this way on up to 1,000 SNV rows read from 64 compressed blocks spread through the file, so a small query can't hide a table's build. A sample REF that differs from the FASTA, and other build mismatches, remain errors.

Single-sample phased SNVs can recover a ClinVar MNV only when every base differs between REF and ALT and all component bases have the same non-missing PS and share a called ALT haplotype. Opposite haplotypes, unphased or missing calls, different phase sets and imputed calls are not composed. WGSE_MNV_COMPONENTS preserves each component's phase, metrics and original provenance. Components remain in the annotated VCF; intervening or overlapping calls must also be phase-compatible with the entire combined allele. The report counts the combined finding only once, but preserves a component's additional pathogenic copy on the other haplotype (showing the original genotype and the residual copy count). A composed MNV is at most moderate sequencing confidence: individual allele depths do not measure read support for the combined allele, and a low-confidence component makes the MNV low confidence.

CLNREVSTAT, CLNSIGCONF, CLNVC and the resource's record ID (WGSE_CLINVAR_ID) are retained in annotations and confidence tables. WGSE_CLINVAR_STARS and WGSE_CLINVAR_REVIEW describe assertion review: 0 stars without assertion criteria, 1 with criteria, 2 for multiple submitters without conflicts, 3 for expert-panel review, and 4 for practice guidelines. Missing review status stays unknown, not an inferred zero-star assertion. These tiers do not alter the technical sequencing label. A well-sequenced call with no assertion criteria is not equivalent clinical evidence to an expert-panel assertion.

clinvar_conflicts.vcf.gz and clinvar_conflicts.confidence.tsv retain conflicting classifications and their submitter distributions for review. Their manifest confidence metrics use the clinvar_conflict_confidence_* prefix and low_confidence_conflicts warning, without changing the pathogenic subset's confidence_* totals or warnings. They are not consensus P/LP findings and do not contribute to report gene carrier/biallelic counts. Review tiers, conflict evidence and ClinVar IDs appear in vcf table and the report's JSON, findings table, HTML and Markdown. Deduplication is scoped to the genes whose evidence a composed MNV replaces; fully phased calls restricted to one haplotype retain carrier status.

  • VCF: INFO/WGSE_CONF (Number=A: high, moderate, low, or . for an ALT the sample doesn't carry) and INFO/WGSE_CONF_REASONS (the reason codes for each ALT, joined by |). A ##wgsextract_confidence header line records the scheme, caller and thresholds. Labelling an already-labelled file replaces the old labels.
  • TSV beside the VCF (clinvar_pathogenic.confidence.tsv, gnomad_af_lt_<AF>.confidence.tsv, significant_<type>_<name>.confidence.tsv, <name>.confidence.tsv for PharmCAT): one row per carried call with confidence, reasons, depth, genotype_quality, alt_fraction, phase_set (FORMAT/PS, empty when the call has none), the genotype and zygosity and the relevant annotations (CLNSIG, CLNDN, GENEINFO and the split record's OLD_MULTIALLELIC, GNOMAD_AF, the PharmCAT gene, ...). Its # header lines state the thresholds and the disclaimer above.
  • Result manifest (result-manifest.md): metrics confidence_high, confidence_moderate, confidence_low and confidence_not_carried; warnings low_confidence_findings and, for ClinVar pathogenic/likely pathogenic calls, unconfirmed_clinical_findings; and details.confidence, a list with one entry per labelled output: scheme (wgsextract.confidence/1), role, output, sample, caller, thresholds, counts, not_carried, reasons (counts per code), findings (the first 1000 calls with their labels and annotations; findings_truncated says whether there were more) and disclaimer.
  • Personal report (personal-report.md): wgsextract report lists ClinVar pathogenic/likely pathogenic calls in the ACMG SF genes with these labels, and labels PharmCAT genes by their weakest labelled call.

Only calls the sample carries are labelled. A ClinVar site where the sample is homozygous reference (DeepVariant writes these as RefCall records with genotype 0/0) is counted as not_carried and is not a finding. Multi-sample VCFs are judged by their first sample, with a confidence_first_sample_only warning.

Rules#

These are germline rules, not a validated somatic evidence scheme. Mutect2 (##source=Mutect2 or its ##GATKCommandLine header) is identified separately from germline GATK. Its carried calls are labelled low with unsupported_somatic (and filtered when applicable), regardless of VAF; no germline balance, GQ or hard-filter threshold is applied. Here low means unassessable under this scheme, not that the somatic call is wrong. Descriptive depth and allele fractions remain in the table, but zygosity is unassessed. A structured unsupported_somatic_confidence warning explains the limitation; the VCF header and manifest record Policy=unsupported_somatic and policy: unsupported_somatic, respectively (otherwise germline). Neither a low VAF nor this policy establishes CHIP or a tumour diagnosis.

Each carried ALT allele is judged on the evidence its caller wrote. The worst rule wins: any low reason makes the call low; otherwise any moderate reason makes it moderate; otherwise it is high.

Zero-sum FORMAT/AD, or AD with a missing count and no FORMAT/DP, does not measure allele balance. The confidence label falls back to the caller's FORMAT/VAF or FORMAT/AF, then to INFO/DP4 for an unsplit, biallelic single-sample call. Without those, it reports allele_balance_unknown.

An imputed genotype (INFO/IMP, from vcf impute) has no reads behind it to judge, so it is always low, reason imputed (with filtered when it is ImpLowConf). An imputed allele rarer than 1% in the panel (GLIMPSE2's INFO/RAF, or Beagle's dedicated WGSE_PANEL_AC/ WGSE_PANEL_AN) is never counted or listed as a clinical/discovery finding. The dedicated counts survive sample subsetting, unlike standard AC/AN. An imputed input with only unqualified AF or standard AC/AN has unknown panel frequency and is excluded too: these can describe just the target sample. Imputation cannot see a rare allele the reads don't show, so it would be a guess. The labelled VCF keeps it; the manifest counts them (rare_imputed_not_listed) and warns.

PharmCAT still uses the input genotypes when deriving diplotypes, so its confidence summary retains all imputed calls, including rare ones, as low-confidence evidence. Suppression from clinical findings must not remove that evidence and accidentally raise a diplotype's confidence.

PharmCAT reference evidence is also retained in <stem>.confidence.tsv, with PGX_STATE distinguishing supported reference, low-quality reference, absent sites, explicit no-calls, gaps and overlap conflicts. Only reference genotypes with known depth and GQ meeting the configured minimums reach the matcher; MIN_DP, when present in a block, is the depth floor. Reference calls do not require ALT allele balance or variant QD. Haploid reference uses the same halved depth thresholds as haploid ALT. Reference confidence rows cover only PharmCAT definition sites and the bases required by their REF spans, including absent-definition evidence. Weak reference blocks elsewhere in a gene are not evidence for its diplotype and do not lower the reported gene confidence.

Multi-base reference fills use the extracted release's pharmcat_positions.vcf.bgz (or .vcf) definition REF, not a guessed span. Every base must have exactly one compatible reference observation and the same ploidy, with no gaps or overlapping ALT/no-call records. The sidecar keeps the worst supporting depth and GQ; an unknown metric stays unknown. Unsupported reference is passed as a no-call, never silently promoted to 0/0. Expansion is bounded to gene regions, even for chromosome-sized blocks. Absent definitions stay absent in the matcher input, distinct from explicit no-calls. The existing opt-in --absent-to-ref may infer those sites as reference in PharmCAT, but their sidecar evidence remains absent/low. When the input VCF's caller published a gVCF beside it (reference-evidence.md), a definition the VCF doesn't list is decided by the gVCF instead: reference where every base of its span is callable reference, else a no-call whose PGX_STATE is the weakest base's state (uncovered, low_quality_reference, filtered, no_call, variant, excluded_by_policy or not_assessed), so --absent-to-ref no longer applies to it.

Reference evidence at the sites checked#

A findings VCF lists only what the sample carries, so a ClinVar pathogenic site it doesn't list can be confident reference or a stretch no read covered. When the input VCF's caller published a gVCF beside it (reference-evidence.md), vcf clinvar, vcf gnomad --max-af and analyze add reference_evidence to their entry in details.confidence: the gVCF, and the number of sites in each gVCF state for each set of sites checked, calls (the labelled calls) and, for vcf clinvar and analyze, clinvar_pathogenic_sites (every ClinVar pathogenic/likely pathogenic site the filter looked for, carried or not). A site is callable_reference only when every base of it is; otherwise it takes its strongest state against reference. Symbolic alleles use INFO/END when present. With a reference FASTA, checked ClinVar alleles and the gVCF are left-aligned to the same reference, and its index supplies missing gVCF contig lengths. The checked ClinVar set has the same compatibility exclusions as annotation, including incompatible hg19 mitochondrial references. ClinVar sites that are neither variant nor callable_reference (nor excluded_by_policy) raise a reference_evidence_unassessed_sites warning with the count per state: the sample may carry a variant there that was not called. The labels themselves are unchanged, and without a gVCF nothing is added. An unchanged analyze rerun retains these details and warnings when it reuses its discovery step; adding, replacing or removing the companion reruns that step.

Contamination applies to the whole sample, not one call: another person's reads can turn a homozygous site heterozygous or add an allele the sample doesn't carry. The estimate is read from the sample workspace, so it applies when the VCF is in a genome folder (one person's files) where qc contamination has run on one of its alignments. The header line ##wgsextract_confidence then records Contamination=<FREEMIX>.

Haploid calls (a man's chrX and chrY, mtDNA, GT=1) use half the depth thresholds: there is no second allele to find.

Annotation splits a multiallelic call (such as 1/2) into one record per ALT, marked INFO/OLD_MULTIALLELIC, so each ALT meets its own ClinVar or gnomAD entry. The split trims each record's PL to REF and that ALT, dropping the called genotype, and copies site-wide DP4 and SB, whose alt reads belong to every ALT. A split record's genotype quality therefore comes only from FORMAT/GQ, and its alt read fraction only from AD with FORMAT/DP (or a per-ALT VAF/AF); otherwise they are gq_unknown and allele_balance_unknown, which cap it at moderate rather than wrongly making it low. On HG002 chr20, the 641 multiallelic bcftools calls were 98.4% correct; judged on the split evidence, 523 of them would have been low. wgsextract vcf snp and vcf indel write FORMAT/AD and FORMAT/DP, so their split calls keep their allele balance.

Change the depth and genotype-quality thresholds for every run in config.toml, or for one run on the command line:

confidence_min_depth = 10.0   # below: low (halved for haploid calls)
confidence_high_depth = 20.0  # below: moderate
confidence_min_gq = 20.0
confidence_high_gq = 30.0
wgsextract vcf clinvar --input s.vcf.gz --confidence-depth 8 15 --confidence-gq 20 30

Why these thresholds#

  • Depth 10 / 20. A true heterozygous site shows each allele in about half its reads, binomially. The chance that a true heterozygote shows an alt fraction outside 0.2–0.8 is 22% with 6 reads, 2.1% with 10 and 0.26% with 20, so below 10 reads a heterozygote is easily called homozygous or missed, and by 20 depth alone rarely misleads. Clinical laboratories set their own minimum depths during validation (Rehm et al. 2013; Roy et al. 2018); 20x per site is a common choice, and depth is one of the standard filters reviewed by Koboldt (2020). These thresholds are per site: a genome's mean depth says nothing about a given position.
  • GQ 20 / 30. GQ is the Phred-scaled probability that the genotype is wrong: 20 means 1%, 30 means 0.1%. DeepVariant's GQ is reported to be well calibrated against GIAB truth (Poplin et al. 2018), so it can be taken at face value; bcftools and GATK GQs are model-based and usually optimistic, which the other rules partly compensate for. When GQ is absent it is derived from PL (the difference between the two most likely genotypes).
  • Allele balance. Germline heterozygous calls should be near 0.5. An alt fraction outside 0.3–0.7 is worth a second look; outside 0.2–0.8 (where only 0.26% of true heterozygotes at 20 reads fall) it suggests a mapping artifact, a paralogous region, contamination or a mosaic/somatic event rather than a clean germline call. Homozygous calls with many reference reads are likewise suspect.
  • Mapping quality, strand bias and QD use the GATK germline hard-filter thresholds (MQ < 40, FS > 60, SOR > 3, QD < 2; for indels FS > 200, SOR > 10), which Broad derived from truth-set distributions. GATK's MQ is the root mean square of the reads' mapping qualities. bcftools instead writes their plain mean ("Average mapping quality" in its header), which sits far lower for the same reads, so 40 would flag ordinary calls: on HG002 chr20 the bcftools calls with MQ 35–39 were as accurate as the genome average. A mean MQ is therefore held to MAPQ 20, a 1% chance that a read is misplaced, below which calls were wrong 10% of the time. QD (QUAL divided by depth) is only judged on GATK calls: its threshold assumes GATK's QUAL. DRAGEN's machine-learning-recalibrated QUAL is on another scale (a clean 34x heterozygote scores QUAL 50, QD 1.5), and in one DRAGEN genome 52% of PASS calls had QD below 2. DRAGEN applies its own hard filters, which arrive through FILTER. When a caller writes no FS or SOR (bcftools), SOR is computed from its strand counts with GATK's formula. DeepVariant writes no strand or MQ annotations; its model sees them directly, so its labels rest on depth, GQ and allele balance.
  • FILTER. A call the caller itself filtered (GATK LowQual, DeepVariant RefCall/NoCall, a VQSR tranche) is low confidence by definition.
  • Missing evidence is not good evidence. A VCF without depth or genotype quality (for example one converted from a microarray or imputed) cannot earn high. Clinical guidance is that each laboratory must validate its own pipeline and quality thresholds and confirm reportable variants it can't vouch for (Rehm et al. 2013; Roy et al. 2018); calls with poor quality metrics are where false positives concentrate (Lincoln et al. 2019).

These rules cannot see systematic errors that look good in the reads (a reference-genome error, a segmental duplication with confident but wrong mapping) or variants a short-read genome misses altogether. GIAB's stratified benchmarks show such errors are concentrated in low-complexity and segmental duplication regions (Wagner et al. 2022).

Validation#

A good label should put few errors in high and many in low. Two call sets were labelled with the default thresholds and every carried call scored against an independent answer:

  • HG002 chr20, Illumina 35x, bcftools calls, scored by rtg vcfeval against the GIAB v4.2.1 benchmark inside its confident regions (82,655 calls).
  • HG008 whole genome, Ultima, DeepVariant calls, compared (allele and genotype class, after normalisation) with an orthogonal Illumina 169x call set (QUAL ≥ 30) inside GIAB's "not difficult" regions where both platforms have identical coverage (3.1 million calls). This truth set has its own errors, so its rates are disagreements, not proven errors.

Ultima GATK scatter#

vcf gatk --scatter optionally runs independent flow-aware HaplotypeCaller processes over nonoverlapping intervals, gathering in reference order. It is off by default: annotations/genotypes can differ far from boundaries, because processes reset random state (annotation jitter, read downsampling) as well as assembly context. Threads/physical RAM cap concurrency, budgeting 6 GiB per worker with explicit 4 GiB Java heap. One fitting worker keeps the unscattered path. --memory remains sort memory, not a GATK heap. Scatter needs bcftools/tabix as well as GATK/samtools and cannot use --gpu.

A functional comparison used original GIABv3-mapped public HG008 Ultima chr20 reads, nominal 30x (7,012,718 primary reads), GATK 4.6.2.0, two workers. Both retained 131,299 sites, but 85 records and two genotypes differed: 0/1 → 1/1 at chr20:47,895,004 and chr20:47,895,025. Differences were 1.91–32.08 Mb from the chr20:32,222,084 split, not boundary-local: not equivalence. One run took 57.2 min unscattered versus 37.5 min scattered including CRAM preparation; this was neither a controlled throughput benchmark nor an accuracy comparison. A separate 200 kb realigned-read smoke was byte-identical across 395 decoded records, but slower scattered due to startup.

Opt-in BAQ in vcf snp and vcf indel#

By default, both commands keep BAQ (base alignment quality) off (bcftools mpileup -B), preserving existing calls and runtime. --baq enables bcftools' heuristic BAQ by omitting -B; it adjusts base qualities where read alignments may be wrong. It also applies to the optional --reference-evidence gvcf pass. Set baq = true in config.toml to persist the choice; --no-baq overrides it for one run. The effective baq boolean is recorded in the result manifest's provenance parameters. The typed API and server accept the same baq parameter.

The BAQ study (#982) on HG002 NovaSeq at nominal 35x, against GIAB v4.2.1 confident regions, found these unfiltered, genotype-aware F1 scores:

RegionSNP F1, off → onIndel F1, off → on
chr2098.30% → 98.99%94.28% → 95.19%
chr2297.84% → 98.47%94.03% → 94.88%

BAQ took 29–35% longer in the matched 35x regional runs. At ~10x (a downsample of the same sample/platform), difficult-region SNP recall fell from 93.62% to 92.63%, despite improved precision. These are regional, single-pass measurements, not whole-genome or independent-platform qualification. BAQ is therefore opt-in, not a universal accuracy upgrade or a replacement for quality filtering. The flat prior was held fixed.

This option does not request full BAQ (-D) or redo BAQ (-E, which ignores existing BQ tags). Those modes were not qualified by this study. The opt-in requires bcftools 1.13 or newer, which supports heuristic BAQ; an older or unidentifiable version fails before calling. The BAQ-off default keeps the existing dependency requirements. Ultima input rejects --baq (including baq = true from config), because its automatic -X ultima profile itself disables BAQ. Use --no-baq for Ultima; the other profile settings and its prior stay unchanged. analyze comprehensive records the effective config choice in its calling step keys, so changing baq reruns SNP and indel calling on resume. With BAQ off, the commands stay identical to those from before this option, so existing default-setting journals resume without redoing completed calls.

The calling prior in vcf snp and vcf indel#

vcf snp and vcf indel run bcftools call -m with a flat prior (-P 0) instead of bcftools' default variant prior of 1.1e-3, so they keep more low-QUAL calls. On HG002 chr20 and chr22 (Illumina 35x, scored by hap.py with vcfeval against GIAB v4.2.1 inside its confident regions; #860):

  • Indels: the flat prior is better. F1 94.98% against 94.61%: recall 94.90% against 94.06% at about equal precision (95.07% against 95.17%).
  • SNPs: the prior only shifts the QUAL scale. Unfiltered, the flat prior trades 1.6 points of precision (97.26% against 98.88%) for 0.25 points of recall. Filtering its calls to QUAL>30 (for example vcf filter --expr 'QUAL>30') reproduces the default prior's call set (precision 98.88%, recall 98.94%), and the best F1 over all QUAL thresholds is 99.06% either way.
  • The extra flat-prior SNP errors concentrate in homopolymers and tandem repeats: in homopolymers of 12 bases or more precision was 49.9% against 76.0%, in all tandem repeats and homopolymers 78.4% against 90.6%. Outside GIAB's difficult regions the flat prior's precision was 99.28%.

Ultima reads are the exception: they keep bcftools' default prior (with its Ultima profile, -X ultima), because on GIAB HG008 chr20 the flat prior let homopolymer-length errors through as indels (precision 0.13 against 0.29).

Precision is only meaningful inside a confident-region BED such as GIAB's. Without one, the same QUAL>30 SNP calls scored 73.9% precision instead of 98.9%, because calls outside the benchmark's regions count as false positives whatever their quality.
