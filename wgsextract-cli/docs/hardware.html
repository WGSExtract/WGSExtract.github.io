Hardware and acceleration

Alignment (align, realign) is the slowest step for a whole genome. This page says which hardware speeds it up and by how much. Each figure is labelled:

  • measured: timed by this project;
  • published: from the cited upstream source, on their hardware;
  • estimate: a model or expectation, not a timing.

For memory and disk planning, see resource estimates.

Genotype imputation#

GLIMPSE2 in the optional imputation environment runs natively on Apple Silicon and Linux ARM64 using NEON. On the M1 Pro, native phasing of a typical HG002 chr20 chunk took 14.6 s versus 28 s under Rosetta in the #1118 speed study. For installation, thread sizing and chr20 results, see imputation.

CPU aligners#

Input and output safety#

FASTQ alignment requires an explicit --ref FASTA when the library holds several genomes: reads cannot identify the intended reference. align validates every FASTQ record before mapping. Paired files need equal counts and ordered matching names (/1//2 accepted); truncated FASTQ or gzip fails. Setup/platform checks run first. Completed alignment must contain exactly one primary record per FASTQ read, not counting secondary/supplementary records. Only validated files replace earlier alignments, atomically, even with --no-atomic-output. API cancellation interrupts validation cooperatively.

Pipes/stdin spool under --tmp-dir (else --outdir) before validation; budget disk for the entire stream. Read names/output filenames retain the original inputs. Use --platform for long-read streams: unlabelled streams use Illumina defaults without consuming the first read to detect platform. Native HiFi/CCS FASTQs select long-read defaults; bounded header/length/quality sampling handles renamed FASTQs. Ambiguous long reads require --platform ont|hifi|clr, never silent BWA defaults; see platform evidence.

BWA/bwa-mem2 use fixed -K 100000000 for thread-count reproducibility, including realign, pet and Ultima alignment; older releases used thread-based batches. On references with ALT contigs (hs38DH/full GRCh38), BWA gets a <ref>.alt list. Without it, reads across ~110 Mb of duplicated sequence (including HLA) get MAPQ 0 or land on ALT copies, losing variants. WGS Extract v4 aligned that way; callers, microarray and trios warn, and realign recovers the affected regions. See input diagnostics. pet-align writes beside the R1 FASTQ unless --outdir is given.

Short-read realign checks the first 10,000 primary reads and, when indexed, 10,000 unplaced unmapped reads before extraction. It refuses single-end primary reads (neither first nor second mate, e.g. flag 0 or 4) with exit 1, rather than silently discarding them. This costs ~0.1 s on a 30x CRAM versus ~3 min for an exact count. Sampling can miss rare single-end reads in paired input, so extraction also counts dropped reads and warns. Extract such inputs with bam unalign --se, then align the single-end FASTQ. ONT, PacBio and Ultima --platform paths handle single ends themselves.

Paired short-read realign streams newly extracted reads as interleaved pairs into BWA or minimap2 sr when a collate bucket fits beside alignment, including 30x genomes. It uses extraction's bucket count for identical records and preserves paired filtering. Minimap2 also needs an explicit uncompressed FASTA that fits in a single index part. Otherwise realign extracts to files without changing aligner. --keep-fastq, supplied/reused FASTQs, and GPU short-read realignment keep using files. --force-extract with cached FASTQs at the exact output paths also retains file handling and success-cleanup/failure-retention rules; fresh forced extraction may stream. Collation needs temp disk and one bucket's RAM beside sorting, both in preflight. Failed streams leave no reusable FASTQs: use --keep-fastq for retries.

Long-read realignment#

Single-end PacBio (PL:PACBIO or read names, all sampled primary reads single-end) selects minimap2 map-hifi, or map-pb for READTYPE=SUBREAD, as explicit --platform pacbio|hifi|clr does. Paired PacBio-labelled input keeps short-read defaults. Aligned BAM/CRAM and unaligned basecaller BAM each supply one primary record per read: samtools fastq -F 0x900 -T MM,ML,MN,pi | minimap2 -y -Y. MM/ML tags survive; secondary/supplementary records never become extra reads. Kinetics tags fi/ri/fp/rp do not carry through. --keep-fastq writes tagged <input stem>.fastq.gz first: movie.ccs.bam gives movie.fastq.gz and movie_aligned.bam, also for ONT.

Streaming long-read realign uses neither pbmm2 nor --gpu. For pbmm2 give PacBio BAM to align --r1 BAM --aligner pbmm2, which reads primary records itself; convert CRAM with bam to-bam first. ONT read groups/UUID read names select minimap2 map-ont; CPU alignment and sorting retain MM/ML. See ONT for methylation, Sniffles, Clair3 basecaller-matched models, phasing and qualification limits.

Automatic short-read selection#

--aligner auto (the default) aligns short reads with bwa-mem2 when all of these hold, and with bwa otherwise:

  • bwa-mem2 will run: upstream bwa-mem2 is installed (it is in the default environment on Linux, macOS and Windows), or, on Apple Silicon with native aligners on, wgse-bwa-mem2 0.5.0 or later is (upstream bwa-mem2 isn't needed then);
  • the reference already has the bwa-mem2 index that aligner reads: the full index for upstream bwa-mem2 (and wgse-bwa-mem2 before 0.5.0), without the .0123 file for wgse-bwa-mem2 0.5.0 and later;
  • the estimated alignment pipeline fits in the RAM available now.

Auto never downloads or builds the index. When the index is missing but would fit, the CLI logs a hint; when the index is there but doesn't fit, it logs the estimated need and uses bwa. --aligner bwa or --aligner bwa-mem2 chooses explicitly; --aligner bwa-mem2 fails when it can't run in this computer's memory rather than falling back.

Few computers can build the bwa-mem2 index, so wgsextract ref index --aligner bwa-mem2 --ref REF downloads the published one (17 GB) for hs38DH and Broad's GRCh38, whose sequences are the same. For other references it builds the index only when the computer has the memory. bwa-mem2 is a reimplementation of bwa's algorithm, but its records are not identical to bwa's: on 5M HG002 read pairs on hs38 the record hashes differ (bwa family e2febf171215d840, bwa-mem2 family dff39743a72242de). Each family is reproducible: wgse-bwa and wgse-bwa-mem3 --compat=bwa-mem write bwa's records, wgse-bwa-mem2 and wgse-bwa-mem3 --compat=bwa-mem2 write bwa-mem2's.

The ~1.3× speedup is what we measured. bwa-mem2's authors published up to 3.5× on one thread and 2.4× on one socket of an Intel Xeon Skylake with AVX-512 (Vasimuddin et al., IPDPS 2019). Bioconda's x86-64 bwa-mem2 (Linux, Intel Macs) picks its SSE4.1, SSE4.2, AVX, AVX2 or AVX-512 kernels at run time, so newer CPUs gain more.

ARM (Apple Silicon, Linux ARM64). The ARM bwa-mem2 builds translate those x86 SIMD kernels to NEON with sse2neon, so expect a smaller gain than on AVX-512 x86 (estimate). On a 16-core Linux ARM64 server, full 30x bwa-mem2 was 19.8% slower than on the x64 control (measured; see Linux ARM64).

There is no fixed memory cutoff, on a Mac or anywhere else: auto compares the estimate for this input, reference and settings with the RAM available at the time. As guidance only, a whole human genome needs a computer with 32 GB or more for bwa-mem2; since the 30x estimate at 6 threads is ~29 GiB, auto picks bwa whenever less than that is free. Smaller inputs need less.

With wgse-bwa-mem2 0.5.0 or later installed (and native aligners on), auto uses its estimate, which leaves out the .0123 file it doesn't load (about 6 GiB less for hs38; see Apple Silicon), and the reference needs no .0123 file. On a 16 GB Mac a 30x genome still doesn't fit, so auto keeps bwa there (wgse-bwa). wgse-bwa-mem3 alone doesn't make auto pick bwa-mem2: it already stands in for bwa with bwa's records. When auto picks bwa-mem2, wgse-bwa-mem3 stands in for it only when its own estimate also fits the RAM available; otherwise wgse-bwa-mem2 aligns.

Records: because bwa and bwa-mem2 write different records, a change in auto's choice changes the BAM, not just its @PG header and the result manifest. On a Mac that gains wgse-bwa-mem2 0.5.0 or later, or with a reference that has bwa-mem2's index without .0123, auto can now pick bwa-mem2 where it used to pick bwa, and a re-run gives a different BAM; it logs when it does. To compare runs, pin the aligner with --aligner bwa (or --aligner bwa-mem2).

bwa-mem3 on Linux#

bwa-mem3 writes bwa's exact records with --compat=bwa-mem and bwa-mem2's with --compat=bwa-mem2, from bwa-mem2's index without its .0123 file, several times faster. Bioconda's build needs a newer htslib than the default environment's samtools, so it has its own environment; install it with pixi install --locked -e bwa-mem3 (Linux and macOS). On Linux, when it is installed and the reference has bwa-mem2's index, align and realign run it in place of bwa or bwa-mem2 (whichever --aligner or auto chose), under the same memory rules as wgse-bwa-mem3 on a Mac (Apple Silicon): in bwa's place its pipeline must fit the RAM available, so on 16 GB computers bwa usually runs. Ultima reads keep BWA. --native-aligners off (or native_aligners = "off") turns this off. A bwa-mem3 older than 0.16.0, or one whose bwa-mem3 version fails, raises the native_aligner_unusable warning and bwa or bwa-mem2 runs. The result manifest records native_aligner bwa-mem3 and bwa_mem3_mode, as on a Mac.

Measured with wgsextract align on the first 5M HG002 read pairs (30x NovaSeq) on hs38, 16 threads, BAM output, two rounds in reversed order, on Azure 16-vCPU, 64 GiB VMs with Ubuntu 24.04. The records were the same with and without bwa-mem3 (SHA-256 of samtools view, 10,062,598 records):

On Linux x86-64, WGS Extract's wgse-bwa-mem3 0.4.0 or later (bwa-mem3 0.16.0 without that allocator, from the linux-aligners-* prereleases; see native/README.md) stands in the same way, ahead of Bioconda's, when it's on PATH. It runs --backend auto: on an NVIDIA GPU when its capabilities report cuda_available (experimental: seeding, seed extension and mate rescue), otherwise on the CPU, with the same records either way. The manifest records native_aligner wgse-bwa-mem3 and native_aligner_backend cuda or cpu.

Threads and memory#

  • --threads (or threads in config.toml) defaults to auto: all cores outside Apple Silicon; on Apple Silicon, the per-stage plan below. An explicit positive count applies to every parallel stage, including staged alignment. No CPU affinity is set: macOS still decides where workers run.
  • --memory is the sort memory per thread. auto divides 25% of effective RAM across the threads and rounds down. For example, 16 GiB and 12 threads gives 341 MiB per thread. With bwa-mem2, sorting is capped at 256 MiB per thread to leave room for its index. Native wgse-bwa can also lower the requested sort budget when fitting its GPU pipeline, or cap an over-budget CPU fallback at 256M per thread as described below.
  • samtools sort reserves all of its threads' memory when it starts. The CLI caps its buffers at half of effective RAM, including Linux cgroup v2 limits, even with explicit --memory, and can lower them further for small inputs (see resource_estimates.md). The log says when this lowers --memory; the output is the same.
  • Before a native BWA run, the CLI prints a memory and disk preflight. More threads use more memory; when it reports LOW, lower --threads or --memory, or use --aligner bwa. Explicit thread counts are not lowered.

Apple Silicon stage plan#

The plan reads hw.perflevelN.name and hw.perflevelN.physicalcpu, not the chip name or just level 0. Big means every level not named Efficiency, including both Super and Performance; all adds the efficiency levels. Without level names, the conservative fallback uses all but the last level as big when there are several levels (a single level is all big).

These are tool thread arguments or calling worker budgets, not exact OS thread counts: some tools also have a main/I/O thread. Serial tools such as samblaster remain serial. The effective plan is in the result manifest's provenance.params.thread_plan; --threads N or threads = N makes every budget N. CPU mapping and sorting have separate memory estimates. Staged Metal retains these worker budgets and lowers sort buffers when needed, rather than silently reducing the requested worker count. Existing staged checkpoints made with different thread plans must be discarded before restarting.

Measurements on the base M1 distinguish throughput from desktop responsiveness: CPU mapping benefited from the efficiency cores, whereas Metal and markdup did not. Standalone sort was faster with all cores but used roughly twice the sort memory; giving all cores to sort in the overlapping mapping pipeline gained less than 2%. Big-core sort is therefore a pipeline/memory tradeoff, not evidence that efficiency cores inherently thrash macOS. Standalone compression and contig jobs benefited from all cores without comparable scheduling stalls. See issue #968 (Apple per-stage thread measurements) for wall/CPU times, periodic-task latency and the experiment's limitations.

Experimental Apple Silicon NEON PairHMM#

vcf gatk --pair-hmm-neon JAR opts into the existing native ARM64 GKL PairHMM port, built for macOS. It is not Parabricks; --gpu keeps its existing meaning. GATK 4.6.2.0, JDK 17+, Apple Silicon and locally installed libomp are required. No dependency is installed or downloaded by calling. See build, fallback and native validation instructions. Metal is not used. NEON removes PairHMM as the main bottleneck in ordinary slices, but the difficult-window measurements below still spend substantial time in PairHMM.

Opt-in, not a default. It calls the same sites, alleles, GT and FILTER as the Java PairHMM across the five-window HG002 panel below, 9.1× faster. In difficult regions (pericentromere, high depth) a few reads near the informative cutoff are counted differently, so 9 of 306,024 gVCF reference blocks and 8 final records differ in AD/DP, QUAL or annotations (for example AD/DP 63,38/101 vs 62,38/100). GATK's own x86 GKL AVX PairHMM is not bit-identical to Java either; #1193 measures how far apart those two are.

Queued measurement: M1 Pro (10 cores, 32 GiB), macOS 27.2.1, OpenJDK 17.0.21, HG002 PCR-free 35×, hs38, chr20:10000001-20000000 (10 Mb), four native threads and 4 GiB Java heap. JVM startup is included; Smith-Waterman stays Java.

Mean wall falls from 45.34 to 25.31 s (44.2%). Every CLI gVCF body (25,534 records) and final VCF body (1,779 calls) matches exactly.

These are bounded-region prototype results, not full chr20 or whole-genome performance/accuracy qualification. Do not extrapolate RSS from the slice or treat the sidecar as a qualified default.

The 2026-11-19 whole-chr20 real-CLI qualification attempt did not complete: Java's progress meter reached chr20:29,840,219 after 283.6 traversal minutes before cancellation. No final gVCF or genotyped VCF was published, and the NEON comparison was not started. This is an incomplete run, not a chr20 timing or parity result. The 10–20 Mb slice does not cover the slow pericentromeric traversal; its speedup is not a whole-chromosome runtime estimate.

Of 306,024 reference blocks, nine do not match completely: six in the pericentromeric window, three in the q-arm window. Eight final VCF records differ in more than the allowed PL-level exception. At chr20:28,830,216, for example, sample AD/DP changes from 63,38/101 to 62,38/100; the next block's DP changes 112→111. At chr20:31,068,903, block DP changes 924→920, and the nearby final variants also change depth and other annotations. These differences are why the option stays opt-in rather than a default. The ordinary and repeat windows have only three already-characterized variant-gVCF <NON_REF> PL differences; their final VCF bodies are identical.

Independent real-CLI 20 kb controls reproduce the failures. At chr20:28,820,001–28,840,000, all twelve differing gVCF rows (six blocks) and six final-VCF mismatch pairs reproduce exactly, taking 214.14→26.08 s Java→NEON. At chr20:31,060,001–31,080,000, two blocks and both nearby final variants still differ beyond PL alone, taking 3,006.57→208.72 s. The q-arm control's absolute annotations change with clipped assembly context, but its depth/allele-depth discrepancies recur at the same sites. Control timings are excluded from the panel totals.

Double precision fixes the earlier ordinary-slice float regression, but is insufficient for exact difficult-region parity. Native likelihood/vector tolerance tests and passing software certification do not establish this scientific gate. Do not infer whole-chromosome/WGS equivalence, extend this speedup to other chips, or conclude PairHMM can never remain a bottleneck.

Around the aligner#

Short reads stream from the aligner through samblaster into samtools sort (or through samtools fixmate, sort and markdup for single-end reads or when samblaster is missing). The last samtools stage writes the .bai or .crai as it writes the BAM or CRAM, so there is no separate pass that reads the whole output again to index it. The records are unchanged, and the index is the one samtools index writes (#545).

The gain is modest. Measured at 4 threads on an 8-core Linux workstation (#545):

  • Index pass, 30x (681M records, 26.5 GB BAM): sambamba index, which Linux used before, took 97 s and 384 CPU-s, and samtools index 54 s. Writing the index during the BAM write added 62 CPU-s, so about 320 CPU-s and a 1.5-minute pass over the whole BAM are saved.
  • Stages after the aligner, 10M reads: samblaster used 12 CPU-s and samtools sort 67; bwa itself is far larger. Converting the SAM to uncompressed BAM before the sort saved nothing, and samblaster only reads SAM. Sorting with 2 threads instead of 4 used 12% less CPU but took 24% longer, so the sort keeps all threads.
  • samblaster or samtools markdup: fixmate | sort | markdup used 74 CPU-s and 34 s, against 67 CPU-s and 30 s for samblaster and sort, and marked 5,884 duplicate records instead of 5,894. samblaster stays the default for paired reads.

NVIDIA GPUs (--gpu, Parabricks)#

align --gpu and realign --gpu run NVIDIA Parabricks: fq2bam (BWA-MEM, sorting and duplicate marking) for short reads, and its minimap2 for PacBio HiFi FASTQs. Streaming long-read realignment directly from BAM/CRAM refuses --gpu to retain tags; supply FASTQs for that GPU path.

These are BWA-MEM, DeepVariant and GATK-equivalent paths, not new callers. On the measured RTX 3090, DeepVariant and HaplotypeCaller took about a minute for chr20. Ultima uses Google's experimental image instead, below.

Requirements, which the CLI checks but doesn't install:

  • Linux on x86-64 (WSL2 should work but is untested; native Windows, macOS and Linux ARM64 are refused);
  • an NVIDIA GPU with 16 GB or more and its driver;
  • Docker with the NVIDIA Container Toolkit;
  • the Parabricks image (parabricks_image in config.toml).

Install the image explicitly with docker pull nvcr.io/nvidia/clara/clara-parabricks:4.8.0-1. Reads, outputs and reference mount at their own paths; tools run as you. Parabricks cannot write CRAM against gzipped FASTA, so it writes BAM and host samtools converts. With wgse-deepvariant and deepvariant_weights, WGS/ONT_R104 run natively on CUDA; deepvariant_native = "off" keeps Parabricks. Other models still use it.

Before starting Parabricks, the CLI reads the GPU's free memory from nvidia-smi. When another program holds part of the GPU, it uses the tool's low-memory mode. When even that won't fit, or the computer has too little RAM (fq2bam needs at least 34 GiB, and 41 GiB for a whole genome), it stops before running, or warns when it only falls short of the whole-genome need; --no-gpu-memory-check overrides this. NVIDIA recommends 100 GB of RAM for one or two GPUs, but the 62 GB host measured below works. See resource estimates.

What --gpu refuses:

  • ONT: the GPU path isn't qualified to keep the MM/ML methylation tags; align ONT reads without --gpu.
  • Ultima: Parabricks drops the flow tags (tp, t0) and can't mark flow-based duplicates.
  • PacBio CLR/subreads: there is no GPU preset.
  • --aligner bwa-mem2: Parabricks runs its own BWA-MEM; use auto or bwa.

Parabricks has no Ultima model. vcf deepvariant --gpu on Ultima (or --model-type ULTIMA) instead runs Google's experimental google/deepvariant:gh1100-ultima-gpu, pinned by digest:

It needs x86-64 Linux, NVIDIA driver and Docker's NVIDIA runtime. Before call_variants, each GPU must have 7.3 GiB free; --no-gpu-memory-check warns and runs anyway. Experimental native CUDA PairHMM for GATK#

vcf gatk --pair-hmm-cuda JAR opts into a locally built native PairHMM sidecar, not Parabricks. vcf gatk --gpu keeps its existing Parabricks meaning. This prototype is pinned to Linux x86-64, GATK 4.6.2.0 and GKL 0.8.11; see build and validation instructions. The CLI validates local dependencies but installs or downloads nothing.

An AVX-capable CPU supplies the original GKL fallback. Kernels target Turing/SM 7.5 and newer; only the RTX 3090 has been tested. NVIDIA GPUs without Parabricks (wgse-bwa --cuda)#

On Linux x86-64, WGS Extract's wgse-bwa 0.10.0 or later (bwa 0.7.19) can run on an NVIDIA GPU, as wgse-bwa --metal does on a Mac (native/README.md). It writes bwa's exact alignments and is experimental.

  • When it runs: with native_aligners = "auto" (the default), align and realign run wgse-bwa --backend auto in place of bwa when it's on PATH. It uses the GPU when its capabilities report cuda_available, and otherwise aligns on the CPU. If the GPU fails during a run, it finishes on the CPU with the same alignments.
  • Order on Linux (bwa's records): bwa-mem3 --compat=bwa-mem (wgse-bwa-mem3, on its own GPU, else Bioconda's) when it's installed, runs and fits; otherwise wgse-bwa on the GPU when it fits in RAM; otherwise wgse-bwa on the CPU (0.14.0 took a quarter less time than bwa on the machine below, in bwa's RAM); otherwise bwa. All write the same records. bwa-mem3 goes first even with a GPU: on an RTX 3090 with a Ryzen 5 5600X (5M HG002 pairs on hs38, 8 threads), bwa-mem3 0.16.0 --compat=bwa-mem on the CPU took 97.7 s (761 s of CPU time) and wgse-bwa --cuda 131.4 s (1006 s), against upstream bwa's 472.5 s, all with bwa's records (measured, #674/#736; bwa-mem3 as wgse-bwa-mem3, the same engine built without Bioconda's malloc override, which crashes on that host's glibc 2.44).
  • What it needs: only the NVIDIA driver; no Docker and no Parabricks licence. It checks the GPU's free memory before uploading the index (about 4.7 GiB for hs38). It needs about 0.75 GiB more RAM than bwa, and the same sort-memory reduction as on a Mac applies.
  • Provenance: the result manifest records native_aligner_backend as cuda.
  • --gpu: still means Parabricks, which also sorts and marks duplicates on the GPU.

Long reads work the same way with wgse-minimap2 0.4.0 or later (minimap2 2.31), which also writes its upstream aligner's exact alignments (native/README.md):

  • When it runs: align and realign run wgse-minimap2 --backend auto in place of minimap2 for ONT, HiFi and other long reads. Its base-level gap fills run on the GPU and the rest on the CPU. Short reads (sr) stay entirely on the CPU.
  • Slice gains (measured): on the RTX 3090 machine above (8 threads), 40k HiFi reads took 20.4 s against 32.5 s on its CPU backend and 45.6 s with Bioconda's minimap2. 47k ONT reads, which spend most of their time chaining, took 100.7 s against 111.6 s.
  • What it needs: about 0.7 GiB of GPU memory, which it checks for (keeping 1 GiB spare) before using the GPU. It needs about 1 GiB more RAM. When only that extra RAM wouldn't fit, it runs on the CPU. On a Mac, wgse-minimap2 still runs on the CPU.

On the same Linux host, a streamed whole-genome HG002 ONT realign with CUDA finished about 8% sooner than upstream CPU minimap2 (15.3 h vs 16.6 h) and produced identical sorted decoded-record digests; see whole-genome ONT requirements for the measured setup, memory, VRAM and disk. The slice gains above are mapping-only and exclude input decoding, methylation-tag preservation, sorting and output encoding. The native backend notes record a newer 93,328-read HG002 ONT CPU profile: sorting and chaining took about 64% of CPU time, dual-affine gap alignment 18.3%. Its native CPU records matched upstream 2.31 exactly. Real CUDA kernel and synthetic-genome failure/fallback tests also passed on the RTX 3090.

On Linux ARM64 (for example Graviton, Ampere or Cobalt), the linux-aarch64 wgse-bwa package has no GPU backend; its CPU backend runs bwa's steps with the same exact NEON replacements as on a Mac, and align and realign run it in place of bwa the same way (native_aligner_backend is cpu). On a 16-vCPU Cobalt 100 (Neoverse N2), wgse-bwa 0.10.0 aligned the first 5M HG002 pairs on hs38 in 224 s against Bioconda bwa's 282 s (−20%, median of three interleaved rounds, 16 threads, -K 10000000), with the same alignments (measured, native/bench/bench.sh).

DeepVariant on NVIDIA GPUs without Parabricks (wgse-deepvariant)#

On Linux x86-64, WGS Extract's wgse-deepvariant 0.2.0 or later (DeepVariant 1.10.0 without Docker; native/deepvariant/README.md) runs call_variants on an NVIDIA GPU through CUDA, or on the CPU.

Updating WGS Extract preserves the optional deepvariant environment. To upgrade an older install, rerun pixi install -e deepvariant from the updated checkout. Haploid chrX/Y/MT calling requires 0.4.0 or later. Replace any older standalone wgse-deepvariant on PATH too, since it takes precedence.

  • When it runs: with deepvariant_native = "auto" (the default), wgse-deepvariant installed (on PATH, or pixi install -e deepvariant, which installs 0.4.0 from linux-deepvariant-4) and deepvariant_weights set to its weights folder (wgse-deepvariant-weights-1.10.0, with both models), vcf deepvariant calls the WGS model with it instead of Google's image: on the CPU, or with --gpu on the GPU instead of Parabricks; from 0.3.0, ONT reads' ONT_R104 model too (#739). Until deepvariant_weights is set, an installed build is ignored. Other models, --checkpoint and Ultima reads keep Google's image and Parabricks; deepvariant_native = "off" keeps them for everything.
  • Same calls: the same sites, genotypes and filters as Google's image on HG002 chr20, and the same GIAB v4.2.1 counts; QUAL differs by at most 0.5 and GQ by 1 at a few thousand of 210,390 sites, as on a Mac. On HG002's ONT chr20, 2 of 387,476 sites differ (outside GIAB's confident regions), with the same GIAB counts, and the same phased genotypes and phase sets elsewhere; call_variants took 45 s on the GPU against 22 minutes in Google's CPU image.
  • What it needs: the NVIDIA driver; no Docker and no Parabricks licence. Before its first stage, --gpu checks that the build has CUDA (the cuda129 package) and that nvidia-smi sees a GPU; before call_variants, that GPU 0 has 3 GiB free (--no-gpu-memory-check overrides it): it used 2.3 GiB at its default batch of 256 on an RTX 3090. --gpu never falls back to the CPU: a GPU that fails stops the run, which resumes from its finished stages.
  • How much faster (measured, HG002 35x, 4 threads, RTX 3090): on chr1 and chr20 (823,376 sites, 270,091 call_variants examples), vcf deepvariant --gpu took 17 minutes end to end (call_variants 72 s), against 41 minutes without --gpu and 93 minutes for Google's CPU image (call_variants 50 minutes), with the same GIAB v4.2.1 counts. On chr20 alone call_variants took 19.5 s, against 79 s for Google's own TensorFlow GPU image on the same GPU. For a 30x genome, about ten times chr1 and chr20, that is about 3 hours on 4 threads with the GPU, mostly make_examples, against about 15 hours for Google's CPU image (projected). See resource estimates.

Apple Silicon (Metal)#

WGS Extract publishes its own builds of four aligners for Apple Silicon Macs: wgse-bwa (bwa 0.7.19), wgse-bwa-mem2 (bwa-mem2 2.3), wgse-bwa-mem3 (bwa-mem3 0.16.0) and wgse-minimap2 (minimap2 2.31). Each writes the same alignments as its upstream release and reads the same index files; wgse-bwa, wgse-bwa-mem2 and wgse-bwa-mem3 can run some of the work on the Metal GPU. Install them as the Installing section of native/README.md describes; WGS Extract doesn't install them.

When one is on PATH, align and realign run it in place of bwa, bwa-mem2 or minimap2 (native_aligners = "auto", the default; --native-aligners off or native_aligners = "off" in config.toml turns this off). The upstream aligner is still needed: it builds missing indexes. Each run asks the build for its capabilities --json once and logs which binary runs; a build that fails the check, or is older than the oldest supported release, raises the native_aligner_unusable warning and the upstream aligner runs instead.

  • bwa-mem3. bwa-mem3 writes bwa's exact records with --compat=bwa-mem and bwa-mem2's with --compat=bwa-mem2 (@PG aside), from bwa-mem2's index without its .0123 file. On 5M read pairs on hs38 it was 1.8 times as fast as wgse-bwa and 1.5 times as fast as wgse-bwa-mem2 on the GPU, for about 11 GiB of memory against 6 and 11.5 GiB. So when the reference has that index, wgse-bwa-mem3 runs in place of bwa or bwa-mem2 (whichever --aligner or auto chose) in the matching --compat mode, if its pipeline fits: Otherwise wgse-bwa or wgse-bwa-mem2 runs as below. Ultima reads keep BWA. The records are the same either way; see the parity results below.
    • In bwa's place it needs more memory than bwa, so the alignment's memory estimate with it must fit the RAM available when the run starts (and the Mac's RAM less 2 GiB). On 8 to 16 GB Macs wgse-bwa usually runs instead.
    • In bwa-mem2's place it needs less memory than bwa-mem2, so it runs when its estimate fits the Mac's RAM less 2 GiB or is no more than that of the bwa-mem2 that would run instead (wgse-bwa-mem2 0.5.0 and later, which also leaves out the .0123 file, may need less, and then runs). An explicit --aligner bwa-mem2 still stops before aligning (and before realign extracts FASTQs) when that estimate doesn't fit the RAM available, as bwa-mem2's own would.
  • Metal. These builds normally run with --backend auto when their capabilities report metal_available; wgse-bwa also applies its GPU-specific RAM-fit check below. Stand-in selection uses the rules above. An explicit --aligner bwa-mem3 or --fast selects its Metal backend from capabilities and may continue after a LOW memory warning: those explicit paths do not use wgse-bwa's GPU-fit guard. If the GPU fails during a run, the builds finish on the CPU with the same alignments. wgse-minimap2 runs on the CPU.
  • Memory. wgse-bwa's GPU backend needs about 0.75 GiB more than bwa (8.76 against 7.96 GB peak for 5M read pairs on hs38 at 8 threads), and 0.76 GiB more for a denser suffix-array sample after 20M reads. When the alignment's memory estimate exceeds the Mac's physical RAM less 2 GiB, the sort memory per thread is lowered (768M, 512M, 384M, then 256M; sorting more often doesn't change the output). This also applies when realignment extracts FASTQs rather than streaming them. An oversized CPU estimate does not make an oversized GPU plan safe. Without a speed override, paired Metal BWA tries a staged plan next: the Metal mapper writes a compressed checkpoint, then duplicate marking and bounded compressed sorting run after the aligner exits. Sort buffers may step down to 256M per thread while retaining the stage thread plan. This plan must also fit the same physical-RAM budget. Its manifest mode is alignment_mode="staged_metal", reason memory_budget_metal_staged. If even staging cannot fit (or for CUDA), wgse-bwa runs on the CPU. If its pipeline with the requested sort memory is also over budget, sort memory is capped at 256M per thread; an already smaller budget is retained. The conservative CPU estimate can still report LOW: this is not a reservation or a guarantee of RAM fit. Momentarily low available RAM warns without forcing a large-RAM host onto CPU; streaming realignment retains its existing available-RAM check. CPU fallback was about 2.5× slower on the measured 16 GB M1 whole genome. To favor speed despite the swap risk, pass --prefer-native-gpu or set prefer_native_gpu = true in config.toml. Normal GPU-fit sort step-down runs first. Only when none fits does the preference permit the concurrent GPU plan instead of RAM-safe staging/CPU fallback: explicit --memory is retained, while default/config memory is capped at 256M, subject to general sort limits. --no-prefer-native-gpu overrides config. The manifest records native_aligner_backend_reason="memory_budget_cpu" on fallback ("prefer_gpu" on opt-in), estimate/budget bytes and requested/ actual sort memory; a fitting stepped-down Metal plan uses "memory_budget_metal_low_sort" (CUDA: "memory_budget_cuda_low_sort"). A resumed run retains these diagnostics; an ineffective preference changes neither the reason nor the journal key. Whole 35x Metal/sort256 retained exact records at 5.08 h, but still moved 378.39 GiB swap-out versus CPU's 47.87 GiB: it failed the under-200-GiB gate, so CPU remains the automatic low-memory choice when no GPU plan fits. Workers and the batch size (-K 100000000) never change. Reducing K changes alignment records, including MAPQ and duplicate flags, so it is not an identity-preserving memory adjustment (#747). wgse-bwa-mem2 is chosen only when bwa-mem2's own (CPU) memory estimate fits, so a GPU too small for its index tables, where it finishes on the CPU, still fits. Before 0.5.0 that estimate counts the 6.2 GB .0123 file (hs38), which keeps it off 16 GB and smaller Macs; from 0.5.0 neither backend loads that file (10.9 GiB peak for 5M read pairs on hs38 at -K 10000000, against 16.3 GiB for 0.4.1), so the estimate and the explicit --aligner bwa-mem2 memory check leave it out, and the reference needs no .0123 file for it.
  • Provenance. The @PG header names the binary that ran and its version (for example VN:0.7.19-r1273-wgse-0.7.1). The result manifest lists it under tools and records the native_aligner, native_aligner_version and native_aligner_backend (metal, cuda on Linux, or cpu) metrics; bwa-mem3 runs also record bwa_mem3_mode (compat=bwa-mem, compat=bwa-mem2 or fast).
  • Dense suffix-array file (optional). wgse-bwa 0.11.0 and later can read a side file beside the reference's BWA index that holds the suffix-array position of every 16th row, so it locates seeds with shorter walks: the same alignments for 5M read pairs on hs38, 11.5% faster on the CPU and 7.7% faster with --metal on an M1 Pro, and 7.7% faster on the CPU but only 1.3% with --cuda on a Ryzen 5 5600X with an RTX 3090. The file takes 0.80 GB on disk for hs38 and as much RAM while aligning. It is opt-in and never built or used automatically:
    • wgsextract ref dense-sa --ref <fasta> builds it with wgse-bwa densify-sa (it shows the disk it will take first; --interval 8, 4 or 2 makes a larger file with shorter walks; on x86 Linux interval 8 wasn't clearly faster than 16), --list shows the FASTA's files and the one wgse-bwa would read here, and --delete removes them.
    • align and realign read it with --dense-suffix-array, or dense_suffix_array = true in config.toml (--no-dense-suffix-array turns that off for a run). Otherwise wgse-bwa 0.12.1 or later gets --dense-sa off, so a file left beside the index isn't read. Production 0.11.0 and 0.12.0 cannot parse that switch: the CLI omits it when no side file exists, but refuses alignment if one is present. Upgrade to 0.12.1 or delete the side files with wgsextract ref dense-sa --ref <fasta> --delete; those older builds cannot safely honor the opt-in setting. The memory estimate counts the file as index memory (with the GPU it replaces the denser sample the GPU would build after 20M reads), and the manifest records dense_suffix_array_interval.
    • It is used only when wgse-bwa aligns. When another aligner runs, such as wgse-bwa-mem3 standing in for bwa or bwa-mem2 (faster, with the same records), or bwa-mem2 chosen by --aligner auto, that aligner is kept. Asked to use the file, a run that can't (another aligner, no file, wgse-bwa missing or older than 0.11.0, or a file wgse-bwa won't read: it needs 16 GiB of RAM or more, a file of at most an eighth of it, and an intact file made from this index) raises the dense_suffix_array_unused warning and aligns without it.

--aligner bwa-mem3 asks for bwa-mem3 itself: wgse-bwa-mem3 on Apple Silicon, else (or with --native-aligners off) bwa-mem3 on PATH, for example from Bioconda on Linux; WGS Extract installs neither, and the run stops if neither is there or the reference lacks bwa-mem2's index. It writes bwa's records (--compat=bwa-mem). --fast (which implies --aligner bwa-mem3) runs bwa-mem3's speed preset instead, about twice as fast again, whose alignments differ from BWA's: on 5M HG002 read pairs on hs38, 3.5% of primary records were placed differently (92% of them reads BWA gave a MAPQ below 20) and 2.1% more kept their place with a different MAPQ. So it is never chosen automatically and the run raises the bwa_mem3_fast warning.

Parity on the M1 Pro (SHA-256 of the records, @PG aside): wgsextract align gave the same BAM records with wgse-bwa-mem3 standing in as with bwa and bwa-mem2 on the fake genome, on the same genome with three ALT contigs (ALT-aware through <ref>.alt) and on 5M HG002 read pairs on hs38; see #542.

The builds are macos-aligners-N prerelease assets; see native/README.md for their measured speed. A 30x genome on a 16 GB Apple M1 measures every command, and a whole genome from realign to report, on the smallest Apple Silicon Mac.

bcftools with mimalloc#

On macOS about a third of bcftools mpileup's time goes to the system allocator. wgse-mimalloc is WGS Extract's build of mimalloc 3.6.1 with malloc override on (conda-forge's has it off), from packaging/mimalloc. The published wgse-mimalloc-1 package is pinned by URL and SHA-256 and included in the default Pixi environment on Apple Silicon; pixi install --locked installs it alongside bcftools. When it is installed in bcftools' environment, vcf snp and vcf indel start their bcftools processes, and only those, with DYLD_INSERT_LIBRARIES pointing at it (mimalloc = "auto", the default; --mimalloc off or mimalloc = "off" in config.toml turns this off). The CLI never installs it at runtime.

The records are the same. On 5M HG002 read pairs on hs38 with 9 threads on the M1 Pro (medians of 3 interleaved runs), vcf snp took 102 s against 132 s and vcf indel 155 s against 193 s, with a quarter less CPU time. Each run first checks that bcftools loads the library (macOS drops DYLD_* variables for protected binaries, and a damaged file stops it starting); if not, or if DYLD_INSERT_LIBRARIES is already set, bcftools runs with the system allocator and the log says why. The result manifest's bcftools_allocator metric (mimalloc or system) records which ran. Linux keeps the system allocator.

Native Windows CRAM encoding with mimalloc#

The Windows allocator measurements, #1123 qualified only standalone samtools CRAM 3.1 encoding with a local reference. bam to-cram --cram-version 3.1 selects the installed samtools-mimalloc.exe beside samtools when mimalloc = "auto" (default). --mimalloc off retains the system build. A startup probe requires matching samtools/HTS versions and actual allocator activation; absent or broken variants fall back without downloads. The manifest records samtools_allocator. CRAM 3.0 remains the compatibility default and is not promoted on unmeasured results. Sort, markdup, other conversions, minimap2 and macOS/Linux samtools retain their existing allocators.

Azure Central US D8ds_v7, Xeon 6973P-C (8 logical CPUs / 4 cores), Windows 11 Pro 25H2, 32 GiB RAM and local NVMe; samtools/htslib 1.24, minimap2 2.31, static mimalloc 3.6.1. Only final linking differs between each allocator pair; UCRT itself is not patched. Reference pages can remain resident, so Windows CRAM preflight includes a full-reference cache allowance rather than extrapolating the slice's memory, including regional runs whose headers may fill missing M5 tags from other contigs.

On the M1 Pro, all four workloads missed the same slice gate (−2.30% at best); no macOS allocator change followed. Native Windows sort/markdup/minimap2 missed it too. These workloads and public subsets do not establish universal allocator gains or long-read whole-genome mapping performance.

Other GPUs#

WGS Extract has no GPU alignment for AMD (ROCm) or Intel (oneAPI) GPUs: we know of no maintained aligner for them whose output matches BWA-MEM. Integrated GPUs give no meaningful benefit.

When a GPU is worth it#

  • One or a few genomes: a CPU is fine. A 30x genome aligns overnight on 8–12 threads; set up bwa-mem2 first if you have the memory.
  • Many genomes, or quick turnaround: an NVIDIA GPU with 16 GB+ on Linux turns hours into tens of minutes. A rented cloud GPU works too.
  • Variant calling: vcf deepvariant --gpu and vcf gatk --gpu run Parabricks' DeepVariant and HaplotypeCaller, about a minute for chr20 on the RTX 3090 (measured). CPU DeepVariant is much slower. On Linux x86-64, wgse-deepvariant runs DeepVariant's WGS and ONT_R104 models on the GPU without Docker or Parabricks: call_variants for chr20 in about 20 seconds (measured). Apple Silicon has wgse-deepvariant, a native build with call_variants on the GPU: the original chr20 qualification took about 5 minutes for the whole pipeline on an M1 Pro, with the same calls as Google's image (measured). Its self-contained 0.4.1 build reduces make_examples wall/CPU medians by 10.7%/9.8% against released 0.4.0, retaining chr20 calls and gVCF blocks. A measured HG002 35x whole-genome comparison (ten workers, batch 1024, gVCF) took 8,831.4 → 7,984.3 s wall and 50,708.6 → 46,455.5 s CPU: 9.6% / 8.4% less. Peak RSS grew 11.95 → 13.32 GB (about 1.4 GB), sampled temporary space 29.4 → 29.5 GB, with zero swap growth. All 7,709,239 VCF and 72,210,019 gVCF non-header records, including 64,500,780 reference blocks, have identical full-body SHA-256 hashes. One run each on the 32 GiB M1 Pro only, not a GPU speedup claim or a qualification of the 16 GB base M1; that remains follow-up. See measurements and qualification limits. Linux ARM64 has a native CPU build; native Windows has no DeepVariant (Windows).
