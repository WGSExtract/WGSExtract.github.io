Result manifests, --json and exit codes

Commands describe each run in a JSON document that follows the versioned schema wgsextract.result/1 (JSON Schema draft 2020-12, shipped in the wheel). The document lists what the command read and wrote, what it measured and warned about, and how it ran. Use it instead of parsing log text or guessing output file names.

The bundled schema is generated from the actual writer dataclasses in core/results.py, through core/result_schema.py. Run scripts/gen_output_schemas.py (or just regen) to update it; --check detects drift. Defaulted and nullable fields remain required because the writer emits them. This generation does not add runtime validation or change tolerant readers. The same dataclass graph generates the complete TypeScript writer contract in gui/app/shared/generated/result-records.ts through scripts/gen_server_contracts.py. The GUI's normalized presentation types derive shared fields from it, but its parser still treats external/compact documents as unvalidated input.

  • Manifest file. A command that writes outputs also writes manifests/<output>.manifest.json inside the output directory, atomically (never in the source/lab folder, even when an index such as .bai or .tbi is written beside the lab file). The name is the first output file's name with any compression suffix (.gz, .bgz, .zst, .bz2, .xz) removed. The type extension stays, so outputs that differ only in type keep separate manifests. sample_MT.vcf.gz gives manifests/sample_MT.vcf.manifest.json, sample_MT.fasta gives manifests/sample_MT.fasta.manifest.json, and sample_mtDNA.bam gives manifests/sample_mtDNA.bam.manifest.json. Multi-output commands such as microarray name their manifest after the run (manifests/<sample>_microarray.manifest.json; manifests/<vcf>_<sample>_microarray.manifest.json, with a sample metric, for a sample chosen from a multi-sample VCF). vcf trio always writes manifests/trio.manifest.json, whichever modes ran. Report-only commands (info, info chip, ref status, ref library --list, report-delta, and ref recheck without --save-answers) and deletions (ref library --delete, vep delete, --delete options) write no file, except info --format, whose manifest is named after the first table (manifests/<input>_chromosomes.parquet.manifest.json). A failed run that registered outputs still writes its manifest, with status: "failed". A vcf annotator (clinvar, gnomad, cadd, revel, phylop, gerp, spliceai, alphamissense, pharmgkb, sv-freq) that fails before registering any output, such as on a missing resource file, still records the attempt, so report can show it: as manifests/<output>.failed.manifest.json (manifests/clinvar_pathogenic.vcf.failed.manifest.json), leaving an earlier run's manifest in the folder as it was. The next manifest written under the output's own name removes it. Commands that name their manifest after the run, such as vcf trio and analyze, write it on failure as on success. A manifest never replaces this run's --log-file; when the two would share a name, the manifest is skipped with a warning.
  • --json. This global option prints the same document to stdout instead of the human-readable result, for every command. Logs, progress and anything external tools print go to stderr, so stdout holds exactly one JSON document, even when the run fails. Argument-parsing errors are the exception: argparse rejects them before the command starts, prints the usage text and exits 2 without a document.
  • --result-file PATH. This global option writes the same document to PATH and leaves stdout as it is without --json, for programs that show a command's human-readable output and also read its result, such as the desktop app. It is not listed in --help. Like --json, it writes nothing when argparse rejects the arguments.
  • --card. This global option (or result_card = true in config.toml; --no-card overrides it) also writes <name>.card.html in the output directory (while its manifest lives in manifests/): sample_MT.vcf.card.html with manifests/sample_MT.vcf.manifest.json. The card is a page to view, print to PDF or share. It shows the command, its status, what the command printed, metrics, warnings and output files, with the WGS Extract and tool versions, the input files with their size and an abbreviated fingerprint, the reference and when the run happened. Files and URLs appear by name only. In the printed text, messages and metrics, URLs, the run's files, its path options as given (missing or relative too) and any other path that exists on the computer are cut to their names, and the home folder to ~, so sharing a card doesn't reveal your folders; the manifest in manifests/ keeps the full paths. The page is self-contained: no scripts, nothing loaded from a network. A report-only command that reads a sample, such as info, which otherwise writes no manifest, writes both into its output folder (with no --outdir, where outputs go by default: output_directory or WGSEv6/ beside the input), named after its input and command (sample.bam_info.card.html and manifests/sample.bam_info.manifest.json); one that reads no sample, such as ref status, writes no card. The card is listed in the manifest's outputs with role result_card. A failed run's card shows the error. Help and settings commands (help, config, deps, sample, serve, report-issue) write no card, and neither does a --status run or a run whose card would replace its --log-file. wgsextract serve --card gives every job it runs a card, inside the folders the server may use; a job started with ?card=1 (or card=0) gets one (or not) whatever the server's default; otherwise jobs follow result_card. A read-only MCP session writes none. The card and manifest are written together under a lock, so concurrent runs on one sample can't pair one run's card with another's manifest; a successful run removes an earlier failed attempt's card with its manifest. Internal steps (analyze, benchmark) write no cards. The desktop app asks for cards only for its analysis actions and shows each one when the run ends.

align and realign report the effective lossless output profile (default, archive or calling) in metrics.output_profile; see output profiles.

Repeat calls#

typing str records details.repeat_calls in the manifest and in --json output. These are the same locus-sorted rows as the repeat_summary output (<stem>.str.tsv or <stem>.str.parquet), not the caller's own JSON. details.requested_loci contains the sorted --loci IDs, or [] for a full catalog run. Targeted runs append a digest of the IDs to their .str prefix so their outputs have their own manifests. An unnamed LongTR or STRkit locus uses its catalog interval (contig:start-end, zero-based with an exclusive end) as its locus ID.

  • allele_1, allele_2, ci_1_low, ci_1_high, ci_2_low and ci_2_high are integer repeat counts. allele_1_reads, allele_2_reads and clipped_reads are integer read counts. An uncalled allele or a bound or support count the caller could not provide is null (blank in TSV), not zero. A hemizygous call has no second allele. No-call variants from the caller are retained with any coverage it reported.
  • coverage is caller-reported locus coverage, rounded to one decimal. clipped_reads counts reads that meet the unsized-expansion warning rule for long-read callers; zero means no such signal was reported.
  • status retains the readable classification and caveats. confidence is low for a no-call, incomplete or low-support call, a below-threshold estimate whose CI reaches the pathogenic range, an unchecked expansion motif or evidence of an unsized expansion. not_assessed does not mean high confidence. normal_max and pathogenic_min are nullable integers (- in TSV); custom loci without thresholds are sized but not classified.
  • normal_repeats, flagged_repeats and unconfirmed_repeats summarize the calls. An unconfirmed call can also be flagged, for example when clipped reads suggest an expansion. The personal report reads this manifest without running a caller.

Fingerprints#

Inputs, outputs and the reference carry a wgse-fp1:<sha256 hex> fingerprint. It is a SHA-256 of the file size plus the whole file when it is at most 3 MiB, or of three 1 MiB blocks (head, middle, tail) when it is larger. That costs at most 3 MiB of reads, even for a 100 GB BAM. Hashing the whole of such a file would take minutes. The mtime is not hashed, so a copied file keeps its fingerprint. Only regular files are read. A named pipe, /dev/stdin or a process substitution is recorded with size_bytes and fingerprint set to null and is never opened, so the command still gets its whole stream. align separately spools one-shot read streams before validating and mapping them; fingerprint collection itself still never consumes stream input.

A fingerprint identifies a file cheaply ("is this the same BAM as last time?"). It is not an integrity check: an edit outside the sampled blocks that keeps the size goes unnoticed. Use wgsextract sign for full-file digests.

Run lineage and artifacts (pilot)#

The pilot of #1182 links the manifests of a BAM/VCF workflow, such as vcf snp followed by analyze comprehensive --vcf-inputs, without a separate lineage file.

  • run. Every document has a run record. id is a random 32-character identifier of this run. root is the first run of its workflow (this run's id when nothing started it). parent and step name the run that started this one as a step, or are null. analyze starts its steps' commands as steps of itself, and vcf chain-annotate does the same for its annotators. A workflow lists its steps in children: step, the run and command that did the step's work, status (ok, failed, cancelled, or reused when the step journal skipped it), and the journal's reason. A reused step names the run that did its work in the earlier run, and so do the artifacts of the files it wrote. A step done inside the workflow's own process names the workflow's run. A step whose command failed is listed with its run, whose own failed manifest names this run as its parent; one whose command never started or left no result has run: null. A step interrupted by cancelling the run is cancelled, like the run. vcf chain-annotate lists each annotator it ran or reused (step is the annotation, such as clinvar), since their manifests are removed with the intermediates.
  • artifact. A BAM, CRAM, VCF or BCF in inputs or outputs has an artifact record. Other files have none.

It names the reads only when its samples are among their @RG SM (for a CRAM, whose header isn't read, when no other VCF went into it). Empty when nothing vouches for that: an external VCF, one whose samples were renamed, or one another VCF without called_from and with the same samples went into (vcf phase of an external VCF, or an external VCF annotated from recorded calls).

The facts come from the file itself: its header (read without running a tool; a CRAM's header isn't read, so its assembly and samples are unknown), its index and its fingerprint. A producer is taken from the manifest beside the file only while that manifest still lists the same fingerprint and names a well-formed producer (one recorded as unknown stays unknown). A server job reads only manifests and indexes in the folders it may use, and so do the steps it starts. A copied, edited or third-party file is external, and nothing about its history is assumed. An output's sources are the run's BAM/CRAM/VCF/BCF inputs, unless the command names them. vcf call --merge names the reads and its per-type VCFs, which it deletes after merging. They stay in sources with lifecycle: temp and retained: false, and they are not listed in outputs. analyze's findings name only the VCF they were found in.

Exit codes#

CodeMeaning
0Success.
1Failure: bad input, a failed tool, an unexpected error.
2Usage error: a missing or invalid option, or an argument-parsing error.
3Missing dependency: a required external tool is absent, will not run, or is too old, including when a command reports it as part of its own failure message.
128+NStopped by signal N (130 for Ctrl-C).

How refusals are classified:

  • Your option choice is unsupported → 2. Conflicting flags (vcf sv --pacbio --ont, align --r2 with ONT, Ultima or pbmm2 reads, vcf gatk --scatter --gpu, a --batch-size that is not positive), aligner, preset and platform combinations that align and realign refuse (--preset with BWA, BWA for long reads, pbmm2 for ONT, --gpu with ONT, Ultima, bwa-mem2, PacBio CLR/subreads or a minimap2 preset Parabricks lacks, pbmm2 with a temporary directory), vcf deepvariant --gpu with --checkpoint or a model Parabricks lacks, conflicting DeepVariant model selectors, a Clair3 --model for another platform, a malformed vcf sv --region, bam merge with fewer than two distinct inputs or an --output extension that contradicts --cram, bam to-ubam without exactly one of --input and --r1, methylation --combine-strands with a non-CpG context, sign verify --allowed-signers without --identity, a non-positive benchmark --coverage or --target-count, qc fake-data --legacy-bam --full-size, example-genome download --method aspera without a key, a resource file option of a vcf annotator (--clinvar-file, --gnomad-file, --cadd-indel-file, --gnomad-sv-file and the rest, or its config.toml setting) that names no file, and options this platform cannot honour while the command itself can run: --gpu off Linux x86-64, and --aligner pbmm2 on Windows. Choosing different options fixes the run.
  • The command or input is unsupported here → 1. A command with no native build on this platform (for example vep, typing, vcf deepvariant or vcf sv on Windows), or an input that needs one (Ultima reads needing GATK, or vcf deepvariant --gpu on reads it detects as Ultima). No choice of options would help.
  • A required tool is missing → 3. This includes deps check when a mandatory tool is missing, deps check --tool NAME when NAME is not found, and a missing container setup (Docker or its daemon, an image, or for --gpu the NVIDIA driver or container runtime, or curl/ascp for example-genome download). Missing optional tools are reported but keep exit 0.

Versioning#

Adding optional fields, warning codes, output roles, metrics or details keys is backward compatible and keeps wgsextract.result/1. Removing or renaming a field, or changing its meaning or type, requires wgsextract.result/2 and a new schema file. Check schema before reading a document.

The envelope fields are stable; details, metrics values and provenance.params are experimental, because they follow each command and its unvalidated scientific calls. Output contracts lists every tier and how each change is checked against the previous release's pinned baseline.

Compatibility#

info chip --json and ref status --json existed before the manifest. Their previous payloads are now the manifest's details: the info chip detection (or {"revisions": [...]} with --list), and the ref status object. Read .details where you used to read the top-level document. ref status --values is unchanged.

In ref status --json, details.bootstrap reports whether support assets are installed, their installedVersion (null if it cannot be determined), the CLI's availableVersion, and its archive size in downloadBytes (null if not in the local catalog). updateAvailable is true only when a known installed version is older than the available release. This lookup is offline.

Coverage#

These commands record full manifests: info (including --detailed), info chip, info calculate-coverage, info coverage-sample, ref status, align, realign, every vcf subcommand, every extract subcommand, lineage mt-haplogroup, lineage y-haplogroup, lineage y-str, lineage y-private, microarray, every bam, qc, ref, vep and typing subcommand, analyze, pet, methylation, repair, benchmark, example-genome download, sign and report.

align and realign record the aligner (bwa, bwa-mem2, bwa-mem3, minimap2 or pbmm2) and the alignment's records. When bwa-mem3 ran, bwa_mem3_mode records its output: compat=bwa-mem (bwa's records), compat=bwa-mem2 (bwa-mem2's) or fast. When one of WGS Extract's aligner builds ran in the aligner's place they also record native_aligner (for example wgse-bwa, or wgse-bwa-mem3 standing in for bwa), native_aligner_version and native_aligner_backend (metal or cuda when it ran with --backend auto for that GPU, which uses the GPU where it can and otherwise finishes on the CPU, so the GPU may have done none of the work; cpu when it ran on the CPU only), and list the build under tools. For a BAM also mapped_records and unmapped_records (from the index, without decoding reads). CRAM counts come from container headers, which also count unmapped reads placed beside their mates, so a CRAM reports records only. Variant callers and annotators record variants per output VCF; vcf snp and vcf indel also record bcftools_allocator (mimalloc when bcftools ran with wgse-mimalloc on Apple Silicon, else system; see hardware.md); filtered outputs (--min-score, --max-af) are separate outputs with their own counts. With --reference-evidence gvcf the gVCF is an output with role reference_evidence, whose metrics are its provenance (engine, quality_model, bands, ploidy_policy, ...), and its index one with role reference_evidence_index; see reference-evidence.md.

Other commands' metrics:

  • vcf pharmcat records the source, callability thresholds, and counts of absent definitions filled or left missing in details.pharmcat_reference_evidence. The pharmcat_reference_evidence output also lists the definitions it couldn't fill.
  • bam subcommands that write a BAM/CRAM record its records as align does (an unsorted or unaligned BAM has no index to count from, so it has none); bam merge adds merged_inputs, read_groups and, for indexed inputs, the combined autosomal_depth (each run's in details.runs); bam unalign its read_groups.
  • Y extractions (extract ydna-bam, extract y-mt-extract, extract region --target y|ymt) record each output's y_scope and its comma-separated contigs; details holds y_scope and contigs, one row per considered contig (name, length, role, included, reason, and for a BAM its mapped_records and placed_unmapped_records). See Y-associated contigs.
  • qc fastp records read counts before and after filtering, the Q30 rate and duplication rate; qc fastqc the module pass/warn/fail counts and total sequences (r2_-prefixed for --r2); qc vcf the bcftools stats totals (records, SNPs, indels, ts/tv).
  • analyze reads each step's result document (the steps still print their tables and results) and includes the step's manifest (role step_manifest), its outputs with their metrics and its warnings with their details (tagged with step), even for steps that write no manifest such as info --detailed; plus sex and significant_variants.
  • methylation records sites, median coverage and weighted percent modified per modification (and, with --format parquet, the rows of the bedmethyl_table); typing the called genotypes (cyp2d6_genotype with cyp2d6_call_status, Cyrius's cyp2d6_call_info and candidate cyp2d6_raw_star_alleles, and cyp2d6_cyp2d7_copy_number, Cyrius's combined CYP2D6+CYP2D7 copy number; one diplotype per HLA gene, flagged repeats, SMN1/SMN2 copy numbers with sma_carrier and sma_affected); repair the records read and repaired.
  • vcf prepare records records_in, records_out, the input's compression and index state and the number of repairs, with one vcf_prepare_* warning per repair (variants.md).
  • microarray on hg38 input records how the hg38-to-hg19 liftover placed the CombinedKit's sites: liftover_lifted, and the no-calls by reason, liftover_unmapped, liftover_alt_contig, liftover_ambiguous (more than one placement) and liftover_collision (sharing an hg19 position with a different site, or with one of its several placements). Each vendor kit and the kept combined_kit_hg19 carry the same counts, so a rerun that reuses them reports them too.
  • vep records inputs, succeeded, skipped and failed, and variants per annotated VCF; a directory of inputs writes vep.manifest.json.
  • Reference installers (ref library --install, ref bootstrap, the annotation downloads, ref gene-map) record every file they add or change in the library; ref index its new index files; ref count-ns the N totals.
  • benchmark records its report files and step counts in benchmark.manifest.json in the run directory.
  • report records its documents, the source manifests it read (role manifest), the number of findings (and findings_<label> per confidence label) and each section's status (section_<name>), with a section_failed warning per failed section and a newer_attempt_failed warning per section showing an older result than the step's newest, failed attempt; its details is the wgsextract.report/1 document (personal-report.md).

repair in pipe mode (no --input) streams to stdout, so --json is a usage error there. Commands that only print (deps, info listings, ref library --list, config) record no outputs.

Alignment implementation#

Alignment output registration, streamed BAM/CRAM publication and atomic index staging are shared in commands/alignment/output.py. Existing commands.align callers use the same helpers through its import interface.
