Working with professional pipelines

WGS Extract is a desktop toolkit, not a pipeline framework. For production cohort work, the community-standard Nextflow pipelines are nf-core/sarek for short reads and EPI2ME's wf-human-variation for Oxford Nanopore. This page covers three things:

  • handing our BAM/CRAM files to those pipelines (or to GATK directly);
  • bringing their VCFs back for the consumer-facing features, such as microarray kits, haplogroups and reports;
  • putting our metrics into the same MultiQC report as everything else.

Our files#

OutputFormat and conventions
align, realignCoordinate-sorted, indexed BAM or CRAM (--format). There is one read group: ID is the reads' file stem, SM/LB come from --sample, and PL comes from --platform. Duplicates are marked with samblaster on short reads. There is no base quality recalibration.
CRAMDecodes only with the exact FASTA it was written against, which is the one in your reference library (ref library --list). Pass the same file to every downstream tool. A different "GRCh38" (for example GATK's Homo_sapiens_assembly38.fasta against our hs38DH) has different extra contigs and cannot decode it. When in doubt, convert with bam to-bam. Tools we run never fetch a CRAM's reference over the network: while a command runs, htslib's REF_PATH keeps only your local entries (http, https and ftp entries are dropped), or is htslib's local hts-ref cache folder when you have none, so a missing reference fails instead of being looked up on EBI's server.
vcf snp/indel/gatk/deepvariant/...bgzipped, tabix-indexed, single-sample VCF named after the input, with chromosome names as in the reference.
vcf table<stem>_variants.tsv and <stem>_variants.sqlite: one row per carried ALT allele with fixed, typed columns (position, gene, consequence, HGVS, ClinVar, gnomAD AF, genotype, depth, ...). See Variant table.
--format parquetTyped, zstd-compressed Parquet copies of our tables (variant table, methylation, info, microarray genotypes) with provenance in the footer, for DuckDB, Polars, Spark or pandas. See Parquet output.
*.manifest.jsonThe result manifest of each run: inputs, outputs, metrics, warnings and provenance.
wgsextract.sample.tomlThe sample workspace of a genome folder: detected sex, platform, build and depth per input, and your overrides.
*.steps.jsonThe step journal of a resumable workflow: each completed step's settings key and input and output fingerprints.

Run wgsextract info --detailed on a BAM/CRAM before handing it off. It reports the reference build and model, read length, insert size, duplicate rate and inferred sex, which are what the pipelines below ask for.

nf-core/sarek#

Sarek takes a CSV samplesheet. Our CRAM is already aligned and duplicate-marked, so start at the step after duplicate marking:

wgsextract info --detailed --input sample.cram     # build, sex (XX/XY)
printf 'patient,sex,status,sample,cram,crai\n' > samplesheet.csv
printf 'P1,XY,0,P1_N,%s,%s\n' "$PWD/sample.cram" "$PWD/sample.cram.crai" >> samplesheet.csv

nextflow run nf-core/sarek -r <VERSION> -profile docker \
  --input samplesheet.csv --outdir sarek \
  --step variant_calling --tools haplotypecaller,deepvariant \
  --igenomes_ignore --fasta /path/to/reference/genomes/hs38DH.fa
  • Which step.
    • --step variant_calling skips base quality recalibration. That is right for DeepVariant, and acceptable for HaplotypeCaller on modern data.
    • To recalibrate, use --step prepare_recalibration and give sarek its known-sites resources (--dbsnp, --known_indels).
    • Starting from FASTQ instead (--step mapping, with columns patient,sample,lane,fastq_1,fastq_2) re-aligns everything with sarek's own reference.
  • Reference. Pass the FASTA your CRAM was written against, decompressed with its .fai, plus --igenomes_ignore. Sarek builds the rest of the indexes it needs.
    • --genome GATK.GRCh38 only works for CRAMs aligned to that exact FASTA.
    • Re-align to it first with wgsextract realign if you want sarek's bundled resources.
  • Several samples. Add a row per sample and --joint_germline to get a joint-called VCF.

wf-human-variation (Oxford Nanopore)#

wgsextract bam to-bam --input sample.cram --outdir handoff    # if you have a CRAM
nextflow run epi2me-labs/wf-human-variation -profile standard \
  --bam handoff/sample.bam --ref /path/to/reference/genomes/hs38DH.fa \
  --sample_name SAMPLE --snp --sv --out_dir wf-hv
  • Reads and methylation. Our align/realign keep the MM/ML methylation tags on ONT reads, so --mod works on our BAMs.
  • Reference. Pass the same reference the BAM was aligned to.
  • gVCF. Add --GVCF for a gVCF alongside the VCF.
  • Outputs to bring back.
    • SAMPLE.wf_snp.vcf.gz (short variants) works with microarray, lineage and the vcf annotation commands.
    • SAMPLE.wf_sv.vcf.gz holds structural variants.
    • Unaligned input comes back aligned as SAMPLE.cram.

GATK directly#

Our BAM/CRAM already carries what GATK requires:

  • a read group with SM, LB and PL;
  • coordinate sorting and an index;
  • duplicate marking.

For example:

gatk HaplotypeCaller -R hs38DH.fa -I sample.cram -O sample.g.vcf.gz -ERC GVCF

wgsextract vcf gatk runs HaplotypeCaller for you. bam to-ubam writes the unaligned BAM that GATK's Best Practices preprocessing starts from.

Bringing VCFs back#

  • Multi-sample VCFs, such as a joint-called cohort or a trio:
    • microarray refuses them unless you choose a sample with --sample. The error lists the samples.
    • The kit and its manifest are named <vcf>_<sample>_..., and the manifest records the sample. vcf to-fasta takes --sample the same way.
  • gVCF input.
    • microarray recognises gVCFs by their reference blocks (<NON_REF>, <*> or . with END=, as GATK, DeepVariant and DRAGEN write them; Sequencing.com's "genome" VCFs are DRAGEN gVCFs) and reads each target SNP from the block or variant covering it.
    • A target inside a 0/0 block is a reference call only when the block passes the same DP/GQ/FILTER gates as alternate calls (default DP ≥10, GQ ≥20, no failing FILTER). MIN_DP, when available, supplies block-wide minimum depth instead of block-start DP. A target inside a ./. block is a no-call, and so is a target that no record covers. Where a block overlaps a variant record, the variant wins.
    • This applies to GRCh37, GRCh38 and T2T/CHM13 gVCFs alike.
    • Absent sites in plain VCFs are also no-calls by default. Unsafe legacy absence-as-reference output requires --assume-hom-ref --min-dp 0 --min-gq 0 (or matching microarray_* settings in config.toml). This does not establish that a site was assessed, in either a VCF or a gVCF.
  • Builds.
    • Microarray kits need the VCF's build in your reference library; pass it with --ref. Reference-block bases come from that FASTA, whose chr1 or 1 naming needn't match the VCF's.
    • GRCh38 VCFs are lifted to the kits' hg19 coordinates exactly as our own calls are.

MultiQC#

MultiQC is how professional pipelines (including both of the above) summarise a run. Our metrics can join that report in two ways.

Without MultiQC installed, write MultiQC custom-content files from the manifests and hand them to any MultiQC run, such as sarek's own:

wgsextract info --detailed --json --input sample.cram > runs/sample.info.json
wgsextract lineage mt-haplogroup --input sample.cram --outdir runs
wgsextract qc multiqc-metrics --input runs --outdir runs/multiqc
multiqc sarek/ runs/multiqc            # our sections join sarek's report

qc multiqc-metrics reads every *.manifest.json, plus saved --json output, under --input. info writes no manifest, so save its --json. It writes:

FileContent
wgsextract_alignment_mqc.jsoninfo: sex, depth, reads mapped, read length, insert size, duplicates, build/model, sequencer
wgsextract_lineage_mqc.jsonlineage: mtDNA and Y haplogroups (with quality), Y-STR panel coverage
wgsextract_microarray_mqc.jsonmicroarray: autosomal calls, homozygosity, kits, worst no-call rate
wgsextract_variants_mqc.jsonRecord counts of the VCFs our callers and extractors wrote
wgsextract_warnings_mqc.jsonCount and codes of the structured warnings each sample raised
wgsextract_general_stats_mqc.jsonSex, depth, % mapped, duplicates, haplogroups and warnings in MultiQC's General Statistics table

How samples, runs and stale files are handled:

  • Sample names. Rows are keyed by sample: the input's file name without its type extension, or the --sample chosen from a multi-sample VCF. Name your inputs as the pipeline names its samples (sarek's sample column), and the rows line up.
  • Repeated runs. When a command ran more than once for a sample, the latest successful run wins.
  • Stale files. Rerunning replaces the files and removes ones whose section no longer has data.
  • MultiQC options. These are standard custom-content files, so MultiQC options such as --sample-names and --ignore apply.

With MultiQC installed (pixi install -e multiqc, version 1.32 or newer, below 2), qc multiqc --input DIR converts the manifests itself and writes one offline multiqc_report.html. The report includes:

  • FastQC reports;
  • bcftools stats output, as written by qc vcf;
  • our sections.

For example:

wgsextract qc fastqc --input sample_R1.fastq.gz --outdir out/fastqc
wgsextract qc fastqc --input sample_R2.fastq.gz --outdir out/fastqc
wgsextract qc multiqc --input out/fastqc --outdir out/combined

Or qc fastqc --input sample_R1.fastq.gz --r2 sample_R2.fastq.gz --multiqc processes both mates and replaces multiqc_report.html in its output directory in one run.

qc multiqc is opt-in: it combines existing reports without rerunning tools or changing their outputs. --input accepts a file or directory; without --outdir, output goes beside the file or into the directory. The output is one standalone multiqc_report.html, never a parsed-data directory, and inherited titles cannot change its filename. Replacing it requires --force; failed replacement preserves the old report. Non-force publication uses atomic hard links against concurrent overwrites; filesystems without them need another --outdir or explicit --force.

The CLI validates MultiQC, never installs it. The optional multiqc Pixi environment is explicit user-managed setup; dev environments include it for tiny real-tool tests. MultiQC is an external GPLv3 tool, not a bundled dataset. Only FastQC, bcftools and custom-content modules run. Version checks, MegaQC uploads, AI summaries and report controls are disabled; no browser opens. The subprocess's standard TMPDIR points to an owned report workspace, not a new application configuration option.
