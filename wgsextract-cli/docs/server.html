Server mode: HTTP/JSON and MCP

wgsextract serve offers WGS Extract's operations to other programs on the same computer: desktop apps, scripts and AI agents. It speaks either a small HTTP/JSON API or the Model Context Protocol (MCP), on stdio or over streamable HTTP.

Both are generated from the typed Python API: the same *Params fields, defaults, config.toml settings, result manifests and error kinds as the CLI. So an operation joins the server as soon as its command moves onto the API. Today they are info, info calculate-coverage, info coverage-sample, info chip, vcf snp, vcf indel, the three lineage commands, microarray, report, lookup and sample show/set/unset.

$ wgsextract serve --allow ~/wgs
WGS Extract server on http://127.0.0.1:41873/v1
Token: 3q2Kx...
  (also in ~/.../state/server/server.json, readable by you only)
Allowed folders: /home/me/wgs
Try: curl -H 'Authorization: Bearer 3q2Kx...' http://127.0.0.1:41873/v1/ops
Stop with Ctrl-C.

On macOS and Linux, Ctrl-C or SIGTERM stops either HTTP server with exit status 0 and removes its discovery file, even during the startup announcement.

Security#

The server runs analyses with your permissions, so it only answers programs you start yourself:

  • It listens on loopback by default. You can opt into another numeric interface with server.listen or --listen ADDRESS[:PORT]; see Remote HTTP access.
  • Every request except GET /v1/health needs Authorization: Bearer <token>. The token is new each time the server starts. It is printed to stderr and saved in <state>/server/server.json (mode 0600), along with the URL and process id, so local clients can find it. Discovery files are published atomically: an interrupted write cannot leave partial JSON or destroy an earlier server's discovery file. The file is removed when the server stops, unless a newer server has replaced it.
  • Requests whose Host header isn't 127.0.0.1:<port> or localhost:<port>, and requests whose Origin is a different site, are refused. This stops a web page in your browser from reaching the server through DNS rebinding or cross-site requests.
  • Paths are guarded. Every path parameter must be absolute. Network and device paths (\\host\share, //host/share, \\?\…, \\.\…) are refused on every system before anything is opened, since Windows sends your sign-in credentials to any host whose share it opens. A path must lie inside an allowed folder as written (with .. removed); only then are its symlinks resolved, and the result must lie inside one too. The allowed folders are those given with --allow, the server_allowed_paths setting, and the dataset_library, reference_library, reference_genome_library and output_directory settings. Of the settings, only the folders that exist are allowed; a missing --allow folder stops the server. Folders a command derives from a path are checked too: a ref FASTA in a genomes folder names the library above it, which must also be allowed. A leading ~ in a path is expanded before it is checked; a text value that may name a file (a region, an output name) must give it as an absolute path, without ~. A symlink inside an allowed folder that points outside it is refused. That holds for the paths a request names; the files a command finds inside a named folder (a reference library's genomes, a model folder's weights, a checkpoint's files) aren't generally checked one by one. The yBrowse installer checks the paths it derives for snapshots, the liftover chain and its staging files, and the reference FASTA and its indexes. The guard limits what a client can name. It is not a sandbox against other programs running as you, which can change the allowed folders (for example retarget a symlink) whatever the server does.
  • Paths recorded in manifests. report reads the outputs that earlier runs' manifests list. Run by the server, it reads only those inside the allowed folders, so a manifest can't lead it to other files.
  • Regions can't pass for options. A region item that starts with - is refused (on the CLI and the API too), and commands pass regions to samtools and tabix after --.
  • Deleting needs an opt-in. Requests that delete data a command didn't make are refused (403 destructive) unless the server was started with --allow-destructive: bam unindex, sample unset, ref library-delete (ref library --delete), and ref gene-map, ref dense-sa and ref test-genome with delete. Over MCP, bam_unindex, sample_unset and ref_library_delete are offered only then, and their tools carry destructiveHint. Regenerating a command's own outputs (restart, force_*) isn't deleting in this sense.
  • Parameters that name programs to run, such as haplogrep_path, or that hide paths inside other text, such as indel_manifest, can't be set by a request. They come from config.toml as usual.
  • Supplied paths are checked before output inference can inspect an input archive. The effective output folder is then checked too, including its real path. Other host-only config defaults stay trusted execution settings; they do not become client-supplied paths.
  • ref download, which fetches any URL, and ref bootstrap, which saves config.toml, aren't offered.
  • Request bodies are limited to 1 MB and must be application/json. Unknown parameters are rejected rather than ignored.
  • HTTP connection admission includes unauthenticated peers and defaults to 32 concurrent sockets (server.max_connections). Excess connections close without allocating a request thread. Request headers and keep-alive idle connections have an absolute 10-second deadline (server.header_timeout_seconds); dripping bytes does not extend it. Completed headers cancel this deadline, so long job waits, event streams and file responses can continue.
  • Over MCP, only read-only queries are offered unless you pass --allow-jobs. Without it, they save nothing: parameters that would save files (outdir, table_format, and info's detailed, which saves the coverage table) are left out of the tool schemas and refused with read_only, and info runs with cache: false, so it reads an existing <input>.wgse_info.json but doesn't write one. Result cards are off, even with --card or result_card = true.
  • Job records and logs (<state>/server/jobs/) are readable by you only.

HTTP API#

Responses are compact JSON, except viewer file bytes. Errors are {"error": {"code": "...", "message": "..."}} with an HTTP status code:

StatusMeaning
400Bad parameters: usage, bad_json or bad_length
401Missing or wrong token
403A path outside the allowed folders (path_not_allowed), a request that deletes data (destructive), or a bad Host or Origin
404Unknown operation or job
409Cancelling a finished job
411Missing Content-Length on an operation submission

A failed analysis is not an HTTP error. Its job finishes with status failed and the manifest's error.

RequestDoes
GET /v1/health{"ok": true, "version": ...}; needs no token
GET /v1Index and the allowed folders
GET /v1/openapi.jsonThe OpenAPI 3.1 document, also wgsextract serve --openapi
GET /v1/opsOperations: op, kind (query or job), destructive when a request may delete data, and a one-line summary
GET /v1/ops/{op}One operation and the JSON Schema of its parameters
POST /v1/ops/{op}?wait=S&card=1Start the operation as a job; the body is its parameters. card asks for its result card (or not), overriding serve --card and result_card
GET /v1/jobs?status=Jobs, newest last
GET /v1/jobs/{id}?wait=S&full=1A job; with wait, block up to S seconds (≤600) for it to finish
GET /v1/jobs/{id}/eventsServer-sent events: status changes and progress; ends when the job does
GET /v1/jobs/{id}/log?tail=NThe last N lines of the job's log (default 200; 0 for all)
DELETE /v1/jobs/{id}Cancel a queued or running job
POST /v1/jobs/{id}/rerunStart a new job with the same parameters
GET /v1/manifest?path=&full=1A result manifest (*.manifest.json); provenance only with full=1
GET /v1/variants?path=&gene=&rsid=&region=&clinvar=&min_confidence=&columns=&limit=&cursor=Rows of a vcf table output; see Lookups
GET /v1/report?path=&section=A sample's personal report; see Lookups
GET / HEAD /v1/viewer-file?path=Read a guarded file or byte range, only with server.viewer_files = true

Operation names are the CLI command with / between words: info, info/chip, vcf/snp, lineage/mt-haplogroup, sample/show. Parameters are the API's Params fields, for example:

curl -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  "$URL/ops/vcf/snp" -d '{"input": "/home/me/wgs/HG002.cram", "region": "chrM", "ploidy": "1"}'
# 202 {"id":"20260105-100425-986af7","op":"vcf/snp","kind":"job","status":"running",...}
curl -N -H "Authorization: Bearer $TOKEN" "$URL/jobs/20260105-100425-986af7/events"
curl -H "Authorization: Bearer $TOKEN" "$URL/jobs/20260105-100425-986af7?wait=600"

A submission can include X-WGSE-Job-ID with a client-generated lowercase UUIDv4. The HTTP server advertises this as "client_job_ids": true in its discovery file and --ready-json output. If the reply is lost, look up the original job with GET /v1/jobs/{id}. After reading the request body, the server returns 409 if that ID already exists, without decoding the JSON or starting a second job. A lookup that does not find the job is not proof that a submission still in flight was rejected.

POST answers 200 if the job has finished by the end of wait, otherwise

  1. A job record holds status (queued, running, succeeded,

failed, cancelled or interrupted), the latest progress, the exit_code and error, and the operation's result manifest as result. The manifest's provenance (tool versions and the full parameters) appears only with full=1, to keep responses short.

Operation submissions require Content-Length (use 0 for an empty body). Requests using Transfer-Encoding are rejected with 400. The server closes the connection if it cannot read the complete request body within 10 seconds.

The event stream keeps the latest 1,024 events per job for active jobs and the 128 most recently finished jobs. Reconnecting with an older event ID returns only the events still in memory. Older job records and logs remain available on disk, but their events are not replayed. Job listings use a compact on-disk index rebuilt from the records on startup.

Lookups#

The server answers three read-only lookups itself, without a job, over HTTP (GET /v1/manifest, /v1/variants, /v1/report) and MCP (tools read_manifest, query_variants, report_section). Their paths must be in an allowed folder.

Manifest and report readers check the document identifier and the object containers they use, not the complete writer schema. Returned field values remain opaque rather than being coerced or cast to canonical writer models. Canonical result/report writer records are generated separately for clients in gui/app/shared/generated/result-records.ts and report-records.ts; those complete contracts must not be substituted for compact or unvalidated loaded documents in server responses. Manifest lookups preserve unknown fields and their values, except that provenance is omitted unless full=1. Report responses project a header with the report file's path plus generated, sample and disclaimer; other top-level report fields are omitted, even when requesting a section. Without section, each section is projected to only status and summary. With section, all fields of the selected section, including unknown extension fields, are merged into that projected header (section fields win on key collisions).

  • Variants. path is a vcf table output: *_variants.sqlite, .tsv or .parquet (needs pyarrow). The filters combine: gene (symbol), rsid (one rsID), region (chr1, chr1:1000 or chr1:1000-2000, named as in the table), clinvar (a ClinVar significance term such as Pathogenic, case-insensitive) and min_confidence (low, moderate or high). columns picks columns (comma-separated over HTTP); empty values are left out. An answer has at most limit rows (default 50, at most 1000); pass its next_cursor as cursor for the next page. The SQLite database is fastest: it uses its gene and position indexes, and starts a page at its cursor. A TSV or Parquet table is read from the start for every page, so use SQLite for paging through large tables. A page whose rows have automated ACMG classes (acmg_* columns, from vcf acmg) also has disclaimer: they are research only, not a diagnosis. Boolean query parameters take true/false, yes/no or 1/0.
  • Report. path is a sample folder, whose newest *_personal_report.json is read, or the report JSON itself (run the report operation first). Without section, the answer lists each section's status and summary; with section (for example pharmacogenomics), it is that section in full, with its findings.
curl -H "Authorization: ******" \
  "$URL/variants?path=/home/me/wgs/HG002/HG002_variants.sqlite&clinvar=Pathogenic&min_confidence=high"
# 200 {"path": "...", "rows": [{"chrom": "chr17", "pos": 43094464, "gene": "BRCA1", ...}], "next_cursor": null}

Jobs#

  • Queries and jobs. Quick queries (info, info/chip, sample/show, ref/status, ref/library-list) start at once. Other operations queue: --max-jobs (setting server_max_jobs, default 1) of them run at a time. Jobs that save to the same folder run one after another, since commands use fixed file names there. ref/index, ref/count-ns and ref/verify save beside their FASTA, so they need no outdir; given a library folder, they also hold its genomes folder. The library installers hold their library and its genomes folder.
  • Isolation. Each job runs the API function in its own worker process. A crash or a cancel affects only that job. Its log, at the CLI's log level (--debug for more), is <state>/server/jobs/<id>.log. A worker gets its job only once the job is recorded as running. If the worker can't be started, recorded or given its job (a full disk, say), the job fails with the reason in its error, the worker is stopped and the slot freed.
  • Cancelling. A queued job is cancelled immediately. A running job gets the API's CancelToken: tools stop, including running containers, and the manifest is written with status cancelled (exit code 130). If the job is still running 30 seconds later, it is killed. As on the CLI, partial outputs are kept unless the atomic_outputs setting is on. align is an always-atomic exception: its failed or cancelled validation/writes preserve previous completed outputs.
  • Persistence. Job records are kept in <state>/server/jobs/<id>.json, so a restarted server still lists the earlier jobs and their results. A finished job whose record can't be saved yet stays listed and is saved once the disk recovers, when another job finishes. Jobs that were queued or running when a server stopped are marked interrupted. Start them again with rerun; commands with step-level resume (step-resume.md) continue from their last finished step. One HTTP server uses a state folder at a time; a second one refuses to start.

Remote HTTP access#

You choose the listening interface. The HTTP/JSON listener accepts numeric IPv4 or IPv6 addresses without forward or reverse DNS resolution. --listen overrides server.listen. An explicit --port overrides any port embedded in either listen value. Without --port, an embedded listen port overrides server_port. Use [::1]:8080 for IPv6 with a port. MCP listeners remain loopback-only.

For a remote connection, configure the HTTP server before starting it:

[server]
listen = "0.0.0.0:8080"
public_url = "https://genomes.example"
allowed_hosts = ["genomes.example:8080", "genomes.example"]
allowed_origins = ["https://app.example"]
viewer_files = true

Non-loopback binds require a nonempty bearer token, an explicit Host list and server.public_url (or --public-url). Set this advertised origin to the connectable URL clients should use, including HTTPS and the external port when you have a TLS proxy. Its canonical authority must appear in allowed_hosts. It cannot be a wildcard bind address. The setting publishes an address; it does not configure TLS or expand the request Host allowlist. Discovery, ready JSON, curl hints and OpenAPI use this public URL; bind_url in non-loopback discovery and the startup warning identify the actual listening interface separately. The public URL option is for non-loopback listeners only. A loopback bind with a saved public URL refuses to start rather than advertise an authority its strict Host policy would reject. An explicit loopback --listen selects local mode and ignores the saved public URL unless you also pass --public-url. The bundled desktop server pins --listen 127.0.0.1 --port 0; its client accepts only numeric loopback ready URLs and refuses redirects before sending tokens or sample parameters. The separately configured remote viewer is an explicit opt-in and does not change ordinary job destinations.

The CLI generates a fresh token at startup; give it to the remote client through a private channel. Remote health requests also require it. The startup warning names the interface and exposed API: anyone with this token can start jobs, cancel them, read logs and lookups, and read viewer files when enabled. Existing destructive-operation and path guards still apply.

Use HTTPS outside a trusted encrypted tunnel. The built-in listener speaks HTTP, not TLS: you provide a TLS reverse proxy and its certificate, including certificate renewal. For example, keep listen = "127.0.0.1:8080" behind a loopback proxy, or bind a private backend interface and firewall it so only your proxy can reach it. A loopback backend retains strict loopback Host/Origin checks; configure the proxy to send the backend's exact loopback Host and omit Origin for backend-to-backend requests. For a non-loopback backend, preserve an authority in allowed_hosts. Neither mode trusts Forwarded or X-Forwarded-* to expand its allowlist. Install your operator-provided certificate on the proxy; the CLI does not fetch certificates or configure it. Plaintext HTTP exposes tokens and genomic bytes to anyone who can observe traffic. Limit network access and proxy logs, especially query strings containing genome paths, to your intended clients.

Non-loopback listeners accept only exact allowed_hosts entries and configured allowed_origins when a request includes Origin. List scheme, hostname and port (if present) for each origin; no wildcard, userinfo, path or trailing slash. Native backend clients can omit Origin. A loopback listener keeps its existing same-origin checks for the job API regardless of these lists.

Viewer files are off by default. Enable them with server.viewer_files. Clients send a bearer token in a header, not a URL or cookie. You allow file paths through server.guard.roots: the same canonical roots established by --allow, server_allowed_paths and existing configured libraries. The endpoint rejects .., network/device paths, symlink escapes, directories and other non-regular files. It provides no directory listing.

On Windows, use an absolute path under a canonical allowed root on a local drive. UNC paths and mapped network drives are not supported. The server opens each component relative to a pinned directory handle and refuses symlinks, junctions and other reparse points along the path, even if they point inside an allowed root. Use the file's direct local path instead.

On Unix, the server pins the canonical path with directory-relative, no-follow opens. On platforms without a safe open method, file serving fails closed with 503 viewer_unavailable; the job API remains available. The path guard is not a sandbox against other programs running as you.

Send Range: bytes=START-END for a closed byte range. The endpoint supports suffix and open-ended ranges too; those and whole-file reads have a 32 MiB fallback limit. Closed ranges can exceed that limit and stream in 64 KiB chunks. An invalid, multipart, unsatisfiable or oversized fallback range returns 416 with Content-Range: bytes */SIZE. HEAD returns the same metadata without bytes, except that a HEAD with no Range returns 200 and the full Content-Length for a file of any size. Read/seek failures after response headers abort the connection instead of inserting an error response into the genomic bytes. Clients must reject an incomplete body. For browser requests, only an exact configured app origin receives CORS access, including preflight for Authorization and Range. The endpoint sends no wildcard CORS or credential/cookie permission. Keep the general API token in your trusted client backend; do not give it to a genome viewer page.

MCP#

wgsextract serve --mcp speaks MCP over stdin and stdout: one JSON-RPC message per line, protocol versions 2024-11-05 to 2025-11-25. It needs no extra packages. Logs go to stderr. Configure your client to start it, for example:

{
  "mcpServers": {
    "wgsextract": {
      "command": "wgsextract",
      "args": ["serve", "--mcp", "--allow", "/home/me/wgs"]
    }
  }
}

Tools are named after the operations, with _ between words: info, info_chip, lookup, sample_show, and with --allow-jobs also vcf_snp, lineage_mt_haplogroup and the others. Each tool's input schema is its Params' JSON Schema. These tools are always offered:

  • read_manifest, query_variants and report_section: the lookups.
  • list_jobs: list the jobs.
  • job_status: a job's status and result. wait_seconds waits for the job to finish.

With --allow-jobs, cancel_job is offered too. Each MCP session has its own jobs, so several agents can run servers at once. When the client disconnects, its running jobs are cancelled and the session's job records are removed; outputs and their manifests stay where the jobs saved them.

  • Query tools wait for the result. They send notifications/progress when the client gives a progressToken, and are cancelled by notifications/cancelled.
  • Job tools return the started job at once. Follow it with job_status.

Results are the job record, as structuredContent and as compact JSON text. A failed analysis or a refused path is a result with isError: true that says why, so the agent can correct itself.

MCP over streamable HTTP#

wgsextract serve --mcp-transport http serves the same tools over MCP's streamable HTTP transport, for clients that connect to a running server rather than start one. It needs the optional mcp package, the official MCP Python SDK: pip install 'wgsextract-cli[mcp]', or pixi run -e mcp from a source checkout (the dev environment has it too). Without it, the command stops and says so; stdio needs nothing extra.

$ wgsextract serve --mcp-transport http --allow ~/wgs
WGS Extract MCP server (streamable HTTP) on http://127.0.0.1:41874/mcp (read-only queries)
Token: 9fJw2...
  (also in ~/.../state/server/mcp.json, readable by you only)
Allowed folders: /home/me/wgs

Point your client at the URL and send the token as a bearer token, for example:

{
  "mcpServers": {
    "wgsextract": {
      "type": "http",
      "url": "http://127.0.0.1:41874/mcp",
      "headers": { "Authorization": "Bearer 9fJw2..." }
    }
  }
}

The token and port are new each launch unless you fix the port with --port or server_mcp_port; a client can read both from mcp.json. The server is guarded like the HTTP API: it listens on 127.0.0.1 only, refuses requests without the token (401 unauthorized) or with a foreign Host or Origin (403 bad_host, bad_origin), and limits request bodies to 1 MB. The tools, --allow-jobs, --allow-destructive and the path guard are the same as on stdio.

Unlike stdio, every client of one server shares its job list: anyone with the token sees and, with --allow-jobs, can cancel all of its jobs. A query whose call is cancelled, or whose client disconnects, cancels its job. Started jobs run until they finish or the server stops, which cancels the running ones and removes the job records, as on stdio.

Workers use the same config.toml as the server (--config). A request parameter that is left out takes its setting, as on the CLI.

A program that starts the server itself, such as a desktop app, passes --ready-json. Once the server listens, it prints {"url": ..., "token": ..., "pid": ...} as one JSON line on stdout, so the program needn't parse the banner or find the state folder. It works for the HTTP API and MCP over HTTP, not MCP over stdio, and not with --json. If the server can't start, for example because another server holds the state folder, it prints {"error": {"message": ...}} instead and exits. Such a program should also pass the global --parent-pid with its own process ID (wgsextract --parent-pid PID serve ...), so the server exits when the program dies, even when it is killed.
