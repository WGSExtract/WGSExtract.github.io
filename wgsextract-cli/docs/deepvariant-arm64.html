Native Linux ARM64 DeepVariant

The CPU path uses a locally built DeepVariant 1.10.0 image on Linux aarch64. Google's released image is x86-only; this is an unofficial native source build, not an official Google ARM distribution. No QEMU, x86 image, ONNX conversion, INT8 quantization or BF16 autoconfiguration is used.

Provision dependencies explicitly#

Install native Docker, Git and Python 3 before building. The CLI never installs dependencies or pulls/builds an image when calling variants. Building is a separate, explicit administrator/developer action; use a native ARM64 Linux builder with 64 GB RAM and enough disk space for Bazel/TensorFlow.

From a checkout of this repository on that builder:

bash packaging/deepvariant-arm64/build.sh out/deepvariant-arm64-build

This creates and loads localhost/wgsextract-deepvariant:1.10.0-arm64, the Linux ARM64 default. The localhost/ prefix prevents Docker Hub namespace resolution; there is no published image to pull. One multi-stage Dockerfile uses its internal builder stage directly, including with buildx's docker-container driver, rather than resolving a builder tag from a registry. The build saves the resulting image ID in out/deepvariant-arm64-build/image-id.txt. Architecture checks are not a provenance signature: build from the audited recipe and retain this ID; the CLI does not authenticate arbitrary custom images. For another trusted installed tag or immutable image digest, set the existing configuration option:

deepvariant_image = "my-local-native-image@sha256:..."

Calling uses the normal command and flags, for example:

wgsextract vcf deepvariant -i sample.bam --ref reference.fna -r chr20 -t 16 -o results

Both Docker's engine architecture and the image's linux/arm64 metadata are validated before the caller prepares inputs. An arbitrary PATH launcher is not used on ARM: its Python, native modules and child executables cannot be proved native from its shell-script architecture. The container entrypoint is explicitly overridden to run_deepvariant, preventing community auto-configuration scripts from silently switching inference precision. Writable home/temporary files stay inside the caller's intermediate directory and are removed after the run. CRAM 3.1+ compatibility staging also runs for ARM images, with temporary CRAM 3.0 and its index inside that mounted intermediate directory. The known htslib 1.18 / htscodecs 1.5.1 SSE4 rANS decoder bug concerns x86-64 images, not the ARM build's NEON decoder; staging is deliberately architecture-independent.

Only the default WGS model is enabled on Linux ARM64. WES (--wes), PACBIO (--pacbio), ONT_R104, HYBRID_PACBIO_ILLUMINA, MASSEQ, RNASEQ, ULTIMA (including automatic read-group detection) and --checkpoint are refused, even if a custom image is configured. Other release models are packaged for checksum auditing, not enabled: each requires its own real-data qualification before a future implementation can permit it. Parabricks --gpu remains unavailable.

Apple Silicon Macs#

On a Mac, prefer wgse-deepvariant, WGS Extract's native Apple Silicon build of DeepVariant 1.10.0 (native/deepvariant): it needs no Docker, runs call_variants on the GPU and makes the same PASS calls, genotypes and filters as Google's image. On HG003's whole genome (0.1.1, an M1 Pro, 2 h 42 min) its PASS calls, genotypes and filters match Google's published VCF (two QUAL-0 RefCalls differ) and hap.py against GIAB v4.2.1 gives identical counts; the details are in its README. Install it and its weights from a macos-deepvariant release (0.1.1 or later), put it on PATH, and name the weights folder in config.toml:

deepvariant_weights = "/path/to/wgse-deepvariant-weights-1.10.0-wgs"

vcf deepvariant then runs it instead of Docker, through the same resumable stages (an interrupted make_examples reruns in full). Before each run it checks the build's version and every weight file against its published SHA-256, and stops with the setup steps if either is wrong. Only the WGS model is qualified: WES, PacBio, ONT, Ultima and --checkpoint are refused. A region selection of any size (literals, BED files or both) is passed to it as one BED file, and CRAM 3.1 is read directly (its htslib is 1.25 on ARM, without the x86 image's rANS bug). call_variants' GPU batch follows the Mac's memory, so 16 GB Macs fit. To use the Docker image below even with wgse-deepvariant installed, set deepvariant_native = "off".

Without it, Docker Desktop on Apple Silicon runs a Linux aarch64 VM, so vcf deepvariant takes the same native path there: the default image is the one above, and the engine and image architectures are checked the same way. Google's google/deepvariant image is linux/amd64 only; under Docker Desktop's x86-64 emulation (QEMU or Rosetta) TensorFlow finds no AVX and aborts (exit 134) in the first stage, so an amd64 image is refused before any input is prepared. This holds under Rosetta too: Apple Silicon is detected from the Mac (sysctl hw.optional.arm64), and on every path the image's architecture is checked against the Docker engine's. Without wgse-deepvariant or a native image, use vcf clair3 for ONT reads, vcf snp/vcf indel for short reads, or an x86-64 host.

build.sh runs only on Linux aarch64: build there and move the image with docker save / docker load. The image uses generic AArch64 code (TensorFlow and oneDNN choose kernels at run time, and the build adds no -march), which the Apple M-series cores run; this has not yet been run on a Mac. Give Docker Desktop's VM enough memory for call_variants (about 26 GiB at the default batch size; see --batch-size below), since the CLI caps its plan by the VM's memory, not the Mac's. Native Apple-GPU options are researched in #647.

Source and numerical provenance#

  • Official scientific source: Google v1.10.0, d6b15e21323d9d15b347083f1d256ad62998c4cf.
  • ARM build scaffolding: Lambda-Biolab v1.10.0-arm64.1, ff2a2a949c8dd244908499ceb6a9fda381fcccf6, BSD-3.
  • Only the fork's HTS NEON selection and libssw sse2neon build declarations are retained in scientific directories. Its CIGAR normalization limit, haplotype cap, image-buffer changes and modified inference code are not retained.
  • TensorFlow CPU 2.16.1 and the original 1.10.0 SavedModels/small models are used. Essential Python runtime versions match the pinned x64 Google image, including NumPy, JAX, Keras and ml-dtypes. Fixed internal TensorFlow image settings are not additional user/environment-variable configuration.
  • out/deepvariant-arm64-build/scientific-source.patch records the actual source delta. The image includes the upstream sources/licenses and model SHA256s. All 38 model blobs are checksum-verified against the immutable x64 image google/deepvariant:1.10.0@sha256:962e5a83b1d76aae6990625d47102785f791603f2138aa1fa9aa4fb6a2eecbe6. The relocated Python 3.10 virtualenv and Bazel launchers support the invoking user's non-root UID; system Python is not used to import its native modules. Runfile extraction uses checked unzip argument lists, preserving symlinks and supporting output/TMPDIR paths containing spaces without invoking a shell.

Image metadata alone cannot prove every binary native. Audit the interpreter, TensorFlow libraries, and the ELF modules inside all three Bazel ZIPs using file/ELF e_machine=183, and compare model hashes against the x64 golden. Do not substitute the community image on the strength of its F1 claims: its scientific changes are not equivalent to this source build.

x64 Linux and Intel macOS defaults and commands are unchanged. Qualification evidence, unnormalized VCF differences, matched-vCPU timings and cloud cost are recorded in the task's out/arm64/deepvariant/report.md; a draft PR does not by itself establish full-genome or performance qualification.

Public HG002 chr20 qualification has 210,390 identical sites and genotypes against the pinned x64 control. Differences are confined to QUAL (at most 0.5), GQ (at most 2) and PL (at most 1), not alleles, FILTER, depth or model routing. FP32 TensorFlow kernels differ between architectures; confidence fields are not promised byte-identical. Other models remain unqualified until equivalent evidence exists.

All 81,898 large-model input tensors and decoded candidate variants match exactly. Maximum probability differences before postprocessing are 2.81e-6 (large model) and 2.39e-7 (small model), with no argmax changes. Three repetitions on each architecture have identical within-architecture VCF bodies.

Matched standard 16-vCPU/64-GB Azure guests give a three-run chr20 wall median of 487.97 s on Cobalt AArch64 versus 424.51 s on AMD x64: 14.95% slower, within the 20% target. ARM has 16 physical cores; x64 has eight with SMT. CPU-time medians are 6,614.15 / 6,173.57 s and maximum-child RSS medians 26,979,616 / 12,075,748 KiB (ARM / x64). The native path needs materially more memory.

Completed public whole-genome qualification#

The complete public HG002 35x BAM (46,033,519,192 bytes) was verified on both guests: SHA256 b5f1255aa08ecda8f0ec01682d32d9a37a7327ca21ea681d94c250f6a2f22de6. Both original WGS pipelines completed successfully, with no region restriction. All 7,709,239 REF/ALT sites match; all PASS-site genotypes match. One non-PASS genotype differs: chr1:31445438 CG>C is x64 0/0;RefCall;GQ=20 versus ARM ./.;NoCall;GQ=19. Its unchanged reference argmax has actual Phred scores 19.5000106 / 19.4999183. Original integer rounding and the GQ-20 hom-reference no-call safeguard explain this difference.

Confidence is not byte-identical. There are 244,796 changed records: 241,646 QUAL, 10,521 GQ, 351 PL, five MID changes and the above GT/FILTER change. Maximum QUAL/GQ/PL deltas are 29.7 / 30 / 19, not the smaller chr20 bounds. Two additional numerical effects explain those larger bounds:

  • Six candidates cross the original small-model acceptance thresholds (SNP GQ 20 / indel GQ 28), changing their small/large-model route. Passing-side scores are only 20.0000300 or 28.0000156. Five final MID labels change; the sixth is a multiallelic merge at chr10:24436757 (PL delta 19). All six candidates retain the same argmax across the alternative routes.
  • At chr6:170418998 C>T, the small model's homozygous-alt probability is exactly 1.0 on x64 versus 0.9999998807907104 on ARM. The original capped Phred calculation gives QUAL/GQ 99/99 versus 69.3/69 without changing GT or PL.

Every actual full-run CVO was compared: all 8,286,723 combined candidate keys match, including the six cross-stage substitutions. The 8,286,717 same-stage vectors have no argmax differences; maximum absolute errors are 3.10e-6 (large model) and 4.77e-7 (small model). The actual probabilities, original threshold/rounding source and exhaustive unnormalized VCF differences are saved. Full-genome image tensors were not traced; the tensor-identity claim is chr20-only. These boundaries are disclosed, not hidden by precision changes or VCF rewriting.

Resident-memory diagnosis and optional mitigation#

The reported full-run RSS is the Linux maximum-child RSS, not an aggregate and not multiplied by the 16 shards. Both guests used 16 vCPUs, 16 shards and 4,096-byte pages. Aggregate cgroup memory including cache is a different metric.

A bounded native chr20 replay instrumented all three scientific executables:

StageTimed processesMaximum-child RSS KiB
make_examples16984,812 (each shard at most this much)
call_variants126,971,300
postprocess_variants1, including children626,044

Thus inference reproduces the original chr20 ~27-million-KiB peak and explains the similar full-run 25,920,200-KiB maximum. The original full run did not record per-stage RSS; its stage attribution is corroborated by this replay, not falsely presented as an original full-run measurement.

Actual model convolution tracing shows oneDNN 3.2.1 indirect_gemm:acl, FP32, batch mb1024, on AArch64 SVE-128. The ARM TensorFlow/ACL inference tensor/scratch/buffer working set is dominant. This is a backend/batch footprint, not duplicated biological inputs or extra shards. Separate TensorFlow activations, prefetch buffers and ACL scratch allocations were not individually traced, and x64 primitive-level allocation was not reprofiled.

Allocator experiments preserve the exact chr20 VCF body but do not solve the footprint: MALLOC_ARENA_MAX=2 gives 26,553,356 KiB (only 1.55% lower); TF_CPU_ALLOCATOR_USE_BFC=1 gives 27,035,236 KiB. Neither is installed as a new default or exposed as user/environment-variable configuration.

Google's existing inference batch_size=256 reduces call_variants to 7,981,020 KiB (70.41% lower). All 210,390 records, genotypes and other VCF fields remain byte-identical to the qualified native chr20 body. Instrumented pipeline wall was 537.12 s versus baseline 539.25 s; these are single diagnostic runs, not new full-genome or repeat-median speed claims.

Use the CPU-only, opt-in forwarding option:

wgsextract vcf deepvariant -i sample.bam --ref reference.fna \
    --batch-size 256 -t 8 -o results

It forwards --call_variants_extra_args batch_size=256; no weights, precision or DeepVariant scientific code change. Omit it to retain all existing defaults, including byte-identical x64 command construction. --threads controls make_examples shards, not the inference batch.

Preflight uses the largest sequential-stage budget, not the sum: inference allowance 2 + 30 × batch_size/1024 GiB, 2 × shards GiB, or whole-genome postprocess_variants (see resource estimates), plus 1 GiB driver/headroom. Defaults at 16 shards estimate 33 GiB for inference; the example estimates 17 GiB. A whole genome's 16 postprocess workers would need about 52 GiB, so with less free RAM the command splits postprocess into more partitions, or fewer workers, to fit. These are conservative WGS estimates against reclaimable, cgroup-aware available memory, not allocations or custom-model guarantees. The smaller batch is chr20-qualified; the full-genome results above retain the original default batch. The additional replay compute estimate was $0.8131 (under $2 even with a $0.50 allowance); its resources were deleted.
