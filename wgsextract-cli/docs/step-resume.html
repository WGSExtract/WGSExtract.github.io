Resuming long workflows

A whole-genome realign, vcf deepvariant or analyze comprehensive runs for hours as a series of steps. Each records its completion, so a run stopped by a crash, Ctrl-C, an out-of-memory kill or a reboot resumes when you rerun the same command. Steps that finished are skipped, and the run restarts at the first step that didn't.

CommandStepsJournal
realignextract (BAM/CRAM to FASTQ), align (map, mark duplicates, sort), index<output>.steps.json, e.g. sample_aligned.bam.steps.json
vcf deepvariantstage_reads (CRAM 3.1 inputs only), make_examples, call_variants, postprocess_variantsdeepvariant.vcf.gz.steps.json

When a step is skipped#

When a step finishes, the journal (JSON, schema wgsextract.steps/1) records:

  • a key made from its settings, the versions of the tools it ran and the version of the step itself
  • the identity of each input (see Integrity checks and Directory inputs), and the run of the step that made it
  • the identity of each output, including the files in an output folder (see Directory outputs)

For analyze, it also records the command run that did each step's work, so the workflow's result manifest can name it in run.children when a later run skips the step (see Run lineage and artifacts).

The internal journal's JSON Schema is generated from the Python models used by its writers. Its runningStep and completeStep definitions describe newly written records. Historical records remain opaque at the read boundary, so unknown record fields survive an unrelated write and existing resume decisions do not change. Regenerate with scripts/gen_output_schemas.py (or just regen); --check detects drift.

A rerun skips the step only if all of the following hold:

  • the key is unchanged
  • every input is unchanged, and no earlier step was rebuilt
  • every output is still the one the step wrote

Otherwise the step runs again, and so does every step that uses its outputs. The log gives the reason for each step, for example:

Skipping step extract: complete (2026-11-05T02:16:41+00:00).
Running step align: an earlier run was interrupted during it.
Running step align: settings changed: sample None -> 'Bea'.
Running step align: x_aligned.bam changed size (1048576 -> 1048476 bytes; truncated or rewritten) since the step wrote it.
Running step annotate: its vcf out/snps.vcf.gz changed (sha256 full digest differs).
Skipping step index: complete (2026-11-05T03:02:11+00:00; checked 1 sha256 full, 1 wgse-fp1 sampled).

A skipped step's reason says how its inputs and outputs were checked, and the journal records each file's digest (algorithm and strength).

Settings that don't change a step's output, such as threads and memory, are left out of its key. You can therefore resume with a different --threads.

vcf chain-annotate keeps intermediate VCFs on failure and removes them after success unless you pass --keep-intermediates. Rerun after a failure with the same output folder to reuse completed annotations. Use --force-step clinvar to rerun ClinVar and the steps that depend on it, or --force (--restart) to rerun the chain. With --region or --bed, the chain reads only relevant contigs for steps that can move a variant during normalization or compose one from neighboring records. It then trims to the requested intervals, so those variants are not lost at interval boundaries.

Use --dry-run to see which steps would run or be reused, including publication and any requested table export. It writes the plan to chain_annotate.plan.manifest.json without running the steps or changing the resume journal or the published outputs.

With --tmp-dir or temp_directory, a failed realign retains completed FASTQs in its run workspace. Rerunning the same command reuses those files after checking the journal's inputs, tools and output fingerprints, even though the new run gets a different workspace. On POSIX, the retained directory and FASTQs must belong to the current user and must not be writable by their group or other users; otherwise extraction runs again. Shared temporary roots must belong to this user or root and either disallow other writers or have the sticky bit set. Changed or missing FASTQs are also regenerated. Use --force-extract, --force-step extract, or --force to explicitly regenerate the pair. Temporary FASTQs are removed after the resumed alignment succeeds.

Without --tmp-dir, realign keeps its FASTQs in the output folder between steps, since they are also usable inputs (align --r1 --r2). They stay there when a later step fails, so a rerun skips extract, and are removed once the alignment succeeds. --keep-fastq keeps them as results. Other commands keep all temporary work in the --tmp-dir workspace (or, without one, a hidden folder in the output folder removed when the command ends), and nothing is written beside an input except an index it needs.

Plain VCFs and annotation tables are compressed into that temporary work, not beside their source files. Without a configured temporary directory, prepared copies use a hidden output subfolder cleaned when the run finishes, including on failure or cancellation. Only standalone preparation without an output/work folder falls back to system temporary storage. Persistent output names and provenance still describe the original inputs, including symlinks.

A step's inputs include the data it reads, not just the sample: the reference FASTA, region BED files, DeepVariant checkpoint files and installed annotation data (a new ClinVar or gnomAD release reruns annotate). Tool versions include Haplogrep 3 (and haplocheck with --contamination) for mt-haplogroup and, for DeepVariant in Docker, the image's ID, so replacing an image under the same tag reruns every stage.

Integrity checks#

Each file a step reads or writes is recorded with its size, modification time (to the nanosecond) and a digest of one of two strengths:

FilesDigestStrengthOn resume
up to 64 MiBSHA-256 of the whole filefullHashed again on every check (about 40 ms for 64 MiB), so any change to its bytes reruns the step, even one that restores the size and modification time.
over 64 MiBwgse-fp1: the size and the first, middle and last MiBsampledThree 1 MiB reads (tens of ms, whatever the file's size). Accepted only while the size, sampled blocks and modification time are unchanged: a new modification time alone reruns the step, with the reason was modified.

So an edit in place to a large BAM or FASTQ, even one between the sampled blocks, reruns the steps that read it, while a resume, the GUI or a render never rereads 100 GB just to decide that nothing changed. Moving a file (mv) keeps its modification time and doesn't rerun anything; copying it without times (cp without -p) does. A large file deliberately edited and then given back its old modification time (touch -r) isn't seen; use --force-step after such a change, or wgsextract sign for full-content checksums. A full digest is never taken on trust: it is recomputed, so one recorded earlier can't vouch for a file that has since changed. On Linux and macOS a full digest is reused within one process only while the file's size, modification and change times and inode are all unchanged; on Windows it is rehashed on every check. A file whose digest can't be read never matches, and an output replaced by something other than a regular file (a pipe or device) reruns the step without being read.

A journal written before these digests runs each step once more, with the reason was recorded by an earlier wgsextract without an integrity digest.

Directory outputs#

A step whose output is a folder records the files in it. By default every file in the folder is required: adding, deleting, replacing or truncating one reruns the step, with a reason such as report's contents changed (12 files, 4096 bytes when written; now 11 files, 3900 bytes). Like directory inputs, this uses each file's path, size and modification time, without reading it. Lock files and the hidden .partial files of unfinished writes are left out.

A step can instead declare the folder's required members (members= when it reports the output). Each member then gets the file checks above, and a missing or changed one reruns the step (report/table.tsv, a required member, is missing). Anything else in the folder is disposable, such as a cache, and adding or removing it reruns nothing. A step that declares a member it didn't write fails rather than being recorded complete.

Today the only folders recorded as step outputs are those a command run by analyze comprehensive reports writing (an Ensembl VEP cache it installed), which use the default, every file required.

Directory inputs#

Some steps read a folder rather than a file: VEP's cache for annotate, or a folder a child command reports reading. The journal records such an input's identity from the path, size and modification time (to the nanosecond) of every file under it, following symbolic links and noting where each points. The rerun runs the step again when a file in the folder is added, removed, renamed, resized or rewritten, or a link in it is repointed, including when the whole folder is replaced by a new release at the same path. A folder that can't be listed is recorded as unreadable, so it reruns the step once it can be read again. Lock files (*.lock, *.guard) and the hidden .partial files of an unfinished download are left out, so another run using the same library doesn't force a rerun.

No file is read, so checking a cache of tens of thousands of files costs one stat per file, not a pass over its gigabytes. The trade-off: an edit that keeps a file's size and also restores its modification time (touch -r, or a copy with rsync -t of a file the same size) isn't seen. Use --force-step after such a change. Copying a folder without keeping times (cp -r) changes every time, so it reruns the steps that read the folder.

A journal written by a wgsextract older than this behaviour holds no contents identity for its directory inputs, so the steps that read one run once more, with the reason is a directory whose contents an earlier wgsextract didn't record.

Partial outputs#

A step is marked running in the journal before it starts. It is marked complete only after all of its outputs are written. Outputs are written under temporary names and renamed into place when they are complete. A run killed mid-step therefore never leaves a step, or a file, that looks done. The rerun removes the half-written temporary files, and any output the killed step left, then redoes the step.

Ensembl VEP and Parabricks DeepVariant stage each completed VCF together with its matching index before replacing either final file. A failed or interrupted cross-volume copy preserves the previous readable VCF/index pair.

DeepVariant is the exception that keeps partial work. Until the VCF is final, its stages work in .deepvariant.work in the output folder. A make_examples run that was interrupted keeps its finished shards: GNU parallel's --joblog and --resume-failed rerun only the shards that hadn't finished. Those shards are kept only when the rerun has the same key and inputs. Otherwise the folder is cleared. A resume with a different --threads keeps the earlier run's shard count, and --threads sets only how many shards run at once. Once the VCF is written, the work folder is deleted. With --reference-evidence gvcf the gVCF and its index are postprocess_variants' outputs too: a missing one reruns it, and after the work folder is gone, every stage (see reference-evidence.md).

Options#

Each of the three commands takes these options:

OptionEffect
--force (alias --no-resume)Rerun every step, ignoring the journal.
--force-step STEPRerun STEP and the steps that use its outputs. Repeatable. For analyze comprehensive, annotate and discovery force the step for every VCF.
--dry-runPrint each step, whether it would run or be skipped, and why. Runs nothing.
 
$ wgsextract realign --input sample_hg19.bam --ref hs38.fa --dry-run
realign plan (sample_hg19_aligned.bam.steps.json):
  extract  skip  complete (2026-11-05T02:16:41+00:00)
  align    run   an earlier run was interrupted during it
  index    run   step align runs before it

The plan is also in the run's result manifest as details.steps, along with the metrics steps_run and steps_skipped. Library users see each decision as a step progress event (see the API).

One run at a time#

A run holds a lock on its journal (.<journal>.lock) until it ends. A second run into the same output fails at once and names the lock, instead of both writing one file. The operating system releases the lock when a run dies, even from SIGKILL.

Tools run in their own process groups, so a SIGKILL or OOM kill of wgsextract alone can leave them running, still writing the step's files. Each step tags the processes it starts (WGSEXTRACT_STEP_RUN in their environment, a marker, not a setting) and its containers (a wgsextract.step label). A rerun lists the killed run's tools and containers that are still alive, then stops before running anything:

$ wgsextract analyze comprehensive --input sample.bam --outdir out
A killed analyze comprehensive run's tools are still writing out: bcftools (pid 4242), ...

Wait for them to exit, or stop them (kill PID, docker stop NAME), then rerun.

Limits#

  • Resuming works within a step's boundaries. The rest of an interrupted align (one pipeline from FASTQ to sorted, duplicate-marked BAM) is redone from its start. Only DeepVariant's make_examples shards resume within a step.
  • realign keeps its extracted FASTQs only until the alignment is complete. When they are temporary, they are deleted after the alignment, and the journal notes that. A later --force-step align therefore extracts them again.
  • A container of a DeepVariant stage in Docker outlives a SIGKILL of wgsextract (a Ctrl-C or SIGTERM stops it with docker kill). The rerun finds it by its wgsextract.step label and stops, as for other tools; stop it with docker stop NAME. If the engine doesn't answer docker ps, the rerun can't check, and goes ahead.
  • The GPU (--gpu) DeepVariant path runs as one step, so it doesn't take --dry-run or --force-step.

Chunk assembly implementation#

Raw BAM/CRAM chunk assembly lives in core/alignment/splice.py, called by core/chunked_alignment.py. This binary I/O layer preserves encoded records and is separate from step-journal serialization.
