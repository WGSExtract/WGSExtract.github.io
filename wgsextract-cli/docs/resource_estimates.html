CLI resource preflight and reusable estimates

For measured Apple Silicon GATK PairHMM slice timings, see NEON prototype evidence. These are not full-chromosome or whole-genome measurements and do not change the caller's resource-budget formulas. The incomplete full-chr20 Java trial reached only chr20:29,840,219 after 283.6 traversal minutes before cancellation; it supplies neither a completed runtime nor peak-RSS estimate. Do not size a full-chromosome run by multiplying the 10–20 Mb slice time: slow pericentromeric regions are absent from that slice. The replacement 12.551 Mb panel measured 6,632.06 s Java → 725.96 s NEON double, with maximum process RSS 1,883.9 → 1,509.2 MiB. Its 9.14× observed speedup is not scientifically qualified: nine reference blocks and eight final-VCF annotation rows fail the strict parity gate. PairHMM still consumes 40.3% and 64.0% of NEON CLI wall in its two difficult windows. See the linked per-window evidence and limitations; neither these maxima nor the aggregate speedup size an unpartitioned full genome.

Pipeline benchmarks#

wgsextract benchmark --help lists datasets and profiles. Start with generated chrM and the lighter core operation suite:

pixi run wgsextract benchmark --profile smoke --suite core --outdir out/benchmark-smoke

The default is synthetic; --dataset real is the release-backed mini-genome, while real-1x/real-30x use public WGS data. HTTP downloads resume .partial files and publish only after completion and available checksum verification. example-genome download shares this downloader; FTP/Aspera keep their specialized transports. See download safety. Keep larger runs last and budget CPU, RAM and disk first.

Runtime/workspace depend on coverage, input, hardware and toolchain. Help and realignment stages promise no fixed times; thread-based estimates are advisory. Choose a reproducible dataset/profile before comparing hosts.

Imputation#

vcf impute prints estimated memory and runtime before starting. HG002 chr20 measurements at four threads: GLIMPSE2 phase/ligate 431–464 s and 2.2–3.1 GB peak RSS; Beagle 60 s and 3.4 GB, with 8 GiB reserved. GLIMPSE2's threads don't speed up one sample, so vcf impute runs --threads GLIMPSE2 chunks at once, one thread each, within 80% of the available memory (or --memory per chunk), estimating each chunk's peak from its binary reference; the preflight reports the peak of the largest chunks that run together. The extrapolated whole-autosome GLIMPSE2 time is about 5.6 h one chunk at a time and about 1 h with eight at once, excluding one-time panel preparation. These are not measured whole-genome runtimes. See imputation for the chr20 timings, accuracy and limits.

Whole-genome host requirement#

Before a run starts, realign (chunked or not), vcf deepvariant and vcf clair3 print what it needs of this computer in one line, from the estimates below and the measured whole-genome runs:

Host requirement: this realign run needs ~221 GiB disk on /data/hg002, ~26 GiB RAM, ~21 h on 7 threads (time approximate).

That is the HG002 ONT CRAM of #431 (103.7 GB, streamed from its URL, 26 chunks), which wrote 185.5 GB (172.8 GiB) of CRAM in 21.4 h on 7 threads of a 16 GB M1. The line names every filesystem the run writes to (the output directory, and a temp_directory on another disk) and sums what shares one.

  • Disk is what the run's own preflight checks:
    • realign: extraction, sort spills and output (long reads), and BWA's missing reference indexes;
    • DeepVariant: its work directory and output, for a --region scaled to the share of the input's data it selects (its CRAI slices, or all the BAM index's reads on each contig it touches; the whole input when the index can't say);
    • Clair3's temporary space;
    • for both callers, the CRAM 3.0 copy an older build needs of CRAM 3.1 input, sized as staging sizes it.
  • RAM is the estimate at the run's settings, sort memory lowered as the run lowers it: the aligner's (minimap2 or BWA's), DeepVariant's largest stage, and 16 GiB for Clair3 (15.2 GiB measured with --gpu on 6 threads).
  • Time is approximate. It scales a measured or projected whole-genome time by the work (read bases, CRAM bytes or reference bases called) and divides by the threads, which no step does perfectly, and CPUs differ. It says whether a run takes minutes, hours or days:

That run (830 million reads, 125 Gb) took 6 h; the table predicts about 3.5 h on 8 threads for wgse-bwa on its GPU, which was timed on an RTX 3090. A 30x short-read genome is about 100 Gb of reads: about 20 h for bwa on 4 threads. The callers count the bases they call on contigs the index places reads on.

Refusal. The run stops before it writes anything when this computer can't meet the requirement:

  • a filesystem has less free space than the run needs on it, or
  • this computer has less RAM in total (or its cgroup or Docker VM allows less) than the run can't do without: the aligner's index and working memory on one thread (for minimap2's long reads, the larger of its index build and its mapping: 11.9 GiB for #431's CRAM on hs38, whose index build measured 11.17 GiB) or DeepVariant's largest stage on one thread at --batch-size 256. Sort buffers, samblaster's table and read-scaled transients can swap, slowly. The floor needs the reference's size (its .fai, BWA's .ann, or for minimap2 an uncompressed FASTA's size); without it there is none.

Less RAM than the estimate at the run's settings is a structured host_requirement_memory warning, not a refusal: a 16 GB Mac realigned #431's whole genome on 7 threads by compressing memory and swapping. Lower --threads, --memory or DeepVariant's --batch-size to fit. Clair3's RAM, measured once, is only ever warned about. Free memory is the existing LOW rows' business.

The refusal names the numbers and exits 1, with a host_requirement warning in the result. --no-preflight runs anyway, the requirement turned into that warning. With --json, or in the result manifest, details.host_requirement has the same data: line, disk (paths, needed_bytes, free_bytes per filesystem), memory_bytes, memory_floor_bytes, memory_capacity_bytes, threads, approximate_hours, shortfalls and enforced. A DeepVariant rerun that keeps finished stages needs less than a fresh one, so it only warns. --dry-run and Parabricks (--gpu for short reads, which has its own check) print no requirement.

Other pipelines#

Native align (BWA/BWA-MEM2 and minimap2), realign, bam sort, bam to-bam, bam to-cram, vcf snp/indel/gatk/deepvariant (CPU, every platform) and vcf clair3 report estimates before starting their heavy pipelines. For example:

Preflight align: estimated peak / available (GiB)
Preflight memory OK      18.13 / 24.00 GiB
Preflight disk   LOW     93.86 / 80.00 GiB at /data/results

Each filesystem gets one disk row. Temporary files, output, output indexes, extracted FASTQs when needed, and missing reference indexes are added together when they share a volume, not separately compared with the same free space. GATK's system temporary directory can be on a different volume. A nonexistent output directory is checked against its nearest existing ancestor, without creating it. Available RAM uses the existing native psutil API; disk space uses Python's native disk_usage, including Windows drives.

LOW warns. Some commands also refuse: explicitly selected BWA-MEM2 refuses inadequate RAM, BWA warns, auto can fall back to BWA, whole-file sorting retains its disk guard, and realign, vcf deepvariant and vcf clair3 refuse what their host requirement can't get. --no-preflight bypasses those, not BWA-MEM2's memory guard; informational estimates are still printed. Realignment reports before FASTQ extraction and alignment reports again when the final aligner is selected.

Native wgse-bwa GPU selection must satisfy physical RAM less 2 GiB of OS headroom. Low momentary available RAM alone warns rather than moving large-RAM hosts to CPU; streaming realignment keeps its existing available-RAM guard. Sort memory is lowered through the existing candidates down to 256M per thread. An over-budget CPU estimate is not a larger GPU allowance: if no GPU plan fits, the CPU backend runs. When the CPU pipeline with the requested sort memory is also over budget, sort memory is capped at 256M per thread without increasing already smaller requests. Workers and fixed -K 100000000 are unchanged, preserving alignment identity. The CLI reports the resolved CPU/backend and sort-memory estimate rather than the rejected GPU plan. A conservative CPU estimate can still be LOW; CPU compression, occupied swap and cumulative SSD swap traffic must not be conflated (#747). The read-only estimate_resources API does not change settings itself: callers supply their resolved backend allowance and sort memory. On macOS and Linux, --prefer-native-gpu / config prefer_native_gpu = true can replace a RAM-budget CPU fallback after normal GPU sort step-down fails, at the risk of heavy swap. Explicit --memory is retained on an override; default/config memory is capped at 256M, subject to general sort limits. Windows CUDA is automatic when RAM and commit both fit, and never bypasses either check. --no-prefer-native-gpu forces CPU on Windows. The manifest's native_aligner_backend_reason, native_aligner_memory_estimate_bytes, native_aligner_memory_budget_bytes, native_aligner_sort_memory_requested and native_aligner_sort_memory_actual explain fallback or an override and survive resume. The fallback estimate is the smallest considered GPU plan, not the selected CPU pipeline's estimate. For paired Metal BWA, automatic selection also tries compressed staging before CPU fallback. RAM is the larger of the aligner/checkpoint-writer phase and the duplicate-marking/sort phase, not their sum. Mapper and sort thread budgets come from the resolved stage plan, including explicit overrides; all sort workers' buffers count toward the estimate. The per-thread staged sort budget can step down to 256M to fit, while the fixed scientific batch size remains K100M. Disk is the per-filesystem phase maximum: generated FASTQs plus raw checkpoint, raw plus compressed marked parts, then parts plus final output. Owned generated FASTQs retire after alignment unless kept; the raw checkpoint retires only after all marked parts are durable. Existing resumable checkpoints and owned-read retirement are credited, never user-provided read files. Recovery checks only the selected aligner's index files. Large sidecars use sampled content and file metadata rather than a full read. If streamed extraction left out single-end reads, recovery reports the saved count even after extraction scratch files are gone. The HG002 35× calibration budgets 108/115 bytes per short input read for raw/marked BAM checkpoints and 2 GiB rolling scratch; longer reads scale those allowances. With --output-profile fast, the raw BAM allowance rises to 125 bytes per short input read, leaving the marked parts and rolling scratch unchanged. Preflight also includes the guard's safety reserve once per guarded filesystem, the extraction collation phase, and one bounded intermediate merge group. Merge fan-in stays at64 regardless of the operating system's file-descriptor limit.

Reasons are memory_budget_cpu, memory_budget_metal_staged, memory_budget_metal_low_sort (or CUDA), and prefer_gpu; preference reasons/journal changes occur only when it replaces the RAM-safe plan. alignment_mode="staged_metal" and the checkpoint, chunk-record, compression-level and minimum-free-byte metrics identify staging. On the measured 16 GiB M1 whole HG002 35x run, automatic CPU4/sort256 reported 19.22 GiB / 10.78 GiB available and completed with identical ordered records. Swap-out fell from 1,116.92 to 47.87 GiB, not zero, while alignment wall time rose from 5.40 to 13.63 hours. This is a conservative safety/speed trade-off, not evidence that the estimate should shrink to the 7.60 GiB RSS. See the whole validation and options. The approved whole Metal/sort256 comparison took 5.08 h with identical records, but 378.39 GiB swap-out, versus CPU's 47.87 GiB. It failed the under-200-GiB gate, so it does not justify reducing the working-set estimate or making an over-budget GPU plan the default. Its native footprint/wired peaks were 10.409/5.551 GiB despite only 8.633 GiB largest-child RSS.

The memory estimate is the selected aligner's. On Linux, bwa-mem3 standing in for bwa (--compat=bwa-mem, chosen first since #736) needs about twice bwa's RAM (5M pairs on hs38: 14.7 GiB peak at 16 threads against bwa's 6.6 GiB; wgse-bwa --cuda peaked at 6.3 GiB at 8 threads), so it is taken only when its pipeline fits the RAM available; otherwise wgse-bwa (on its GPU when that fits) or bwa runs, and the preflight reports that aligner's estimate (hardware guide).

Eligible paired BWA and minimap2 sr realignment without --keep-fastq streams newly extracted reads (forced refresh of cached FASTQs at the exact output paths retains file handling): samtools view | collate | fastq writes interleaved pairs to the aligner's stdin through ordinary process pipes. There is no extracted_fastqs demand. For minimap2, streaming requires an explicit uncompressed FASTA small enough to fit in a single index part: minimap2 would otherwise need to reread the inputs for each part. GPU short-read realignment still uses FASTQ files.

Streaming uses file extraction's collate bucket count (20× BAM / 70× CRAM input size against sort-stage threads × per-thread memory, 64–200 buckets). Codec -@ workers are independent: using efficiency cores for compression does not enlarge collate's bucket budget or its concurrent-RAM estimate. Collate's output order depends on that count, so the aligner receives the same pairs in the same order either way and the realigned records are identical. A 30x genome streams whenever one bucket fits beside alignment in RAM.

Collate holds one bucket in memory while the aligner maps. Its estimate is the largest bucket's records (the indexed input count over the buckets, plus six standard deviations) times the power-of-two buffer of the largest BAM record in the read-length sample, plus 128 bytes of per-record bookkeeping and 64 MiB of headroom. Without an indexed count it falls back to 30× BAM / 100× CRAM of the input size per bucket. This amount is added to mapping's RAM preflight; if it does not fit, realignment extracts files without changing the selected aligner. It is an estimate, not an enforced RSS limit:

Streaming wrote 38% less (HG00096 113 → 75 MiB, HG002 316 → 196 MiB) at the same wall time and within 3% of the same peak RSS.

samtools sort buffers#

samtools sort -@ N -m M mallocs all N × M bytes when it starts, and the kernel refuses an allocation larger than RAM plus swap however few reads arrive: the sort fails with couldn't allocate memory for bam_mem and the aligner then dies of a broken pipe (#781). An explicit --memory can ask for more. Automatic memory budgets start at 25% of effective RAM (host RAM capped by the Linux cgroup v2 limit), divided across threads and rounded down. align, realign, pet, bam sort and bam to-ubam give each sort the smallest of:

  • --memory per thread;
  • what its read files can fill: 96 bytes of records per byte of input (the bound minimap2's estimate uses below), split across the threads, when every input is a local file;
  • half of effective RAM, split across the threads, leaving room for the rest of the pipeline.

The CLI logs when that lowers --memory. The input bound never goes below 16M per thread, but the RAM cap can lower that further. If the budget cannot provide samtools' minimum of 1 MiB per thread, lower --threads. Records and their order are unchanged: a sort that fits its input sorts in memory, and a sort that spills merges its spills stably. FASTQ collation uses the total budget to size its buckets and does not have samtools sort's per-thread minimum. Alignment memory checks count the sort's reservation (threads × -m) at least, as well as what its reads fill. realign's checks before extracting FASTQs use the requested --memory, so they never ask for less than its alignment uses.

minimap2 (long reads)#

minimap2 builds its index from the reference FASTA in memory on every run; WGSExtract keeps no .mmi file. Its preflight therefore counts the index for the selected preset, plus the larger of the build's scratch and mapping's batches and per-thread buffers, plus the sort and a fixed overhead (and samblaster for paired sr reads). Only samblaster depends on the read count. The batches, the threads' buffers and the sort's buffers fill only as reads arrive, so each is capped at 96 bytes per byte of read file (at least one thread's buffers stay): a read file smaller than about 30 MB fills one smaller batch, and a few-MB FASTQ at many threads is not budgeted gigabytes of sort memory.

Long-read presets (every preset but sr) are budgeted as the larger of two phases. While the index builds, no reads reach the sort and the decoder waits on its pipe, so that phase is the build's peak plus the fixed overhead. While mapping, the index, the batches, 0.85 GiB of buffers per thread at a 20 kb mean read length (scaled up for longer reads; the mean is sampled from the input), samtools sort's 1.75 × --memory per thread, the fixed overhead and 1 GiB for the CRAM/FASTQ decoder are summed, plus 10%: the whole-genome peaks below were measured in a full cgroup, so they are lower bounds. When the estimate exceeds the available memory (the cgroup limit included), align and realign log a structured alignment_memory warning before minimap2 starts. WGSExtract does not offer minimap2's -I (split index): a split index of hs38 needs --split-prefix and a merge pass, and maps more slowly.

The GPU accelerates gap fills, not chaining, decoding, sorting or CRAM encoding. For whole-genome runtime, use the Linux x86-64 RTX 3090 whole-genome ONT realign comparison rather than extrapolating the ONT/HiFi slice mapping speedups or using them to reduce host resource budgets.

NVIDIA GPUs (Parabricks)#

With --gpu, align, realign, vcf deepvariant and vcf gatk read each GPU's total and free memory from nvidia-smi before starting Parabricks, and report a gpu row beside the host memory row. pbrun uses every GPU, so each GPU is checked against its own memory: low-memory mode is chosen when any GPU is short of its default need, and a GPU that reports no memory doesn't hide another one's shortage.

  • A GPU with less than 16 GB (a T4 reports 15 GiB) is refused.
  • When less memory is free than a tool's default mode needs, the tool runs with its low-memory option, --low-memory for fq2bam and minimap2 and --htvc-low-memory for HaplotypeCaller. The run logs this and records a parabricks_low_memory warning. fq2bam sizes its work from the GPU's total memory, so it needs its low-memory mode whenever another program holds more than about 2 GiB of the GPU.
  • When even the low-memory mode won't fit, the command stops before running anything. DeepVariant has no low-memory mode.
  • Each tool also needs host RAM, whatever the GPU mode: at least 34 GiB for fq2bam, and 41 GiB for a whole 30x genome, whose sort holds more (minimap2 is assumed to match); 25 GiB for DeepVariant; 18 GiB for HaplotypeCaller. A computer with less RAM than the minimum is refused. When it has the minimum but less than the whole-genome need is available, because the computer is smaller or other programs hold it, the run continues with a parabricks_host_memory warning: available memory moves, and the kernel can often reclaim cache. The log also notes when the host has less RAM than NVIDIA recommends (100 GB for one or two GPUs, 49 GB a GPU beyond that).
  • --no-gpu-memory-check runs anyway, with a parabricks_memory warning. When nvidia-smi reports no memory ([N/A]), Parabricks runs with its defaults.

Preflight behaviour#

The estimate rows are advisory: preflight_resources() guards estimation and reporting against ValueError, OSError and subprocess failures, warns that the resource estimate is unavailable, and lets the command continue. The host requirement and existing dependency, memory and disk guards enforce their own policies.

These are conservative estimates, not reservations, memory limits or guarantees. When size or free-space measurement is unavailable the row says UNKNOWN, never a misleading OK. Regional disk estimates deliberately retain whole-input upper bounds rather than guessing coverage. CPU models do not describe pbmm2 pipelines; Parabricks has its own memory check (above), and hardware and acceleration covers GPU alignment.

GUI/API integration#

There is deliberately no second command-execution/dry-run path. A GUI can call the same read-only function used by the CLI:

import json
from wgsextract_cli.core.resource_estimates import estimate_resources

estimate = estimate_resources(
    "align",
    input_paths=["sample_R1.fq.gz", "sample_R2.fq.gz"],
    output_dir="results",
    reference="hs38DH.fa.gz",
    aligner="bwa",
    threads="6",
    memory="256M",
    reads=679_639_896,  # individual reads, not pairs
    output_format="CRAM",
)
print(json.dumps(estimate.to_dict()))

The function only inspects file metadata, reference index sizes/FAI, RAM and free disk. It neither creates output directories nor executes alignment/indexing tools. The caller supplies resolved reference/aligner choices; the CLI still validates dependencies normally. A GUI may supply temp_dir, and realign callers set extract_fastq=True only for newly extracted reads. Existing input files and reused FASTQs are not charged again.

to_dict() returns schema_version: 1, operation, notes, and resources. Each resource has resource (memory or disk), estimated_bytes, available_bytes, status, components (byte counts) and paths. Unavailable sizes are JSON null. report_resources(estimate) is the optional logging presentation layer.

The GUI/API estimator remains strict: invalid settings raise ValueError so clients can validate them. CLI callers use preflight_resources(lambda: estimate_resources(...)) instead.

For alignments, callers can obtain reads using the existing bounded core.alignment.read_counts.fastq_input_reads or indexed core.warnings.indexed_read_count. Omitting it leaves the D3 model's explicit 680-million-read RAM fallback; disk uses input bytes and format (12 bytes/read for compact CRAM, 80 for BAM, 70 for FASTQ). A missing reference uses the human reference RAM fallback, and adds a structured UNKNOWN disk row with no guessed filesystem for reference-index storage.

Calibration and limitations#

Native short-read preflight checks available, not installed, RAM on Linux, macOS and Windows. It includes resident indexes, working buffers, samblaster, per-thread sort plus overhead and pipeline bookkeeping. Read-dependent headroom scales with input count, not reference length. FASTQ counts use size and a bounded prefix (up to 4 MiB compressed/16 MiB decoded per mate, plain/gzip/BGZF); realign uses indexed idxstats before extraction. Unreadable/unsupported samples or missing indexes use the explicit 680-million-read fallback, not a guarantee for larger inputs. Changing length/compressibility later in a FASTQ can affect extrapolation. Swap/pagefile does not count as available RAM.

Component and per-read spill estimates are logged. Low spill space warns for align; realign retains its refusal. Auto falls back to BWA if MEM2 cannot fit; explicit MEM2 fails before alignment/extraction, including when its proposed native MEM3 stand-in does not fit. BWA warns and continues. Free RAM, lower --memory/--threads, or choose --aligner bwa. In a 339.8-million-pair genome, BWA's working set was 17–17.5 GiB including paged-out memory: the resident peak alone is not the requirement. At six threads/256M, the historical conservative budgets were ~18 GiB BWA and ~29 GiB MEM2 including transient headroom; smaller inputs scale down, deeper/shorter-read inputs up. Newer platform/read-length calibration below also applies.

  • Ordinary 150-bp, up-to-six-thread alignment RAM retains the #179/#194 model: resident reference indexes, aligner working set, read-scaled samblaster and transient overhead, and threads × sort memory plus 25%.
  • BWA-MEM working memory also accounts for platform, sampled mean read length and threads. FASTQ count and mean length come from the same bounded prefix; BAM/CRAM preflight does not decode the input to measure read length. Unknown lengths use 150 bp for ordinary short reads and 300 bp for Ultima. GUI/API callers can supply platform="ultima", read_length=300 and samblaster=False for single-end Ultima inputs.
  • At fixed -K 100000000, Ultima allows 4.5 GiB of working memory at two threads and 10 GiB at four threads (300 bp), in addition to the index, sort and pipeline overhead. It scales with read length and populated batch, with a 2 GiB floor. This conservatively covers HG008/hs38DH: BWA peaked at 9.18 GiB at two threads; four-thread anonymous memory reached 14.70 GiB before the 16 GiB unit OOM. The two-thread diagnostic timed out: this is a memory observation, not completed full-genome correctness. For 313,736,048 reads and 256M sort memory, estimates are approximately 12.0 GiB at two threads and 18.1 GiB at four. Longer ordinary reads and more than six BWA threads also increase the allowance. BWA-MEM2 calibration is unchanged.
  • Available RAM honors Linux cgroup-v2 ancestor caps, including reclaimable inactive file cache; Windows/macOS retain native available-RAM reporting. Namespace/subtree mounts retain their visible descendant limits. LOW-memory BWA warnings recommend a lower thread count plus the resolved --memory value, keeping the modeled per-sort-thread allowance fixed. No automatic thread cap is applied: requested threads and BWA arguments remain unchanged. Existing BWA advisory and explicit BWA-MEM2 refusal policies remain. Read complexity, flow-tag volume and tool versions can change peaks; estimates are not allocation guarantees.
  • Phase-2 H2 processed 679,639,896 reads (339,819,948 pairs). Its compressed FASTQ inputs totalled 47.84 GB, and its binned-quality output was only 8.63 GB CRAM, plus a 1.14 MB CRAI. Do not extrapolate that unusually good compression to full-quality inputs.
  • The conservative disk envelope uses 120 bytes/read sort spill, 28 bytes/read CRAM, 100 bytes/read BAM, and 100 bytes/read extracted FASTQ. At H2 depth this is 81.56 GB temporary sort space and 19.03 GB CRAM (75.96 and 17.72 GiB), within the phase-2 planning ranges of 70–90 GB sort space and about 16–20 GB CRAM. Output indexes add 1% (at least 64 KiB). Existing reference indexes cost no new disk; missing ones receive an additional two-resident-index-size build allowance on the reference volume. The FASTQ allowance was raised from 75 after #722's full-quality HG002 slice wrote 937.4 MB for 10,971,483 indexed records (85.4 bytes/record): the files were 14% larger than the old budget. Known indexed counts avoid additional uncertainty from BAM/CRAM compression-based count inference.
  • The full-quality HG002 35x run on a 16 GiB M1 (#722, wgse-bwa 0.12.1/Metal, four threads, automatically selected 512M sort memory) adds whole-genome evidence to that slice calibration. Its 835,260,805 indexed input records produced 71.11 GB extracted FASTQs (85.1 bytes/record) and a 46.38 GB BAM (55.5 bytes/record). Sampled scratch including the FASTQs peaked at 134.86 GiB, and scratch plus results at 166.15 GiB. With the existing input and reference already on disk, 210.36 GiB free was enough, but only 37.42 GiB remained at the observed minimum. These different envelopes are not allocation guarantees or equivalent measures. Retain the conservative disk coefficients and additional free-space margin. The historical measured stage table records the exact run and resume conditions.
  • macOS RSS is not the uncompressed working set. That run's startup RAM estimate was 22.02 GiB against 10.80 GiB available. The largest process peaked at 8.30 GiB RSS and the sampled concurrent pipeline at 10.11 GiB, but 1,113.72/1,116.92 GiB of system-wide swap-in/out traffic coincided with resumed alignment (vm_stat can't attribute it to a process; other desktop apps were open), with sampled occupied swap up to 3.70 GiB and warning memory pressure. Completion under compression/swap does not validate an 8–10 GiB working-set budget. This heavy swapping is tracked as product bug #747: LOW memory predicts the problem, but defaults do not yet adapt to avoid it. The conservative RAM model is unchanged.
  • Ultima pipelines using GATK flow duplicate marking pass duplicate_marking="gatk-flow". Their temporary budget includes retained sorted/marked BAMs: up to two BAMs (200 bytes/read) for CRAM output, rather than assuming only sort spill and final CRAM coexist.
  • bcftools compressed VCF output allows 1.6 bytes per inferred read for SNPs and 0.4 for indels, at least 64 KiB. Without a supplied read count, BAM and CRAM bytes are normalized using the existing 80/12 bytes-per-read fallback, so input compression does not directly set the VCF budget. The CLI supplies the cheap indexed BAM count; CRAM keeps the fallback rather than decoding the file for preflight. Serial calling (--no-parallel, one thread, an explicit region, or a caller-resolved serial fallback) writes directly to the staged output and reserves no part/concatenation temporary space. Parallel calling uses the runtime's shared batching plan, not one part per reference contig. Compressed batch headers are estimated from the complete reference dictionary and supplied alignment header, with compression and metadata headroom. Non-replaying indels reserve two output-sized data sets. Parallel SNPs also reserve possible deep-site split/replay files: a full uncompressed header for each split contig, both window and whole-contig fallback splices, and reheadering, plus an eight-output-sized record-data envelope. These files can coexist until publication, even though a shallow run may not need replay. All of these files are charged to the output volume, where the caller actually creates them. The CLI supplies the resolved bcftools_contigs and alignment_header; read-only API clients without that metadata conservatively use the reference dictionary. If neither a reference index nor resolved contigs are available, parallel temporary disk is reported unknown rather than assuming a serial run. On #722's nominal-30x HG002 slice, the 670.5 MB BAM produced 2.95 MB SNP and 0.80 MB indel VCF.gz files; the old tenth-of-input output estimate was 23×/84× high. The new budgets retain several-fold headroom; depth, variant burden and compression vary. The subsequent whole 35x run produced 180.70 MB SNP and 47.75 MB indel VCF.gz files from 835,260,415 realigned records. With the existing result directories subtracted, the sampled incremental temporary plus new output peaks were 0.497/0.056 GiB on the output volume, respectively. These are combined peaks, not separate measurements of temporary files. They support keeping the compressed-output budgets conservative rather than replacing replay/header worst-case allowances with one run's peak. GATK retains 10% of input bytes for output and twice that for temporary storage. Regional GATK CRAM conversion also budgets a whole-input BAM upper bound on the output volume. GATK 4.6.2.0 can read indexed CRAM 3.0 directly when --region selects whole contigs and the CRAI is compatible. Partial intervals, other CRAM versions, and unqualified GATK builds retain regional BAM staging. GATK scattering additionally charges retained shard VCFs and their indexes to caller staging (--tmp-dir when configured, otherwise the output volume). JVM temporary storage has its own demand (--tmp-dir, otherwise system temp). With --reference-evidence gvcf the gVCF (GQ bands 10,20,30,60) is budgeted at 3% of the input's BAM-equivalent bytes (its read count, so a CRAM of the same reads gets the same budget), three times over for its partition parts, gathered copy and published file (2.6% of the BAM measured on HG002 chr20, #863). One copy is charged to the output volume and the other two to caller staging, combined when they share a filesystem. GenotypeGVCFs runs after HaplotypeCaller, within its memory.
  • Sort RAM is threads × --memory plus 25% and 256 MiB overhead; conversion allows 64 MiB per codec thread plus 256 MiB overhead. bcftools allows 1 GiB per active contig worker plus 256 MiB. With more than one thread, contigs are called in parallel workers by default (--no-parallel, parallel=False in the API, calls them in one stream), capped by reference contig count and one worker for an explicit region. GATK uses a 6 GiB heuristic per worker, not a claim about its Java heap limit. The opt-in vcf gatk --scatter flow-mode path selects at most --threads workers and one worker per 6 GiB of currently available physical RAM, then supplies that count as gatk_workers to the reusable estimator. Each parallel JVM has an explicit 4 GiB heap and one native PairHMM/GC worker; the remaining allowance covers non-heap memory. Unknown RAM or room for only one worker retains the original unscattered command. This is a conservative concurrency policy, not a reservation or hard RSS cap. These non-alignment models are conservative heuristics, not measured guarantees for every caller, read length or depth.

The Linux allocator comparison (#966, bcftools allocator measurements) does not change these budgets. On a 1.560% HG002 30× coordinate slice with two workers, largest-child peak RSS was 284/286 MiB for SNP/indel calling with glibc, versus 318/340 MiB with mimalloc. Across the slice and whole fake-genome runs, sampled concurrent pipeline RSS stayed below 0.91 GiB and sampled temporary-plus-output disk below 8.6 MiB. These are small-input observations, not whole-genome bounds or grounds for reducing the conservative 1-GiB-per-worker allowance. Neither caller reached the 5% median speedup gate; Linux retains the system allocator.

The native CUDA PairHMM measurement does not change GATK's budgets. On public HG00096 across all mapped reference intervals, the one-thread CUDA caller with a 4 GiB heap sampled about 2.01 GiB peak RSS and 338 MiB peak GPU process memory. An 8 GiB RAM lease and 64 GiB disk reservation covered the run, with about 1.55 GiB of compressed calls and indexes. These are observations for one sample and host, not minimum requirements, hard limits, or a reason to reduce the estimator's allowance.

Native DeepVariant#

wgse-deepvariant on Apple Silicon and Linux x86-64 has a separate sequential-stage model, not the TensorFlow partition model below. It allows a fixed base plus per-thread make_examples memory, batch-scaled GPU inference, and serialized whole-run records plus one parsed contig for postprocessing. RSS alone does not capture Metal's unified-memory footprint.

Calibration in #721: 0.1.1, six threads, batch 512, HG002 35x chr20 on a 16 GiB M1 peaked at 6.56 GB inference footprint, with 0.843 GB workspace from a 1.09 GB BAM. The temporary-disk allowance is shared by regional and whole-genome runs: 0.8 temporary bytes per input byte. An earlier 0.1.0 whole-genome run used only 17.3 GB of workspace from a 46.0 GB BAM, but lowering the shared allowance to that ratio would underbudget chr20. Its largest stage RSS was 3.70 GB, while Metal inference's measured peak footprint was 5.26 GB. At batch 512, the inference-stage RAM envelope is 7 GiB (1 GiB base plus 512 × 12 MiB), plus 1 GiB driver headroom: 8 GiB total preflight RAM, covering the footprint rather than RSS alone. The existing envelopes remain conservative.

On Linux x86-64 (#719), call_variants peaked at 1.5 GiB host RAM at batch 256 on either CUDA or the CPU, also within the shared native RAM envelope. See the Linux/CUDA measurements for inference backend, GPU memory and qualification details.

DeepVariant postprocess_variants#

DeepVariant's stages run one after another, so its RAM estimate is the largest of TensorFlow inference (2 + 14 × batch_size/1024 GiB on x64, 30 on ARM), make_examples shards (1 GiB each on x64, 2 on ARM) and postprocess_variants, plus 1 GiB of driver headroom.

postprocess_variants splits the calling regions into partitions (DeepVariant 1.9+ --num_partitions, at least --cpus) and sorts each partition's call_variants records in memory, one partition per worker process. The estimator replays DeepVariant's own partition_calling_regions on the reference .fai and the --region selection, then charges each worker for its partition's bases:

  • 768 MiB per worker, plus
  • 4.75 records per kilobase × 2 KiB per record.

Calibration (#173, HG008 Ultima ~30x on hs38DH, --threads 5): DeepVariant's five partitions held 2.93, 3.01, 3.10, 3.30 and 1.06 million call_variants records (13.4 million in total; 4.70 per kb at most, in chr13–chr20). Three workers were OOM-killed mid-sort under a 12 GB cap at 3.39, 4.49 and 6.14 GB anonymous RSS, which are lower bounds on their peaks. The model gives 7.1 GiB per worker, about 36 GiB for the five, so the whole genome at --threads 5 needs 37 GiB rather than the 17 GiB that inference alone suggests. Density was measured on one 30x Ultima genome; deeper or noisier inputs and other models can produce more candidates. A chr20 replay with 16 shards peaked at 0.6 GiB per worker, consistent with the base allowance.

Before running, vcf deepvariant (CPU, not WES, which DeepVariant postprocesses in one sequential pass) bounds this step by the RAM available now, capped by docker info's engine memory, such as Docker Desktop's VM:

  1. If --threads workers fit, the command is unchanged.
  2. Otherwise it keeps every worker and passes --postprocess_variants_extra_args num_partitions=N with the fewest partitions that make the largest one fit, logged at INFO. More partitions cost runtime: each worker rereads all call_variants outputs.
  3. If no partition count up to 128 fits, it also lowers --postprocess_cpus, with a warning.

num_partitions needs DeepVariant 1.9 or later. It is used with the pinned default images, image tags of version 1.9 or later, and other images or a local run_deepvariant whose postprocess_variants --helpfull lists it (asked only when more partitions are wanted). Otherwise step 2 is skipped: only --postprocess_cpus is lowered, with a warning. That saves little: fewer workers sort bigger partitions, so a whole genome still needs about 30 GiB.

With --reference-evidence gvcf each worker also writes its partition's part of the gVCF, streaming make_examples' reference records: HG002 35x chr20 as one partition peaked at 1.14 GiB with the gVCF and 1.14 without (#863), so the plan is the same. wgse-deepvariant's postprocess_variants differs: it keeps every contig's calls until it writes the gVCF. HG002 35x chr20 and chr22 together peaked at 0.94 GiB with the gVCF and 0.81 without, chr22 adding 3.5 bytes per base beyond its serialized records; the estimate charges 5 more bytes to every called base (about 20 GiB for hs38DH, against 5 GiB without the gVCF), 0.4 more temporary bytes per input byte for the gVCF records make_examples writes (0.26 measured), and a gVCF of 5% of the input (1.9% measured). When even that cannot fit, the refusal suggests DeepVariant 1.9+.

  1. If one worker cannot fit, it refuses before make_examples starts and gives the memory needed and available.

The plan uses memory available at the start; other jobs that start later can still take it. In a container, an OOM kill of any process (from a Docker memory cap or a host out of memory) is reported by docker events. The command then kills the container and fails with an actionable error instead of letting DeepVariant's worker pool wait forever on its lost worker. A local run_deepvariant on PATH has no such watcher. On any failure, the stages' work stays in .deepvariant.work in the output directory. A rerun with the same settings skips the completed stages and finished make_examples shards, so after freeing memory it restarts at postprocessing (see resuming long workflows).

Compression, read lengths, depth, extra flow-specific stages and tool versions can change these costs. Missing reference-index construction has its own existing tool-specific guards; the alignment RAM row describes mapping, not index construction. No swap/pagefile is counted as available RAM.
