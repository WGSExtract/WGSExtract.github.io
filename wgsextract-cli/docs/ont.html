WGS Extract CLI / CLI Docs / Oxford Nanopore

Oxford Nanopore

align and realign detect ONT from @RG PL:ONT or UUID read names in BAM/CRAM/FASTQ (including gzipped FASTQ). Read groups take precedence; mixed platforms are not assigned one platform. An explicit --platform overrides detection.

For FASTQs with inconclusive names (including SRA-renamed reads), detection samples at most 4096 reads, 4 MiB compressed and 16 MiB decoded, including gzip/BGZF files. A median length below 1 kb keeps the previous short-read defaults, including renamed 301 bp Illumina and 400/600 bp Ion Torrent reads. FASTQ and compression are recognized by content, not filename; wrapped sequence and quality lines are supported. Named pipes are left untouched until alignment stages them. Longer reads use ONT header tags (runid=, ch=, start_time=, basecall_model_version_id=), or PacBio consensus tags (rq= of at least 0.99; otherwise np= of at least 2). Conflicting tags are not resolved by guessing. Without tags, a HiFi-like quality profile (mean Q30 or higher, at least 90% of bases Q30+, some qualities above ONT's Q50 cap) selects PacBio HiFi. A short-read tail does not disqualify an otherwise high-quality HiFi sample. These are conservative heuristics, not instrument identification: low-quality ONT and PacBio CLR can overlap. Ambiguous long reads are refused: pass --platform ont, --platform hifi or --platform clr. Both paired FASTQs are checked; conflicting evidence is refused. Explicit --platform still wins. For known short-read data above the conservative 1 kb cutoff, choose --platform illumina explicitly.

The sample workspace's platform fact records the method, confidence and sampled statistics (median and N50 length, mean/max Q, p90/p10 length spread and sample size). The result manifest includes the same evidence under provenance.params.platform_detection. Samples are cached per file revision; replacing a FASTQ invalidates its evidence. BAM/CRAM detection is unchanged. FASTQ facts also hash the entire bounded input prefix used for detection, so same-size edits outside the usual first/middle/last-MiB fingerprint windows invalidate the cached evidence. An override is recorded separately as effective_platform; it never erases the detected method or statistics, including inconclusive (Unknown) samples. Native read-name evidence is independent of parsing the sequence/quality sample, so empty or malformed sample records cannot erase a recognized ONT UUID. Conclusive names do not require a length/quality sample. Zero-length records are excluded from sampled statistics; full FASTQ validation still reports invalid input before mapping.

A BAM/CRAM whose read groups name several platforms (ONT and Illumina reads merged, say) is reported by info (the Platforms line, platforms in the manifest's metrics and details, warning mixed_platforms). Commands whose defaults depend on the platform refuse it unless an option chooses: align/realign (--platform), vcf deepvariant (--model-type, --ont or --pacbio), vcf sv (--caller, --ont or --pacbio) and typing str (--caller); vcf clair3 calls PL:ONT read groups only. Other callers (vcf snp, vcf indel, vcf phase and the like) and methylation pileup warn mixed_platforms and carry on. Or split the reads by read group with samtools split and process each platform separately.

ONT and PacBio FASTQs gain automatic long-read alignment defaults, as does realign of single-end PacBio BAM/CRAM. Native PacBio m84…/…/ccs names select HiFi/CCS (map-hifi with minimap2), not CLR; align may use pbmm2 when installed, just as for PacBio BAM input. Ultima- and MGI-named FASTQs, paired PL:PACBIO and PL:DNBSEQ BAMs retain the previous Illumina alignment defaults unless --platform is explicit. The pre-existing BAM/CRAM PL:ULTIMA automatic path is unchanged. Other detected platforms may be reported, but reporting does not select their alignment workflows.

CPU ONT alignment uses minimap2 map-ont, carries MM, ML and MN through samtools fastq -T MM,ML,MN,pi and minimap2 -y, and soft-clips supplementary alignments (-Y) so the modification coordinates still describe the full read. Sorting retains these tags. Long reads from a BAM/CRAM keep its read groups' descriptions (DS, where Dorado names its basecall_model and modbase_models, and PacBio its READTYPE) in the new read group, so vcf clair3 can still choose its model from them. FASTQ input first passes through samtools import -T MM,ML,MN,pi, so ordinary ONT runid/channel comments do not become invalid SAM fields with -y. Realignment streams single-end tagged FASTQ instead of reusing potentially untagged paired FASTQs. With --keep-fastq it first writes them, tags included, to <input stem>.fastq.gz and aligns from that. GPU ONT alignment is refused rather than silently losing modification data. Single-end PacBio input takes the same path (see the README's alignment notes).

For CRAM realignment, --input-ref supplies the original decoding FASTA for both platform detection and extraction; --ref selects the alignment target. Without --input-ref, a CRAM lacking platform read groups is decoded with --ref when its sequence names, lengths and MD5 checksums match the CRAM's (realigning to the build it was encoded with), and otherwise with the reference-library FASTA whose signature matches, before its read names are probed. A failed CRAM read-name probe is an error, never a silent fallback to paired short-read extraction. The usual realignment disk-space preflight also applies to streamed ONT reads.

Experimental CPU backend: bonefish#

Pass --aligner bonefish to align or realign for ONT DNA or PacBio HiFi. The default aligner selection is unchanged. For example:

wgsextract align --r1 reads.fastq.gz --platform ont --aligner bonefish --ref hs38.fa
wgsextract realign --input reads.cram --platform hifi --aligner bonefish \
  --input-ref original.fa --ref hs38.fa --format CRAM

Install bonefish 0.5.2 or later and put bonefish on PATH with samtools 1.13 or later. WGSE checks the versions and does not download them. The upstream release has Linux x86-64/arm64 (glibc 2.28+) and Apple Silicon binaries. On Windows use the Linux CLI inside WSL, or use minimap2 natively. The Bioconda 0.5.0 build predates the modification-tag fix and is not supported.

WGSE selects bonefish's dna for ONT (--preset map-ont) and hifi for HiFi (--preset map-hifi or ccs). The DNA scoring is closer to minimap2's lr:hq than to map-ont, so mapped locations and MAPQ can differ. CLR, RNA, short reads and --gpu are not supported with this backend. WGSE streams the same tagged, primary reads as its minimap2 path and uses samtools to produce a sorted and indexed BAM or CRAM, including the lossless CRAM profiles. Bonefish runs in one pass (--chunk-size does not apply); a failed mapping step restarts from the beginning. See hardware before using it on a whole genome.

Lossless output profiles#

align and realign accept --output-profile default|archive|calling. The default leaves --format and the installed encoder's defaults unchanged. The other profiles select CRAM when --format is omitted. An explicit profile conflicts with --format BAM and is refused; use --output-profile default for BAM. When the profile comes from config.toml instead, explicit --format BAM wins and the effective profile is default (logged at info level), including in the desktop app and Python API:

ProfileEncodingReaders
archiveCRAM 3.1, samtools' archive compressionModern htslib and GATK 4.7+
callingCRAM 3.0, normal compressionGATK and older htslib-based callers, including DeepVariant

Both are lossless: full supplementary SEQ/QUAL, soft clipping and MM/ML/MN tags are retained. Archive trades encoding time for smaller files; savings depend on the reads. Calling avoids DeepVariant's CRAM 3.1 compatibility copy, not every caller's other staging requirements. Native pbmm2 only writes BAM: auto selects minimap2 for PacBio CRAM profiles, while explicit --aligner pbmm2 is refused with a profile-specific message. GPU alignment writes BAM first and converts it with samtools for these profiles, so it needs temporary space for that BAM too.

On one 5M-pair HG002 short-read observation, archive reduced size by 9.4%, but writing was 1.9× slower, SNP calling took 12% longer, and peak RSS during writing/calling was 2.71 vs 1.53 GB (about 1.8×) compared with default CRAM 3.1. These are single warm-cache observations on a shared M1 Pro, not established performance guarantees; the trade-off depends on the reads and reader.

The follow-up public 30× full HG002 genome observation on Linux saved 9.37% with archive, but encoding/indexing took 3.10× as long, used 5.19 vs 1.38 GB encoder RSS, and SNP calling took 1.63× as long. Calling output was 11.99% larger than default. Retained ONT slices from the realignment disk-growth investigation saved 3.56–6.53% with archive; the realigned slice's sequences, qualities and MM/ML/MN tags were unchanged. Every profile gave identical SNP records within each dataset, including 4,504,821 full-genome records, read directly without conversion. These are single shared-host measurements, not ONT caller-accuracy validation or a full ONT-genome benchmark. See the size/time tables and methodology.

wgsextract realign --input ont.cram --ref hs38.fa --output-profile archive
wgsextract align --r1 reads_R1.fastq.gz --r2 reads_R2.fastq.gz \
  --ref hs38.fa --output-profile calling

Set output_profile = "calling" (or "archive") in config.toml for a persistent default; --output-profile default overrides it. The typed API and server expose the same output_profile option. The result manifest records the effective profile in metrics.output_profile. Changing the profile invalidates realign's completed alignment and chunk resume state. Installed samtools is checked for the requested options and version before mapping; WGS Extract does not install it.

info, extraction and bcftools calling read both profiles. Older DeepVariant/Clair3 builds use the existing temporary compatible copy for archive output. GATK 4.7 and newer read CRAM 3.1 directly; whole-file calling with an identified older GATK is refused before making a .dict. Use calling output, convert to BAM (bam to-bam), or specify vcf gatk --region for the existing regional BAM conversion.

Chunked realignment#

A whole-genome ONT realignment runs for days. In one pass, its sort spills grow to more than the output (about 260 GB of temporary files for a 104 GB 51x CRAM, beside a 170 GB output), and a run killed near the end starts over. So realign aligns long reads (ONT and PacBio, with minimap2) from a coordinate-sorted, indexed BAM or CRAM in chunks of about --chunk-size of the input (default 4G; 0 aligns in one pass):

  • Each chunk's primary reads (those starting in its regions, planned from the .crai or the BAM's .bai) are aligned and sorted on their own, then split into about 24 groups of the output's contigs. Unplaced unmapped reads form a chunk and a group of their own. The minimap2 index is built once, beside the output.
  • When every chunk is done, each group is sorted across the chunks and appended to the output, and its pieces are deleted.
  • Work lives in <output>.chunks/, and state.json there records each finished chunk and appended group. An interrupted or cancelled run resumes at its first unfinished chunk or group. Changing the input, reference, format, --chunk-size, minimap2 build, CRAM decoding settings, or read extraction settings starts the chunks over. --no-resume and --force also start over. A rerun that aligns in one pass removes the directory.
  • The records are the same as a single pass's, in the same order. Only the header differs: minimap2's @PG names the index, and there is no samtools sort @PG.

Temporary space is then about the largest chunk's sort spills, or the largest group's. The output directory needs the output, plus the index (about 7.5 GB for hs38) while aligning, plus the largest group while assembling. The preflight checks this, sized from the index, and counts what an interrupted run already wrote as done. These still align in one pass:

  • input smaller than one chunk;
  • unsorted or unindexed input (such as basecaller uBAMs), or a CRAM whose .crai lists slices out of order;
  • --keep-fastq;
  • the sr preset, whose duplicates are marked across the whole alignment.

Realigning from a URL#

--input may be an http:// or https:// URL of an ONT or PacBio BAM or CRAM, such as GIAB's HG002 CRAM:

wgsextract realign \
  --input https://ont-open-data.s3.amazonaws.com/giab_2023.05/analysis/hg002/sup/PAO83395.pass.cram \
  --ref hs38.fa.gz --outdir hg002
  • htslib reads the input by byte range: no local copy is made, so the disk needs room for the output only.
  • Its index (URL.crai, .bai or .csi) is downloaded beside the output and deleted once the alignment is done. Nothing is written to the current folder.
  • The output goes to the current folder unless --outdir says otherwise.
  • Chunks and resuming work as for a local file. The step journal recognises the input by the server's ETag or Last-Modified, so a rerun skips an unchanged input and redoes a changed one. A server sending neither gets no reuse: a rerun starts over.
  • A dropped connection fails the chunk it was in; rerun to resume there. Failing to download the index stops the run too. Only a missing index (404, or S3's 403) makes the run align in one pass.
  • The URL must be public: one with a query string or credentials (a signed URL) is refused, so no token reaches the manifest, the journal or a log.
  • samtools must read http(s): its htslib needs libcurl, which the Windows build lacks.
  • Short reads are refused: their realignment collates the input, which needs a local file. The local server (wgsextract serve) refuses URLs, which it would otherwise fetch on any caller's behalf.

Combining flow-cell runs#

A sample sequenced on several flow cells, each aligned to the same reference, becomes one BAM or CRAM with bam merge:

wgsextract bam merge run1.bam run2.bam --sample HG002 --output HG002.bam
  • Read groups. Each run keeps its own read group, so callers can tell the runs apart. If an input has no @RG lines or reads without an RG tag, or with --attach-rg, each input's read group is named after its file (run1, run2); each input must then hold at most one. Otherwise the inputs' read groups are kept, and IDs that clash get a suffix (warning read_group_conflict). Identical @RG lines in several inputs (minimap2 -R '@RG\tID:HG002' for every flow cell) are one read group only if they name the run (PU, or an ONT DS runid=) or templates span the files (one run split by region); otherwise each run keeps its own, suffixed ID (warning read_group_renamed).
  • Sample. Every read group gets the same SM: --sample, else the inputs' own. Inputs naming different samples are refused unless --sample is given; inputs naming none take the output's name (sample_name_assumed).
  • Platform. Missing PL fields are filled from the detected platform. Reads from different platforms (ONT and Illumina, say), in one input or across them, are refused.
  • Reference. Inputs must share contig names and lengths, and MD5s where both headers list them.
  • Duplicates. The first 5,000 reads of each input are compared. A run included twice (the same reads, as sequenced, in two inputs, even if realigned) is refused, as are ONT runs sharing read IDs, which name molecules: a run basecalled twice. Other different reads that share names warn read_name_collision.
  • Modifications. MM/ML tags pass through unchanged. If only some runs carry them, or their read groups name different modified-base models, the merge warns (mod_tags_partial, mod_models_differ).
  • Coverage. For indexed inputs, each run's and the combined autosomal depth are printed and recorded in the result.

Basecalling#

basecall turns POD5 signal (a file, or a folder searched recursively) into an unaligned BAM with ONT's Dorado, 1.0 or newer. Dorado is optional and isn't installed with WGS Extract: download the release for your system, then put its bin folder on PATH, set dorado_executable in config.toml, or pass --dorado-path. A missing or older Dorado stops the command with that hint before anything runs. FAST5 input is refused with the pod5 convert fast5 command that converts it.

wgsextract basecall --input pod5/ --modified-bases 5mCG_5hmCG
wgsextract align --r1 pod5.hac.5mCG_5hmCG.bam --ref hs38.fa.gz
wgsextract methylation pileup --input pod5.hac.5mCG_5hmCG_aligned.bam --ref hs38.fa.gz
  • Models. --model is fast, hac (the default) or sup, optionally pinned (sup@v5.2.0), or a downloaded model folder. Dorado picks the model for the run's chemistry from the POD5 and downloads it, and the modification models --modified-bases names (5mCG_5hmCG, 5mC_5hmC, 6mA, ...), into the models folder: --models-dir, else dorado_models_directory in config.toml, else dorado-models in the WGS Extract cache. Later runs reuse them.
  • Device. --device auto (the default) uses the GPU of a Mac with Apple silicon (metal), else an NVIDIA GPU that nvidia-smi -L lists (cuda:all), else the CPU, which the run warns about (basecall_on_cpu). --device cpu, metal, cuda:all or cuda:0,1 choose one.
  • Output. <POD5 file or folder stem>.<model>[.<modifications>].bam beside the POD5 input, or in --outdir, so a sup re-basecall doesn't replace the hac BAM. It keeps Dorado's read group (PL:ONT, the models in DS) and read tags, MM/ML included, so align --r1 detects ONT and carries the modifications into the aligned BAM. The manifest records the reads, device, Dorado version and models, and with --modified-bases how many reads got MM/ML tags; it warns (no_modification_tags) when none did, and (no_reads) when Dorado wrote no reads.
  • Subsets. --read-ids FILE basecalls only the listed reads. --regions-bed panel.bed --alignment sample_aligned.bam re-basecalls the reads the alignment maps in those regions, for example with --model sup for a gene panel after a hac run. A read Dorado split is named by its parent (pi tag), the ID its signal has in the POD5; unmapped reads are left out. Both write <stem>.<model>[.<modifications>].subset.bam.

Small variants#

vcf deepvariant automatically selects ONT_R104 for detected ONT input. --ont is an alias for --model-type ONT_R104; explicit model selectors override detection. Contradictory ONT selectors are rejected.

wgsextract vcf deepvariant -i hg002-ont.bam --ref chr20.fa \
  --region chr20:10000000-10010000 --threads 1 --outdir ont-variants

This model supports R10.4.1 only. R9.4.1/R9.4 data is unsupported; the CLI warns when @PG or @RG DS basecaller metadata identifies it. UUID names cannot identify chemistry, so absence of a warning does not establish support. Use Google's installed google/deepvariant:1.10.0 image (the default), or an installed run_deepvariant that provides this model. Dependencies are checked, never installed automatically.

ONT_R104 requires x86-64. Linux ARM64 remains WGS-only, and ONT calling is also refused on Apple Silicon rather than assuming emulation is qualified. Other models retain their existing platform policy. The pinned Parabricks 4.8.0-1 supports deepvariant --mode ont, selected by --gpu; this command mapping is tested, but GPU ONT accuracy has not been hardware-qualified here. CPU container temporary files and HOME stay inside the owned output work directory and are removed after the run.

Clair3 (optional)#

vcf clair3 runs Clair3 2.x, an ONT-trained small-variant caller. It is optional, and DeepVariant remains the default ONT caller. The Pixi environment pins Clair3 2.0.5 or newer, which Bioconda builds for Linux x86-64, Linux ARM64 and Apple Silicon macOS. It is not available on Windows (use WSL2) or Intel Macs. Install it into its own Pixi environment with pixi install -e clair3. The CLI checks for it but never installs it.

Clair3 2.0.5 bundles htslib 1.24 and reads CRAM 3.1 itself. Older Clair3 builds on PATH can't decode some CRAM 3.1 blocks (#604), so for them the command calls from a temporary CRAM 3.0 copy.

Clair3 runs on the CPU by default. On Apple Silicon, vcf clair3 --gpu selects MPS inference in the WGSE-built code-only wgse-clair3 package. It preserves the CPU streaming pipeline and high-depth scaling, including gVCF; it does not select upstream's CUDA disk-tensor pipeline. Preflight refuses missing/unpatched packages or unavailable PyTorch MPS, even with --no-preflight, rather than falling back or installing anything. On Apple Silicon, pixi install -e clair3 installs the pinned package (release and pin). Models are resolved and checked exactly as on the CPU; the new package redistributes no weights (ONT Rerio's licence is research-only). Whole-genome MPS qualification is still pending.

On an M1 Pro (10 cores, 32 GiB; four calling threads), the original-alignment public HG002 chr20:10-11 Mb slice produced identical 1,830 sites, alleles, GT and FILTER on CPU/MPS, including gVCF calling. QUAL differed by at most 0.01; sample fields matched exactly. All 32,362 gVCF reference records matched in every column. Through the real CLI, CPU/MPS took 27.43/22.26 s without gVCF and 37.01/32.63 s with it (2026-11-18). These shared-host, startup-heavy slice timings are not whole-genome speed claims. This is not the realigned slice behind the older Linux/M1 figures below.

On whole chr20 (64.44 Mb), paired four-thread gVCF calls also matched: 142,070 sites/alleles/GT/FILTER in both VCF and gVCF, and 3,084,277 reference records identical in every column. QUAL differed by at most 0.03; six PL fields and two GQ fields differed by one, without changing GT or FILTER. In an awake paired repeat (2026-11-19, caffeinate, shared bench lock), CPU took 20.36 min and MPS 15.19 min: about 1.34x end to end, with the same results. Whole-genome qualification remains pending. See the sizing table and caveats.

On x86-64 Linux, vcf clair3 --gpu runs its neural networks on an NVIDIA GPU from HKU's CUDA image of the same Clair3 2.0.5, pinned by digest (docker pull hkubal/clair3:v2.0.5_gpu@sha256:3f660a693142db0aa8361a58fb6379fc6e3eeead20916eaae5614bd00d21cbeb, about 4.5 GB; clair3_gpu_image in config.toml for another build). It needs x86-64 Linux (or WSL2), the NVIDIA driver, Docker and the NVIDIA Container Toolkit; the CLI checks for them and the image but installs nothing. Clair3 starts a GPU worker only on a GPU with 7.8 GiB free, so the command gives it only such GPUs and refuses to start when none has; each worker used 1.0-1.3 GB of GPU memory here. It also refuses an image whose PyTorch can't use the GPU, where Clair3 would quietly call on the CPU, and holds the container to --threads CPUs. A custom image's Clair3 version is read from the image, not its tag, to decide whether CRAM 3.1 reads need a CRAM 3.0 copy. The model still comes from --model, clair3_model or the reads' metadata, as on the CPU, and is checked the same way; a bundled model name needs the clair3 Pixi environment, otherwise pass the model's directory.

The CUDA GPU mode needs far more disk than CPU or MPS: Clair3 2.0.5 writes every full-alignment tensor into its work folder in the output directory before the GPU predicts any, about 100 GiB for a 43x whole genome and two to four times that for 6-15x reads, which send it more low-quality candidates. Clair3 has no option to stream or batch them. vcf clair3 samples the reads' depth, estimates this peak for the bases it calls and refuses to start when the output directory's disk lacks it (--no-preflight overrides; see Clair3's temporary space). Choose an --outdir on a disk with room, or call a whole genome in --region batches (for example a few chromosomes at a time).

On the HG002 chr20:10-11 Mb slice below, --gpu gave the same 1,829 calls as the CPU (alleles, genotypes and filters; QUAL within 0.19, GQ within 1). On all of chr20 it took 8.5 min instead of 10.3 min on 4 CPUs (resource estimates), with the same vcfeval F1 (0.9785), but about 2,700 of the 144,543 records (1.8%) were missing, extra or genotyped differently. About two thirds lie in the 25.5-32 Mb pericentromere, where depths pass 216x: Clair3 2.0.5's GPU mode stores pileup counts as 8-bit integers, so counts above 127 wrap, and skips the CPU mode's scaling of such deep pileups; every pileup call whose quality changed by 1 or more was deeper than 100x. With both fixed by hand, the pileup calls matched the CPU's (QUAL within 0.03), but 6 of 360,471 flipped near a threshold, which changes WhatsHap's phasing and so about 1,000 full-alignment calls, with the same F1.

Bioconda's unpatched caller cannot select Apple MPS. Its Linux Clair3 depends on CPU-only PyTorch (pytorch-cpu), so its --use_gpu falls back to the CPU. With conda-forge's CUDA PyTorch swapped in by hand, Bioconda's own Clair3 ran on the GPU and gave the same calls (#639).

On the HG002 chr20:10-11 Mb slice (R10.4.1 sup v4.0.0 reads, model r1041_e82_400bps_sup_v400, 4 threads), Clair3 2.0.5 on Linux x86-64 gave the same records as 2.0.3, from CRAM 3.1, CRAM 3.0 and BAM input (vcfeval F1 0.979 against GIAB v4.2.1). On an Apple M1 it took 44 s, and 1,786 of its 1,827 calls matched the 1,829 Linux calls in alleles and genotype. The rest were mostly multi-allelic homopolymer indels, and qualities differ slightly, because floating-point results can differ between CPU backends. Its F1 was 0.978.

On Linux ARM64 (Ubuntu 24.04, Ampere Altra, Azure Standard_D4ps_v5, 4 cores, 16 GiB RAM), the native clair3 Pixi environment installed successfully. The same realigned 1 Mb slice, supplied as CRAM 3.1 with the full hs38 reference, took 95.77 s wall and 0.52 GiB peak RSS through the CLI with 4 threads (2026-11-15). All 1,829 sites, alleles, genotypes and FILTER values matched Linux x86-64; only two QUAL values differed, by 0.01. Both used Clair3 2.0.5 and CPU PyTorch 2.14.1.

wgsextract vcf clair3 -i hg002-ont.bam --ref chr20.fa \
  --region chr20:10000000-11000000 --threads 2 --outdir ont-clair3 \
  --model r1041_e82_400bps_sup_v500

The model must match the basecaller that produced the reads. It is chosen in this order:

  1. --model NAME|DIR;
  2. clair3_model in config.toml, for example clair3_model = "/data/clair3-models/r1041_e82_400bps_sup_v420";
  3. the Dorado/Guppy basecaller model named in the @RG (DS:basecall_model=, ID) or @PG header lines. For example, dna_r10.4.1_e8.2_400bps_sup@v5.0.0 selects r1041_e82_400bps_sup_v500, R10.4 E8.1 selects r104_e81_*_g5015, and R9.4.1 selects r941_prom_sup_g5014.

If the header names no basecaller (common after realignment, or for older public data), or names several, the command stops and asks for --model. A model for another pore, kit or speed than the metadata states is refused. A different accuracy (hac/sup) or basecaller version is allowed with a warning. HiFi and Illumina models are refused, as are *_with_mv models, which need Dorado move tables and --enable_dwell_time.

A NAME is one of the models Bioconda bundles in the environment (.pixi/envs/clair3/bin/models; the error lists them). Download others (for example Dorado v4.2/v4.3 models) from HKU's PyTorch catalogs, keeping the directory name:

m=r1041_e82_400bps_sup_v420
mkdir -p clair3-models/$m
for f in pileup.pt full_alignment.pt; do
  curl -fL -o clair3-models/$m/$f \
    https://www.bio8.cs.hku.hk/clair3/clair3_models_rerio_pytorch/$m/$f
done

Then set clair3_model in config.toml to that directory, or pass it with --model.

Bundled models are in clair3_models_pytorch/, Rerio-derived models in clair3_models_rerio_pytorch/. Clair3 1.x TensorFlow models do not work with Clair3 2.x. Before calling, the CLI checks both files against the SHA-256 digests pinned in src/wgsextract_cli/assets/clair3/models.json, which covers 31 ONT models from both catalogs. A mismatch is an error. A model without a pin, such as a custom one, runs with a warning.

On a 1 Mb slice (chr20:10-11 Mb) of public HG002 R10.4.1 sup reads (ONT's GIAB 2023.05 release, which records basecaller_cfg dna_r10.4.1_e8.2_400bps_sup@v4.0.0), realigned with realign and scored with rtg vcfeval against GIAB v4.2.1 inside its confident regions (1,355 SNVs and 234 indels):

CallerSNV F1Indel F1Overall F1
vcf deepvariant (ONT_R104)0.9990.8750.982
vcf clair3 --model r1041_e82_400bps_sup_v400 (matching model)0.9970.8620.979
vcf clair3 --model r1041_e82_400bps_sup_v410 (bundled)0.9980.8910.984
vcf clair3 --model r1041_e82_400bps_sup_v4200.9980.8390.977

The callers are within a few indels of each other on this slice, so DeepVariant stays the default. Results on all of chr20 are under Validation on GIAB HG002.

Structural variants#

vcf sv runs Sniffles2 for detected ONT input; --ont requests the same explicitly, and the platform-neutral --long-read selects Sniffles for any long-read data. pbsv is PacBio-only, so it is refused for ONT (detected or --ont), whether chosen by --caller pbsv or by --pacbio's pbsv default. --ont/--long-read with --caller delly, and --ont with --pacbio, are rejected; an explicit --caller delly on detected ONT or PacBio reads runs but warns (a short_read_sv_caller manifest warning) that Delly is a short-read caller.

PacBio input gets a long-read caller too, whether detected (read group PL:PACBIO) or declared with --pacbio: pbsv when installed, else Sniffles. HiFi reads get pbsv's CCS thresholds; detected subreads (CLR, every read group's DS naming READTYPE=SUBREAD) keep its defaults, as does an explicit --caller pbsv unless --ccs is added. When neither pbsv nor Sniffles is installed, vcf sv stops and names the pacbio Pixi environment that provides them, rather than silently falling back to Delly; it never installs them. Pass --caller delly to use Delly anyway. The result manifest's caller metric names the tool and caller_reason says why it was chosen (for example detected PacBio HiFi reads, --pacbio, or --caller).

wgsextract vcf sv -i hg002-ont.bam --ref chr20.fa \
  --region chr20:10000000-11000000 --threads 1 --outdir ont-svs

Sniffles2 runs with its defaults, which are tuned for both ONT and HiFi. --tandem-repeats BED is forwarded to Sniffles (as well as pbsv). On HG002 chr20, though, Sniffles' own GRCh38 TRF annotation lowered agreement with the GIAB v5.0q benchmark (F1 0.861 without it, 0.797 with it; see validation), so it is not passed by default. Mosaic mode (--mosaic) is not used: this command calls germline SVs. The VCF sample is the reads' @RG SM when they name one sample (Sniffles itself would write SAMPLE).

Without --region, Sniffles skips contigs shorter than 1 Mb (chrM, unplaced and decoy contigs), so they get no SV calls. A --region on such a contig is called. Install Sniffles (for example via the pacbio Pixi environment); it is checked, not installed automatically.

Methylation#

methylation pileup turns the MM/ML base-modification tags that Dorado writes (with a modified-base model such as 5mCG_5hmCG) into a bedMethyl table with ONT's modkit pileup. modkit is optional. Install it with pixi install -e modkit; the CLI checks for it but never installs it. Bioconda builds modkit for Linux and macOS only, so the command is refused on native Windows; use WSL2 there.

wgsextract methylation pileup -i hg002-ont.bam --ref chr20.fa \
  --region chr20:10000000-11000000 --threads 2 --outdir ont-methylation

It writes <input>.cpg.bedmethyl.gz (BGZF, tabix-indexed) and <input>.cpg.methylation.tsv, and logs the summary. With --format parquet (needs the optional pyarrow) the summary is <input>.cpg.methylation.parquet and every site is also saved, typed, in <input>.cpg.bedmethyl.parquet; see Parquet output. Per modification, the summary lists sites, sites with at least 5 valid calls, median coverage, the weighted fraction modified (all calls pooled), the mean per-site level, and the shares of sites at 80% or more and at 20% or less.

Promoter, CpG island and imprinted DMR summaries#

Use methylation regions on a coordinate-sorted, strand-combined CpG bedMethyl from methylation pileup, or on a precomputed modkit-style bedMethyl with valid-call and modified-call counts. It also reads the typed .bedmethyl.parquet from pileup. You don't need modkit to summarize these files; the command works natively on Windows with samtools. Supply the indexed plain or BGZF FASTA used for the pileup and declare its assembly (hg38 or t2t, the CHM13v2.0/hs1 build).

wgsextract methylation regions -i sample.cpg.bedmethyl.gz --ref hg38.fa \
  --build hg38 --preset promoters --outdir reports
wgsextract methylation regions -i sample.cpg.bedmethyl.gz --ref hg38.fa \
  --build hg38 --preset cpg-islands --outdir reports --download
wgsextract methylation regions -i sample.cpg.bedmethyl.gz --ref hg38.fa \
  --build hg38 --preset imprinted-dmrs --outdir reports
  • promoters uses primary-chromosome NCBI RefSeq RS_2025_08 annotations for GRCh38.p14 and CHM13v2.0. It takes one transcript per gene locus: MANE Select, then RefSeq Select, then the longest exonic transcript; ties within a priority are resolved by accession (GFF feature ID for unaccessioned transcripts, after accessioned ties). The window is 2,000 bases upstream and 500 transcribed-side bases from the 5′ boundary, clipped to each chromosome. The half-open windows are [t−2000,t+500) on + and [t−500,t+2000) on −; override the sizes with --upstream and --downstream.
  • cpg-islands uses the masked UCSC cpgIslandExt track on assembled chromosomes (hg38 SQL table, hs1 BigBed; UCSC data terms). Both tracks are pinned by SHA-256. The hs1 intervals and promoter starts are bundled. For hg38 islands, the first run needs explicit --download; subsequent runs verify and reuse the cached table in the reference library's methylation/ directory. The request sends only the public table name to UCSC, never sample data.
  • imprinted-dmrs uses 14 bundled GRCh38 differentially methylated regions (DMRs), including imprinting centers and secondary DMRs. Use --build hg38 with matching input and FASTA. T2T and GRCh37 are not supported for this preset; it never lifts coordinates over. The preset runs locally with no download and works with both pooled calls and --partition-hp. It reports methylation for research, not clinical imprinting results or X-inactivation. These intervals are separate from the broader qc roh review regions. HP1 and HP2 do not identify the parent of origin.
  • BED positions are zero-based and half-open. A CpG belongs to a region when its reference C is inside, even when its G is outside. Overlapping regions each receive the CpG. Primary aliases (21, chr21, assembly accessions) are matched only via the build's assembly report and matching FASTA lengths. Plain bedMethyl has no reliable assembly header: you are responsible for giving the same build and FASTA. The command checks the available assembly metadata and the CpG context of calls that hit the selected regions.
  • A CpG qualifies with at least five valid calls (--min-valid-calls), and a region needs at least three qualifying CpGs (--min-cpgs). The table gives expected, observed and qualifying CpGs, the fraction that qualify, median qualifying depth, valid and modified call counts, and three percentages from qualifying sites: pooled_percent weights by call count; mean_percent and median_percent give each CpG equal weight. no_transcript, contig_absent, no_reference_cpgs, no_valid_calls and insufficient_coverage leave percentages empty (null in Parquet), not zero. --5hmc is an explicit declaration that the source model called 5hmC and reports separate m and h rows. A missing code is marked modification_not_tabulated when the file contains the other requested code. Do not add valid depths across codes or use --combine-mods pileups.

The output is <input stem>.<build>.<preset>.methylation.tsv, or .parquet with --format parquet. The result manifest records the reference, annotation version and checksums, and the promoter and coverage rules. Without --partition-hp, these are pooled, descriptive summaries. For timing and disk measurements on public HG002 data, see methylation region resource estimates. If you already have a site table and do not need haplotype comparisons, summarize that table rather than running modkit again.

The imprinted-dmrs BED adapts Mackay, Bliek, Kagami et al. (2022), Table 2, © The Author(s) 2022, under CC BY 4.0. The retained coordinates are based on Monk et al.. We converted the source positions from 1-based closed to 0-based half-open BED and removed footnote markers. The 37 bp MEG3/DLK1:IG-DMR row, which cites a different coordinate source, is omitted; MEG3:TSS-DMR is retained.

Split region summaries by haplotype#

On Linux or macOS with modkit 0.6.4, add --partition-hp and pass the coordinate-sorted, indexed BAM or CRAM from vcf phase --haplotag. The alignment must retain its MM/ML tags and have HP tags on reads in the selected regions. Use the original indexed alignment FASTA. The command does not phase the reads again, and it does not fetch sample data.

wgsextract methylation regions -i phased/haplotagged.bam --ref hg38.fa \
  --build hg38 --preset promoters --partition-hp \
  --phase-blocks phased/phased.blocks.tsv --threads 4 --outdir reports

In this mode, the command writes <input stem>.<build>.<preset>.methylation.hp.tsv or .methylation.hp.parquet, without keeping intermediate bedMethyl files. The row schema describes the output. Each region and modification has combined, hp1, hp2, and unphased rows, with coverage thresholds applied independently. unphased counts are the site-level combined counts minus HP1 and HP2; they include calls without a usable HP tag. Use observed_valid_calls to see counts even below the reporting threshold. An absent or low-coverage partition has no percentage, not 0%.

  • The combined row reports shared_qualified_cpgs and, when there are enough shared CpGs, hp1_minus_hp2_pp. This signed difference subtracts HP2 from HP1 in percentage points, weighting each group by its own valid depth on the same CpGs. It is not necessarily the difference between the two partition rows' pooled_percent values.
  • A single_ps result requires one consistent PS among overlapping haplotagged MM/ML reads. It does not assert phase-block bounds. Provide --phase-blocks from the same phasing run to additionally require the entire region to fit within one matching block (single_block). cross_block, missing_ps, phase_set_mismatch, outside_block, no_phased_reads, no_transcript, and contig_absent leave the difference blank. The phase check conservatively includes reads overlapping the one-base right pad used to capture reverse-strand CpG calls.
  • HP labels are local to the phase set. They do not identify maternal or paternal copies, and the result does not call imprinting.

The manifest records the modkit partition method, coverage cutoffs, and whether a phase block table was used. The pinned UCSC annotation download rules are the same as for the precomputed workflow.

Phasing#

vcf phase phases a sample's heterozygous calls with its own reads and writes phased.vcf.gz (phased GT with PS phase sets), phased.blocks.tsv (one row per phase block) and, with --haplotag, haplotagged.bam/.cram with HP/PS read tags for haplotype-resolved views or methylation.

pixi install -e phasing          # WhatsHap and LongPhase; checked, not installed
wgsextract vcf phase --input sample.cram --vcf-input calls.vcf.gz --ref hs38.fa.gz \
  --outdir phased --haplotag
  • --phaser chooses whatshap or longphase. Unset, LongPhase is used for Nanopore and PacBio reads (faster, and fewer switch errors below) when it is installed, otherwise WhatsHap. LongPhase is long-read only; short reads get WhatsHap and a short_read_phasing warning, since short reads link few variants.
  • The VCF sample is the one named by the reads' @RG SM; a single-sample VCF is used as is. Existing PS values are dropped and recomputed, so a phased benchmark VCF (GIAB's PS is a string) can be re-phased.
  • WhatsHap is single-threaded; --threads runs contigs in parallel.
  • The result manifest records heterozygous_variants, phased_variants, phased_pct, phase_blocks and block_n50_bp (block span = last minus first phased position, as whatshap stats measures it).
  • Linux and macOS only. LongPhase has no Intel-Mac build; WhatsHap is used there.

Repeat expansions#

typing str sizes the disease repeats of ExpansionHunter's catalog (HTT, FMR1, C9ORF72, ... 31 on hg38, 30 on hg19) and puts each allele in STRchive's normal, intermediate or pathogenic range. Nanopore and PacBio reads go to LongTR (GPL-2.0 in its repository, BSD-2-Clause on Bioconda), short reads to ExpansionHunter, by the reads' platform. --caller strkit uses STRkit (GPL-3.0) instead.

pixi install -e longtr           # or -e strkit; checked, not installed
wgsextract typing str --input sample.cram --ref hs38.fa.gz
  • The output contract is the same for every caller: <stem>.str.tsv (or <stem>.str.parquet with --format parquet and PyArrow) with one row per repeat. There is a repeat_outside_normal_range warning per flagged repeat and the repeat_caller metric. GRCh37 has no NOTCH2NLC, so on hg19 its row reads "not available on hg19" with a repeat_unavailable warning. LongTR writes <stem>.str.vcf.gz; STRkit <stem>.str.vcf and <stem>.str.strkit.json. LongTR gives no confidence interval, so its ci column is -. Typed allele counts, intervals and support are in both formats and in details.repeat_calls in the result JSON; see the manifest contract.
  • --loci HTT,FMR1,AR sizes only those case-sensitive catalog IDs. Selection preserves catalog order, including all variants of a compound ExpansionHunter locus. LongTR takes the ID from column 5 and STRkit from the ID= attribute in column 4. Any unknown ID is an error. Targeted runs add a hash of the selected IDs to the .str prefix, so they don't replace full-catalog results. Custom loci without disease thresholds are still reported, with no assigned disease range.
  • The bundled catalog (commands/genotyping/str_catalog/, rebuilt by scripts/build_str_catalog.py) uses ExpansionHunter's reference regions, so counts are in the units of the STRchive thresholds, with STRchive's extra motifs (RFC1's AAGGG, ACAGG, ...). Its sources are pinned by commit and SHA-256 in provenance.json: ExpansionHunter v5.0.0 (Apache-2.0) and STRchive v2.28.0 (MIT). NIPA1's motif is CGC on hg19 and GCG on hg38: GRCh38 inverted its region, and the motif follows the reference strand.
  • The allele_reads column has each allele's reads (LongTR's MALLREADS, STRkit's peaks). An allele from a single read, under 10% of the repeat's reads, is "low support": LongTR makes such alleles (HG002's DMPK 11/19, truth 11/11). It doesn't count towards the status; when it alone would change it, the status adds "unconfirmed: one read suggests ..." with a repeat_unconfirmed warning. The limits are low because true expansions are thinly read: on the PureTarget set below, STRkit read a 1.2 kb DMPK expansion in 2 of 247 reads, and LongTR an FXN one in 1 of 1. When every called allele is low support, the status is unresolved, not pathogenic or normal. Expected ploidy is two autosomal copies and one X copy for males or two for females (the explicit or inferred --sex). A missing allele is not evidence of homozygosity: incomplete recessive calls are unresolved, even when the observed allele is expanded. Raw sizes remain in the table and caller files. These unresolved calls emit repeat_unconfirmed, count in unconfirmed_repeats rather than the normal range or flagged_repeats, and appear in the personal report's Repeat Expansions section. If clipped reads independently suggest an unsized expansion, the unresolved call also retains repeat_outside_normal_range, its flagged_repeats count, and the clinical-confirmation warning.
  • LongTR has no threads; --threads runs chromosomes in parallel. It drops reads below mean base quality 30, which leaves most ONT R9.4.1 loci uncalled; R9 reads (named in the header) get an r9_reads warning suggesting --caller strkit.
  • Aligners soft-clip expansions much longer than about 1 kb, and neither caller sizes clipped reads. When at least 3 reads (and 5% of them) are clipped by 100 bases or more at a repeat, its status says so and it is flagged, even as a no-call. STRkit realigns clipped PacBio HiFi reads and then sizes those expansions (it recommends that for HiFi only).
  • TRGT refuses Nanopore reads and is PacBio-licensed, so it isn't wrapped.

Measured on HG002 ONT R10.4.1 (~51x, the #431 CRAM), 4 cores: about 10 s for either caller after sex inference (2.5 minutes for this CRAM; --sex skips it). Against the GIAB HG002 tandem-repeat benchmark v1.0.1 (assembly-based), LongTR was within one repeat unit at 26 of the 27 repeats inside its benchmark regions (96%) and STRkit at 24. The miss was DMPK, where LongTR made a one-read allele of 19 units (truth 11/11). Outside the benchmark regions, both read 24 CAGs on one HTT allele where the benchmark VCF has 19; the reads agree with the callers.

On PacBio PureTarget data of 19 Coriell cell lines with known expansions, every expansion under about 1 kb (HTT, ATN1, ATXN1, ATXN3, DMPK, AR, FMR1 premutation, PABPN1 with LongTR) was called pathogenic or premutation, at TRGT's sizes once its wider regions are allowed for (STRkit missed the PABPN1 one); the 1-3 kb ones (DMPK, FMR1 full mutations, FXN, RFC1) were flagged by their clipped reads, and STRkit sized most of them.

Adaptive sampling targets#

panel bed turns gene names and curated presets into a BED for MinKNOW's adaptive sampling (or any targeted analysis), and info calculate-coverage --by reports how well a run covered it.

wgsextract panel bed --list-presets
wgsextract panel bed --preset pharmacogenes --preset hla --ref hg38.fa
wgsextract panel bed --genes BRCA1,BRCA2 --gene-file my_genes.txt --pad-kb 50
wgsextract info calculate-coverage --input run.bam --by panel_pharmacogenes_hla_hg38_pad100kb.bed
  • Genes. Names are matched without regard to case against the bundled NCBI RefSeq annotations (public domain) for hg38 (GRCh38.p14, release RS_2025_08), T2T (CHM13v2.0, RS_2025_08) and hg19 (GRCh37.p13, RS_2024_09). A name that is a unique alias of one gene resolves to it with a warning. Every unknown or ambiguous name is reported at once, with suggestions, and nothing is written.
  • Presets. pharmacogenes (PharmCAT's genes), hla (the classical MHC, GABBR1 to KIFC1), autoimmune (Cotsapas 2011's shared autoimmune loci plus the MHC), acmg-sf (ACMG SF v3.3's 84 genes) and cardiac (its cardiovascular genes). --list-presets prints each source and gene list.
  • Regions. Each gene's span is padded by --pad-kb (default 100 kb each side: adaptive sampling decides on a read's first few hundred bases, so reads that start in the flank reach the gene), clipped to the contig, and overlapping or touching regions are merged. The BED has four columns: contig, start, end and the genes in the region. No strand is given, so both strands are targeted.
  • Build and names. --ref (or the configured reference) sets the build and the contig names, so chr1/1 and chrM/MT match the FASTA MinKNOW aligns to. A reference of another build than --build, or with other contig lengths, is refused. A chrM that isn't rCRS (UCSC hg19's 16,571 bp) is targeted whole, with a warning. Without a reference the BED uses chr names of --build (default hg38).
  • Size. ONT recommends targets of no more than 5% of the genome, best around 1%, for the best enrichment. Each run reports the fraction and warns above 5%. At 100 kb padding on hg38, pharmacogenes is 0.21%, hla 0.13%, autoimmune 0.43%, acmg-sf 0.75% and cardiac 0.40%.

--by BED replaces the per-chromosome report with one row per target: mean and median depth, the fraction of bases at 10x, 20x, 30x and --min-depth (default 30), and whether the mean is below --min-depth. A summary gives the on-target and off-target mean depth and their ratio, the enrichment. Overlapping targets are each measured in full, but counted once on target; the mitochondrial contig counts as neither on nor off target unless the BED names it. Depth follows samtools depth's defaults, like --bins: deletions and duplicates don't count, overlapping mates do. BED contig names may use chr1 or 1 style either way.

The assessed scope defaults to the whole alignment header, not just contigs with reads. For a regional BAM retaining a full reference header, explicitly declare the assessed contig or 1-based inclusive interval with --region chr20 or --region chr20:100001-200000. With --by, every target must fit inside that scope (outside targets are refused rather than silently clipped). The off-target depth sum and denominator then use only assessed nuclear bases outside the merged targets. Capture and whole-genome BAMs should retain the whole-header default: unsequenced off-target contigs still count in the assay. The scope is recorded in the manifest's provenance.params.region, the assessed_scope metric and the text summary; regional output names include the scope so they do not overwrite whole-header reports.

Sampling needs the BAM/CRAM index: without one, info warns, falls back to the record estimate and caches it until an index appears. Unaligned reads have no depth to sample, so it is cached as zero.

Whole-genome ONT requirements#

Read lengths and mapping rate#

For ONT and PacBio input (by the read groups' PL or the read names, else reads averaging over 410 bp), info also reports the read N50 and, with --detailed, a read-length histogram and the percentage of reads that map (#338). Neither needs a full pass over a large file:

  • The N50 and histogram come from the primary reads among the first 20,000 records, which info reads anyway; QC-failed reads count too. When those are the whole file the N50 is exact; otherwise it is labelled an estimate.
  • A file of up to 200,000 records has its reads counted exactly (samtools flagstat). For a larger one, the index counts mapped and unmapped records, but a long read often has several supplementary or secondary records. So the share of mapped records that are primary is sampled from records that start in evenly spaced 10 kb windows, at least 1 Mb apart, which counts short split records as fairly as whole reads. Windows that sample their contig more densely, like chrM's, are weighted less. That turns mapped records into mapped reads. It needs the index and a mapped read, so unaligned input reports no mapping rate.

info warns (short_read_n50) when the N50 is under 3 kb, below the roughly 4 kb peak of buccal-swab ONT runs, and (low_mapped_read_fraction) when under 95% of reads map. Both are recorded in the result manifest, and the <input>_qc table gains read_n50 and mapped_read_pct columns. The older reads_mapped_pct counts records, so it overstates long reads' mapping.

CLI / GUI contract#

No new option is needed for detection. Leave --platform unset for automatic selection; explicitly sending --platform illumina disables it. The CLI logs the detected platform. info recognizes PL:ONT even when read names were renamed. BAM/CRAM variant callers share the same cached, file-revision-aware platform resolver; detection alone does not qualify short-read callers for ONT. GUI integrations should allow automatic platform selection and surface the tag-preservation limitations above. Expose ONT_R104 and --ont for DeepVariant, preserve an unset model for automatic selection, and show its chemistry and architecture restrictions. For vcf clair3, expose --model (leave it unset for config or metadata selection) and hide the command on Windows. For vcf sv, expose --ont/--long-read, leave --caller unset for automatic Sniffles (ONT) or pbsv/Sniffles (PacBio) selection, and do not offer pbsv for ONT input. For methylation pileup, leave --context, --5hmc and --combine-strands unset so config.toml applies, hide the command on Windows, and show its bedMethyl and summary outputs. The GUI repository is separate; these CLI changes do not update it.
