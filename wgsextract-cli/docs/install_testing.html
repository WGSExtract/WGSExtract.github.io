End-to-end install testing (the install lab)

scripts/installlab/ tests what a new user actually does: install with the README command on a machine that has never seen WGS Extract, run real commands on a real genome, update, uninstall, and leave the machine as it was. It is built to be run over and over on the same computer, and to make false passes hard.

pixi run -e dev python scripts/installlab/lab.py run linux       # fresh Ubuntu container
pixi run -e dev python scripts/installlab/lab.py prepare macos    # once: clean macOS base image
pixi run -e dev python scripts/installlab/lab.py prepare macos --repair-policy # repair an existing base
python3 scripts/installlab/lab.py run macos                      # fresh macOS VM
python3 scripts/installlab/lab.py prepare windows                # once: Windows 11 base image
python3 scripts/installlab/lab.py run windows                    # fresh Windows VM (QEMU)
python3 scripts/installlab/lab.py selftest linux                 # negative controls must fail
python3 scripts/installlab/lab.py run linux --install-dir "WGS Extract"   # a path with a space
python3 scripts/installlab/lab.py run linux --update-from v0.4.0        # update a real release
python3 scripts/installlab/lab.py judge out/installlab/runs/<run>/results
python3 scripts/installlab/lab.py run macos --gui-repo gui                 # the macOS app
python3 scripts/installlab/lab.py prepare windows-gui            # once: WebView2 + a desktop
python3 scripts/installlab/lab.py run windows --gui-repo gui               # the Windows app
python3 scripts/installlab/lab.py run windows --gui-installer <setup.exe> --test-sign  # signed install
python3 scripts/installlab/lab.py run linux --gui-repo gui                 # the Linux app
python3 scripts/installlab/lab.py mutate out/installlab/runs/<run>/results  # must all FAIL
python3 scripts/installlab/lab.py gc --dry-run                    # what disk cleanup would remove

Results land in out/installlab/runs/<target>-<mode>-<time>/: the guest's evidence, state snapshots, outputs, and verdict.json. The lab's state (runs, base images, downloads, SSH key) lives in the main checkout's out/installlab, shared by every git worktree: base images take hours to build, and a linked worktree's out/ is deleted with the worktree.

SSH keys#

The lab logs into its VMs with its own key. The macOS base image trusts out/installlab/ssh/id_ed25519; if that key changes (the lab's state moved, or the key was deleted), the next macOS run authorizes the current key in the base over the vanilla image's password login, in about a minute, instead of needing prepare macos again. The Windows images trust out/installlab/windows/ssh/, kept beside them: Windows filters an admin's token on network logons, so a key file can't be rewritten over SSH, and the key moves and expires with the images.

Disk space#

A lab machine can hold 60 GB or more: base images, Tart's downloaded macOS images, per-run evidence, and the leftovers of a run that was killed. Everything the lab reuses is kept as a cache only while it's being used. lab.py run, prepare and selftest remove what has expired when they finish (afterwards, so the image a run just used is never the one removed), and lab.py gc does the same on demand:

WhatRemoved when
A killed run's VM clone, container, QEMU work dir or QMP socket dirnot running and over an hour old
Run evidence (out/installlab/runs/*) and lab logs14 days old (--runs-days)
A run's serve/ dir (installer, archive and dataset copies)1 day old
Base images (wgse-lab-macos-base, Windows base/gui-base), the dataset cache, the GUI build's Docker volumes and ubuntu:24.04unused for 30 days (--images-days)
What only prepare needs (Tart's OCI images, the Windows and virtio ISOs, the WebView2 installer)unused for 7 days (--downloads-days)
Pixi and Homebrew package cachesonly with --package-caches DAYS

"Used" is when a run last cloned or booted it: Tart records this for its VMs and images, and the lab records it in out/installlab/last-used.json (main checkout) for the rest (falling back to the file's modification time). Windows' base is kept as long as gui-base, which is built on it. Only things the lab names and creates are touched; ubuntu:24.04 only once a run has recorded using it. pixi run clean still removes all of out/ and tmp/ at once.

Test runs clean up after themselves too: pytest keeps the temporary directories of failed tests only (tmp_path_retention_policy = "failed").

Why installs used to "pass" while being broken#

Failure modeDefence
Leftover state from earlier runs or the developer's own setup (~/.pixi, Homebrew tools on PATH, caches, config.toml, reference data) masks a missing dependencyEvery run uses a new machine cloned from a clean image and destroys it afterwards: a Tart VM from Cirrus Labs' vanilla macOS image (no Homebrew, no tools), or a fresh ubuntu:24.04 container. Nothing survives between runs, so cleanup on the host is never needed.

It downloads the script completely before starting the shell, so a transient HTTP failure cannot execute a partial installer. Only the source archive and dataset come from the host, over HTTP, so the tree under test is installed exactly like a release.

It records exit codes, logs and outputs; the host oracle checks the outputs against values that come from biology, not from a previous run: HG00096's published mtDNA haplogroup (H16a1), recall and precision against its 1000 Genomes genotypes, read and mapping counts measured with the host's own samtools/bcftools.

The lab machine's policy differs from a normal Mac (the vanilla macOS image disables both Gatekeeper and its Developer ID rules)prepare restores the normal policy through authenticated Settings input. What one run covers#

  1. Baseline snapshot of a machine with only the documented prerequisites (macOS: Xcode Command Line Tools, baked into the base image by prepare; Ubuntu: curl, ca-certificates).
  2. Fetch the installer with bounded retries, then run sh with the script on stdin from the user's home directory, as a normal user. Only the download is retried; the installer runs once.
  3. The workload (guest/workload.sh) on the HG00096 mini genome: --help, deps check, ref bootstrap (a real GitHub release download with digest verification), info on BAM and CRAM, extract mt-bam / mito-vcf, lineage mt-haplogroup / y-haplogroup, vcf snp, sample set --sex Male, microarray, align (bwa, from FASTQs), vcf gatk (after explicitly installing the optional gatk Pixi environment), and a command that must fail.
  4. Update by rerunning the installer; a marker in app/reference/ must survive, and the CLI must still work. With --update-from <tag> the run instead installs that published release with its own installer (and the prerequisites it had, e.g. git before 0.4.1), updates it to the tree under test, and runs the workload on the result. --install-dir installs into another folder under $HOME, such as one whose path has a space. CI runs both on Linux, updating from the latest release.
  5. uninstall.sh --yes --remove-config --remove-pixi, then the final snapshot.

Explicit config removal includes the owned default visible users workspace's config and, only when otherwise empty, its ownership marker and directory. Workspaces containing libraries or other user data remain intact; the oracle does not ignore leftover workspace config files.

The CLI workloads and app test plan explicitly declare HG00096's known male sex through sample set before running the analyses. This rebased mini genome has no informative chrX assay, so coverage-based inference correctly returns Unknown; the lab must not bypass the product's unknown-sex ploidy safeguard.

Its truncated, rebased contigs also cannot confirm the full hg19 assembly. The CLI workload passes the fixture's ploidy explicitly for microarray; the app workload puts the same file in its test reference library for SNP and microarray calling, whether Setup installs the current tree or the CLI pinned by the app. The file uses mini-genome coordinates.

The mini genome has 5x coverage, below microarray's default DP ≥10/GQ ≥20 evidence gates. The scenario keeps those real-user defaults and requests --call-reasons; it does not disable filtering to make the fixture pass. The oracle independently checks each exported call/no-call against the called VCF's sample depth, confidence and FILTER (using internal reference-call QUAL when bcftools omits GQ). All eligible calls must be retained, weak sites must be no-calls, and their reason table must agree. At least 1,500 truth sites must be represented and some callable sites must remain; an all-no-call kit cannot pass. At least 95% of the callable genotypes must match 1000 Genomes. No-calls at weak sites are expected, not genotype disagreements.

The macOS app#

lab.py run macos --gui-repo gui tests the WGS Extract app the same way. It packages the DMG and builds the bundle-test runner from that checkout every time (--dmg tests a given DMG instead), so a stale build can't be what passes. In the VM:

  1. The DMG is downloaded and given the quarantine flag a browser sets; Gatekeeper must accept a Developer ID build and must reject a local ad-hoc one (the base image has standard Gatekeeper policy, and every run records its status).
  2. The app is copied to /Applications as a drag install would, then launched; it runs its own setup (WGSEXTRACT_GUI_AUTO_RUN_SETUP) and writes the result. Setup installs the CLI release the app pins, or this CLI tree with --cli-from-tree.
  3. The real actions run on the HG00096 mini genome through the same GUIForCLICore runner the app uses (gui-for-cli bundle test) with the installed app's bundle and workspace. On macOS, Linux, and Windows, the packaged Node runner uses the same app-data identity as setup so it finds the installed CLI runtime, rather than looking in a development directory. Clicking isn't simulated; everything the click would start is. The reference-genome dropdowns' data sources are loaded the same way (dataSource steps): each script must resolve for the platform, run on the app's own runtime and print its list (gui-for-cli#140 was these failing with spawn python ENOENT on Windows). The dropdowns only list catalog genomes and the mini genome isn't one, so the plan first downloads hs38 (755 MB, from this repo's release) with the Library page's own download action, and each dropdown must then offer it.
  4. The app's own Uninstall (WGSEXTRACT_GUI_AUTO_RUN_UNINSTALL) runs the bundle's uninstall steps, removes the app's data and moves it to the Trash; the Trash is emptied and the machine must match the baseline. One exception: macOS's preferences daemon (cfprefsd) writes the app's deleted preferences file back, empty, up to seconds after the app exits, whatever the app does (even defaults delete leaves it). The scenario saves the file as the final snapshot sees it, and the oracle excuses it only if that copy has no keys; lab.py mutate checks that a kept setting, or a missing copy, still fails.

The oracle (gui_oracle.py) treats the app's own setup, uninstall and test reports as evidence, not verdicts: every planned action must have passed, and its outputs get the same biology checks as the CLI's. The app's microarray action has no --ref-vcf-tab, so on the rebased mini genome only the kit's format is checked there; the CLI lab measures concordance.

Published macOS release acceptance#

Test the DMG downloaded from the published release, not a locally packaged app or a manually dispatched Actions artifact. Use the app's source at the release tag (gui/ of a checkout of the tag; for releases up to v0.6.6, a checkout of the former gui-for-cli repository) to build the bundle-test runner. The plan's dataSource steps need v0.4.4 or later; an older runner rejects them.

mkdir -p out/installlab/releases/v0.4.4
gh release download v0.4.4 --repo WGSExtract/gui-for-cli \
  --pattern WGSExtract-0.4.4.dmg --dir out/installlab/releases/v0.4.4
pixi run -e dev python scripts/installlab/lab.py run macos \
  --gui-repo ../gui-for-cli \
  --dmg out/installlab/releases/v0.4.4/WGSExtract-0.4.4.dmg

Do not add --cli-from-tree: acceptance must exercise the CLI pinned by the released app. Retain the release URL, tag commit, downloaded DMG's SHA-256 (matching GitHub's asset digest), and run verdict. Require both standard Gatekeeper policy and artifact acceptance, all planned actions, and strict uninstall baseline restoration; a successful signing job alone is not release acceptance. Use the DMG rather than a raw .app artifact, whose framework symlinks can be lost during artifact upload.

macOS base policy#

Cirrus's vanilla image disables Developer ID and notarization rules as well as Gatekeeper's master switch. spctl --global-enable alone leaves an App Store-only machine: even a correctly notarized app is rejected. On macOS 26 the old spctl --enable and native policy-update interfaces cannot restore those rules.

prepare macos uses Tart's authenticated, loopback-only VNC display to select App Store & Known Developers in System Settings and approve the normal authorization dialog with the disposable image's public admin account. Apple Vision reads the screenshots to locate controls instead of relying on screen coordinates. Swift (the host's Command Line Tools) and the dev Pixi environment are prerequisites; the lab does not install host tools. No host credentials, TCC changes, policy-database edits, Gatekeeper bypasses, or app exceptions are involved.

To repair an existing base without rebuilding or reinstalling its prerequisites:

pixi run -e dev python scripts/installlab/lab.py prepare macos --repair-policy

The repair is a no-op when the native read-only policy checks already pass. Provisioning screenshots and before/after state live in the shared lab's out/installlab/macos-policy/; its vnc.private.log is mode 0600 because the temporary VNC connection URL contains authentication material. Do not publish that file. A missing, ambiguous or unverified control fails provisioning rather than accepting a less secure policy. Each subsequent test boots a fresh clone and verifies the persisted policy before any product code runs.

The Windows app#

lab.py run windows --gui-repo gui tests the WGS Extract Windows app (Tauri, NSIS installer) the same way. It cross-builds the x64 installer from that checkout every time: on macOS with make package PLATFORM=tauri-windows-cross (which needs cargo-xwin, NSIS and LLVM, and says which are missing), on Linux the same way in an Ubuntu container, since distributions don't all package NSIS. --gui-installer <setup.exe> tests a given installer instead, such as a release. An app needs a signed-in desktop and the WebView2 runtime, so prepare windows-gui (once, after prepare windows) adds a second read-only layer, gui-base.qcow2, on top of the CLI's base image: the WebView2 Evergreen runtime (pinned by SHA-256; every Windows 11 PC has it, the image built from Windows Update files doesn't), and Lab User signed in at boot (autologon). Lab User's first desktop sign-in happens while preparing, so a run's baseline is a user who has used their PC before. Each run records the VM's screen once a minute (screens/ next to results/). In the VM, as the standard user Lab User:

  1. The installer is downloaded and given the Mark of the Web a browser adds. Its Authenticode signature is checked: a signed installer must verify (Valid), an unsigned one must be reported unsigned (NotSigned). Then it is unblocked, as clicking SmartScreen's "Run anyway" does.
  2. The installer is opened as a double-click would, on Lab User's desktop, and UI Automation clicks through its wizard's defaults (Next, Install, Finish), logging each page. The Apps entry, the Start menu shortcut and the app must exist, and the app must open from the Finish page's ticked "Run" box; it is closed again.
  3. The app is opened on Lab User's desktop (through a scheduled task that only runs in their signed-in session) and runs its own setup (WGSEXTRACT_GUI_AUTO_RUN_SETUP); the setup events it logs are the evidence. The window must report that the page drew (webAppRendered). Then the window is closed, and nothing the app started may still run.
  4. The real actions run through the app's own runtime: its bundled Node and the bundle-test runner it ships (bundle-test-cli.js), on the installed bundle and the app's workspace.
  5. Uninstall is Settings > Apps > Uninstall: the registered UninstallString opens the uninstaller's wizard, where UI Automation ticks "Delete the application data", clicks Uninstall, explicitly answers Yes to the separate users-workspace deletion question, and clicks Close, so the controls used are the wizard's real ones. The machine must then match the baseline, including the registry (Apps entries, user Path), the Start menu and %LOCALAPPDATA%.

Setup installs the CLI release the app pins, or this tree with --cli-from-tree. lab.py mutate has Windows-specific corruptions too (an Apps entry, shortcut, Path entry or running process left behind, and the signature check reversed: an unsigned installer reported as signed, or a signed release reported as unsigned).

No Windows release is Authenticode-signed yet, and a publicly trusted certificate costs money. --test-sign (windows target, app install runs) covers the signed path without one: before the baseline, the disposable VM creates a throwaway code-signing certificate, trusts it machine-wide (as an organization deploys its own signing root), signs the unsigned installer with it and deletes the private key. The signed installer replaces the one served to the guest, so its signature must then verify as Valid and the rest of the run proceeds as for a signed release; lab-run.json records test_signed. This proves the lab's signed path and that signing doesn't break the installer; it does not prove a public release is signed.

The Linux app#

lab.py run linux --gui-repo gui tests the Linux app (Tauri, .deb). Tauri can't cross-build Linux packages, so the lab builds the .deb the way make package PLATFORM=tauri does, in an amd64 ubuntu:24.04 container (Cargo and the build tree are kept in Docker volumes between builds); --gui-installer <deb> tests a given package. The scenario (guest/gui-linux.sh) runs in a fresh ubuntu:24.04 container as a desktop user who may use sudo, as Ubuntu's first user can, with Xvfb as the display: sudo apt install ./WGSExtract.deb, the app runs its own setup, the plan's actions run through the app's bundled Node and runner, then the app's own Uninstall (File menu; WGSEXTRACT_GUI_AUTO_RUN_UNINSTALL), since a package manager can't remove what setup put in the user's home, and finally sudo apt remove --autoremove. The desktop entry must have been installed, and the home folder must end as it started.

Setup runs alone#

No scenario step may start while the app runs setup: the app's Uninstall stops every process under the runtime folder, including a running install (#448). So on every app target (Linux, macOS and Windows), however setup ends, the scenario closes the app and waits until the app and everything it started (processes under the install and the workspace) are gone. What won't stop after the window closes is killed; what won't die ends the scenario, and the evidence it then lacks fails the verdict. The Linux and macOS scenarios share this in guest/app-lifecycle.sh; they watch the app they launched by its process ID.

Each scenario writes timeline.tsv (milliseconds, event): step starts and ends, the app's launch, exit and close, growth of setup's event log, and what the harness did. The oracle checks from it that nothing ran beside setup (app.setup_alone). When a setup step ends with a signal, app.setup names its likely sender: the last scenario step, harness action or app exit before the event was seen.

Targets#

  • macos – Tart VM (Apple Silicon hosts). prepare macos clones ghcr.io/cirruslabs/macos-tahoe-vanilla and installs the Command Line Tools headlessly into wgse-lab-macos-base; each run clones that (an instant APFS clone), boots it headless, shares only the results and guest-script folders, and deletes it.
  • linux – ubuntu:24.04 linux/amd64 container (Docker or OrbStack), with a non-root tester user. On a Linux host the container downloads from the lab's file server on the Docker bridge's address (172.17.0.1), so a host firewall must let the bridge reach it, e.g. with ufw: ufw allow in on docker0 from 172.17.0.0/16 to 172.17.0.1 proto tcp.
  • host – the current machine, for disposable CI runners only (refuses to run without CI set). The CLI runs as a new account; on a macOS runner the app runs as the runner's signed-in account (see In CI).
  • windows – Windows 11 Pro in QEMU, with the host's architecture so it runs under hardware virtualization: ARM64 under hvf on Apple Silicon Macs (out/installlab/windows/), x64 under KVM on x86_64 Linux (out/installlab/windows-x64/; needs /dev/kvm, OVMF, bsdtar and Docker). prepare windows builds that directory's base.qcow2 once; each run boots a throwaway qcow2 overlay of it (the base is read-only), reaches it over SSH on a forwarded localhost port, and deletes the overlay afterwards. The guest downloads artifacts from the host at 10.0.2.2.
  • windows-host – a new standard user on a disposable GitHub Windows runner (CI only; see below), for the CLI and the app.

Windows#

The documented Windows path is: put install_windows.bat in an empty folder and run it; it downloads the release .zip, installs Pixi, and installs the Pixi environment with the native Windows tools. guest/windows/scenario.ps1 does exactly that as a standard (non-admin) user named Lab User, so every profile path contains a space, as on many real PCs. The workload is the same as on macOS/Linux, run as pixi run wgsextract … from the install folder; "update" reruns the installer in the same folder, and uninstall is uninstall_windows.bat --yes --remove-config --remove-prerequisites followed by deleting the folder the user downloaded. Each step's output goes through cmd.exe, so logs are raw bytes, and only the step's own process is awaited (a background process a step starts can outlive it). Before the workload, and after each installer run, the scenario reloads the environment from the registry, as a new terminal would.

guest/windows/inventory.ps1 snapshots the profile (depth 6, including AppData), C:\ top level (so a folder such as C:\msys64 appearing or staying behind is seen), Program Files, ProgramData, Start Menu, Windows Error Reporting and crash dump folders, user and machine environment variables (Path's value, not just its presence), Run keys, HKCU\Software vendors, Uninstall keys, scheduled tasks and PowerShell profiles. Registry values are recorded raw (unexpanded) with their type, and programs still running from outside C:\Windows are listed, so a background agent left behind fails the run. The user's %TEMP% is treated as noise, like /tmp on macOS/Linux. Paths are written with forward slashes so the same oracle and noise patterns apply. A walk that errors for any reason other than an access denial is retried and then reported as an error line, which fails the run.

Building the base image#

Microsoft's own ISO download refuses scripted requests, so prepare windows builds the install media from the files Windows Update serves (UUP dump), each checked against the hash in Microsoft's update metadata. The conversion runs in an ubuntu:24.04 container (cabextract, wimlib, chntpw, genisoimage); the Linux converter doesn't fold in cumulative updates, so the image is the newest release's base build (win11-<arch>.json records which). The virtio-win ISO (pinned by SHA-256) supplies the NetKVM driver for the VM's network card. On Linux, the files are taken from it with bsdtar and the setup ISO is made with genisoimage in a container (macOS uses hdiutil for both).

Deviations from a user's PC, all needed only to drive the VM headlessly, are listed in vm/windows/autounattend.xml: Setup's TPM/Secure Boot checks are bypassed, lab-apply.cmd applies the image from WinPE (24H2's new Setup host stalls before touching the disk in a headless VM), a local labadmin account replaces the Microsoft-account OOBE, and lab-setup.ps1 adds OpenSSH Server, the Lab User account, and turns off automatic Windows Update installs so a run isn't rebooted halfway. Windows' firewall rule for SSH is opened on the Public profile (QEMU's NAT is an unidentified, Public network, as on a user's PC). Defender stays on. Nothing WGS Extract needs is in the base image; Lab User has logged in once (over SSH), so the baseline isn't Windows' first-logon setup. On a Mac the VM is ARM64, so Pixi installs the win-64 environments under Windows' x64 emulation, as on a Snapdragon laptop; on an x64 host they run natively, as on most PCs.

On GitHub's Windows runners#

windows-host runs the same scenario on windows-latest, which ships MSYS2 at C:\msys64, Git, conda, Java, Python, Strawberry Perl and more. Before the run, vm/windows/deprovision-runner.ps1 renames C:\msys64, resets the machine Path to Windows' defaults and removes non-default machine environment variables, and the scenario runs over SSH as a newly created standard user. The tool survey (pixi, samtools, bcftools, java, python, conda, bash, gcc, perl, MSYS2) fails the run if anything is still reachable. The oracle runs on Linux with the host's samtools/bcftools, so the evidence is uploaded and judged (and mutated) by a separate Linux job.

In CI#

.github/workflows/install_lab.yml runs on manual dispatch and at release preflight. It does not run on push, on PRs or on a nightly schedule. See CI routing and cache budget for the routes and coverage. Within an hour of a new app release, app_release_watch.yml also dispatches the full matrix on main for that release (-f app_release=<tag>; the run is named after it):

JobMachineWhat runs
linuxa fresh ubuntu:24.04 container on ubuntu-latestthe CLI; again into a folder with a space; an update from the latest release; selftest
linux-appthe samethe app's .deb: the latest release, or built from the tree (see below)
macosa new account on macos-latestthe CLI; selftest
macos-appthe runner's signed-in accountthe app's DMG, chosen the same way
windowsa new standard user on windows-latestthe CLI; each sabotage on its own runner
windows-appa new standard user's desktop on windows-latestthe app's installer, chosen the same way
windows-judgeubuntu-latestjudges every Windows job's evidence

Every passing run is then corrupted (lab.py mutate) and every corruption must fail. The tree app jobs run with --cli-from-tree, so the app sets up the CLI under test, and drive the app with this tree's plan (scripts/installlab/gui/wgsextract-plan.json), which names the app's actions. They test the latest app release, as users get it, unless this tree's gui/ or plan differs from that release's tag. In that case app-build (gui-build.yml) builds the app unsigned from this commit for Linux, macOS arm64 and Windows (about 14–24 extra runner minutes), and the tree jobs test that build. The judge still requires the platform's signature check to refuse it. A plan step the app lacks fails as "the test plan expects action X, which this app version doesn't have". The pinned jobs test the published app with the CLI release it pins, exactly as on a user's machine. Preflight instead takes the candidate's distribution run ID and runs only the tree app jobs, since the pinned release isn't public yet. The pinned jobs check out the same immutable release revision used to select the installer and use its Install Lab plan and app step/report expectations, not the current tree's action names or workspace tokens. The judge and mutation checks use that trusted checkout too, never a plan or oracle from collected evidence. All scientific output checks and clean-machine/state checks remain those of the current tree. Locally, select such a checkout with lab.py --app-contract <release-checkout> run ... (or judge ... / mutate ...); the checkout must contain scripts/installlab/gui_oracle.py and its gui/wgsextract-plan.json. Legacy app-only releases from WGSExtract/gui-for-cli (for example v0.4.4) have no version-bound Install Lab contract and are rejected during app-source resolution. Select a published release from WGSExtract/wgsextract-cli instead. A sabotaged run's evidence (--sabotage --no-judge) is judged as a negative control: lab.py judge passes it only if it fails on the checks the sabotage breaks.

The linux jobs' container installs its prerequisites (curl, ca-certificates and, for the app, sudo, Xvfb and the rest) with .github/actions/apt-install/apt-install.sh: official Ubuntu mirrors in turn, with bounded time. The lab bind-mounts an apt cache under out/installlab-apt/, split by Ubuntu image, architecture and package set. It can install prerequisites from cached lists and packages after verifying them against Ubuntu's signed archive metadata. It saves the cache after prerequisite setup; the installer under test cannot write to the saved copy. If neither the mirrors nor the cache can supply the prerequisites, the lab reports Upstream package mirror unreachable. The app's own .deb install still uses the normal guest apt and can need the network for other dependencies.

The hosted Linux jobs restore that cache and refresh it weekly from main; PR jobs never save it. Local GUI builds and Windows VM media preparation also use a host cache for their container prerequisites. To test today's mirrors without reading or writing that cache, add --no-apt-cache to lab.py run, prepare or selftest, or set no_apt_cache=true on a manual Install Lab run.

To try an app fix before releasing it, run the GUI distribution workflow (gui-distribution.yml) on its branch, then this workflow on the same commit: gh workflow run install_lab.yml --ref <branch> -f app_run=<run id>. Only successful first-party GUI distribution runs from push, schedule or manual events are accepted; PR runs and mismatched commits are rejected before any app job starts. To test an unmerged build, dispatch both workflows on that branch, not on main: unmerged code must never execute in main's cache context. The app jobs test that run's builds, and macos-app checks out the validated immutable commit. Release sources likewise resolve a published release's tag to its immutable commit (including annotated tags). App jobs restore Pixi caches only; they never publish them. The latest app release is this repository's latest release once it carries the app; until then, the latest of the former gui-for-cli repository.

Runners aren't new machines, so each run first makes its runner look like one, and the oracle still checks the result:

  • macOS: lab.py moves Homebrew and the JDKs aside and turns Gatekeeper on (the runner image has it off). The oracle fails a macOS run whose recorded Gatekeeper status isn't on, or whose tool survey finds pixi, samtools, bcftools, Java, Homebrew or conda, including a Pixi in ~/.pixi, where installers look for it.
  • The macOS app: an app needs a desktop session, and a runner can't sign a new account in (that takes the login window or a reboot), so the app runs as the account signed in at the runner's console. Launch Services gives it launchd's environment, as on any Mac, and the run is judged against that account's own baseline like any other. lab.py runs on a tool-cache Python, not Homebrew's, and Pixi, which the oracle needs, is installed only after the scenario, so nothing the lab uses is in that account's home while the app runs.
  • Windows: as above (deprovision-runner.ps1).
  • The Windows app: Lab User needs a signed-in desktop. A runner can't reboot into autologon, but it is Windows Server, which hosts a second desktop session, so Lab User (added to Remote Desktop Users, still a standard user) signs in over Remote Desktop to 127.0.0.2 (the client refuses 127.0.0.1, its own console). The runner image doesn't let the client use a saved password, so vm/windows/rdp-sign-in.ps1 types it into the client's credentials dialog with UI Automation, as a person would. Their first sign-in settles for three minutes before the baseline. If the runner lacks the WebView2 runtime, which every Windows 11 PC has, the pinned installer adds it. The runner's screen, showing Lab User's full-screen desktop, is saved once a minute in screens/.

Noise lists for runners (noise/host*.txt, noise/windows-host*.txt) come from --mode control runs on the runners themselves. An app's control run opens a stand-in app for as long as the app's window is open: TextEdit on macOS (the app is native, with editable text), a minimal WebKitGTK window on Linux and a minimal WebView2 window on Windows. The stand-in must report that it loaded, or the control run fails: a control whose stand-in never opened measures less than an app run causes, and would make real leftovers look like noise.
