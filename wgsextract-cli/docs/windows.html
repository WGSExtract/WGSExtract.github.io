WGS Extract CLI / CLI Docs / Windows

Windows

WGS Extract CLI runs natively on Windows the same way it runs on macOS and Linux: Pixi installs Python, the CLI and the external tools into the project's environment, and the CLI runs every tool from there. There is no WSL, MSYS2 or other Unix layer to set up, and tools read and write your Windows files directly.

Installing#

Run install_windows.bat from PowerShell or a command prompt, in the folder you downloaded the CLI to (or alone, in an empty folder: it then downloads the latest release there first). It installs Pixi for your user if it is missing, installs the Pixi environment and checks the tools with wgsextract deps check.

If Pixi was installed for the first time, close and reopen PowerShell or the command prompt before running pixi, so the new window picks up the updated user PATH.

.\install_windows.bat
pixi run wgsextract --help

The folder can be anywhere: another drive (D:\WGSE), or a path with spaces, parentheses or & in it. Pixi goes in %USERPROFILE%\.pixi, or under PIXI_HOME if you have set Pixi's own PIXI_HOME; the installers and the CLI look for it there even when it is not on PATH.

uninstall_windows.bat removes the environments and clears old runtime settings from config.toml; --remove-prerequisites also removes Pixi. Installers before this one set up MSYS2 (by default at C:\msys64) for their tools. Nothing uses it now; uninstall_windows.bat --remove-msys2 removes it if you have no other use for it.

When Windows blocks an installed tool#

Smart App Control or App Control for Business (WDAC) can block an executable even though Pixi installed it. The full wgsextract deps check starts each tool to check that it runs; deps check --tool NAME only locates it. If Windows blocks the wgsextract.exe launcher itself, run the check through Python with pixi run python -m wgsextract_cli deps check.

Use a signed build that your policy allows or ask your administrator for an approved build. Paired alignment uses samtools markdup when Windows blocks the optional samblaster. If Windows blocks BWA-MEM2's CPU-specific executable, you can explicitly select --aligner bwa if BWA is allowed. BWA can produce different alignment records from BWA-MEM2.

Work folders and Microsoft Defender#

On Windows 11, if your security policy allows it, prefer a trusted Dev Drive with Defender performance mode for WGS Extract's working files. Point --tmp-dir and --outdir at dedicated folders on that drive. Create the temp folder before running the command. Keep real-time protection on. Check Windows Security → Virus & threat protection → Manage settings → See volumes to confirm that performance mode is on for the drive. An ordinary ReFS volume is not necessarily a Dev Drive.

Microsoft's Dev Drive setup guide says that Dev Drive “builds on ReFS technology to employ targeted file system optimizations”. The Defender performance mode guide explains that it works by “deferring security scans until after the open file operation has completed”. Files are still scanned, but malware may be detected later than with synchronous scanning. Performance mode does not change Defender scanning on your NTFS system drive.

If you cannot use a Dev Drive, leave NTFS scanning on by default. An administrator can make a folder exclusion if measurement shows a worthwhile benefit and policy permits it. A folder exclusion skips Defender Antivirus scans, so malware there may go undetected. If you use this option, limit it to one dedicated scratch folder, use only trusted inputs there, and remove the exclusion as soon as the job finishes. Never exclude a whole drive, Downloads, a shared folder or the tool installation. WGS Extract never changes Defender settings.

One Windows benchmark#

In November 2026 we ran WGS Extract 0.8.9 on native Windows 11 (build 26300.9974, Ryzen 9 9900X3D, 62 GiB RAM) with a 12-core, 24 GiB job limit. We tested three setups:

  • A: NTFS, standard real-time scanning.
  • B: The same NTFS folder, with a temporary folder exclusion.
  • C: A trusted ReFS Dev Drive in a VHDX on the same SSD, with Defender performance mode.

We ran A/B/C and then C/B/A. Each run copied 9.65 GB from common sources on C: and D: to the test volume, a separate timing. With inputs, work files and outputs on that volume, we aligned 5 million HG002 pairs against hs38 using the default CPU BWA, called SNPs in the first 5 Mb of chr20 from a separate small BAM, and annotated the chr20 GIAB truth VCF against offline ClinVar. Every run started with fresh copies and outputs. We repeated the ClinVar timings with an empty normalization cache on the test volume for every run. We did not flush the Windows file cache.

Qualifying a whole genome on your own PC#

The 30x qualification script runs public GIAB HG002 data through chr22 extraction, BWA realignment and SNP/indel calling, then repeats processing on the whole genome. Before calling variants it declares HG002's known Male sex with sample set --input <aligned.bam> --sex Male in both phases and uses GRCh38 ploidy; the chr22 slice cannot infer sex from coverage. Use native x64 Windows and PowerShell 7.2 or newer (pwsh). Install the CLI as above first; the script checks dependencies and does not install or upgrade software.

Allow 400 GiB of free space on a local SSD and 48 GiB RAM minimum (64 GiB recommended, with 40 GiB available). This conservative disk budget allows for a 100+ GB input, reference/indexes, both sets of outputs and temporary files. Existing files from the same run count toward the budget on resume. In the earlier qualification, chr22 extraction took 46 seconds and used 4.2 GiB of system memory. That measures extraction only, not chr22 processing. The older full-genome baseline took about 14.4 hours on 16 vCPUs and peaked at 35.8 GiB; allow longer for downloads, indexing or a slower PC.

From your installed CLI folder, use a dedicated workspace on your chosen drive:

pwsh -NoProfile -File .\scripts\qualify_30x.ps1 -Root D:\wgse-30x -DryRun
pwsh -NoProfile -File .\scripts\qualify_30x.ps1 -Root D:\wgse-30x -Download

-Download permits only the documented public inputs: HG002 BAM/BAI from Google's brain-genomics-public bucket, the reference bootstrap archive from GitHub releases, and hs38 from the CLI reference catalog's public mirrors. The script prints these sources before work starts. Without -Download, missing preparation steps stop with instructions to opt in. Processing runs locally; the script does not upload data or send results anywhere.

-Root defaults to $HOME\wgse-30x; -Threads defaults to your logical CPU count. Use -InstallDir if you run outside your installed CLI folder. Select -Phase prepare, -Phase slice or -Phase full to run in stages; the default all runs them in order and requires a passing slice before full processing. Preparation downloads the whole BAM before making the slice. Close other workloads, keep the PC awake, and leave the PowerShell window open. After interruption, repeat the same command: completed steps remain skipped and curl resumes partial downloads. The CLI's realignment checkpoints resume an interrupted realignment.

To select a version, install the desired release with install_windows.bat in that release's folder first. -Version 0.9.0 checks the installed version; -Commit <40-character SHA> checks an existing Git checkout (and requires Git). Neither option downloads source or changes your installation. Keep the same script, installation, root and thread count when resuming; choose a fresh root to compare versions. Do not edit the workspace's generated config.toml or delete completed outputs.

Attach evidence\summary.md and evidence.zip from the workspace to #1024 (Windows 30x qualification). The summary includes wall times, sampled process-tree and whole-system memory peaks, alignment/VCF record counts, CPU/RAM and disk details. The zip contains logs, installation manifests and summaries, including failed steps. Each retry keeps its own logs and measurements under evidence\attempts; summary wall times sum all attempts and peaks take the maximum, so checkpoint reuse does not hide earlier work. Time between retries is excluded. It excludes BAM/VCF/FASTQ files. Review it for local paths and machine details before posting. Failures print the evidence location and return a nonzero exit code.

Where the tools come from#

Bioconda publishes no Windows packages, so WGS Extract builds its own: samtools, bcftools and htslib's bgzip, tabix and htsfile, BWA, bwa-mem2, minimap2, fastp and samblaster are compiled from their upstream releases with MinGW-w64 (UCRT), linked statically so each .exe needs only Windows' own DLLs, and packaged as conda packages that pixi.toml pins by URL and SHA-256. The recipes, patches and build instructions are in packaging/windows/README.md.

Java tools (GATK, FastQC, Haplogrep 3, haplocheck) come from conda-forge, Bioconda's platform-independent packages and PyPI as on the other platforms. Y-DNA analysis is native Yleaf-derived Python code; its checksum-pinned tables download on demand into the configured reference library, not the app bundle. The GATK environment also includes the native Windows GKL sidecar described below. haplocheck 1.3.3 can't load its HTML report template on Windows, so lineage mt-haplogroup --contamination writes only its text reports there and warns haplocheck_no_html. deps check lists what isn't available on Windows (for example Ensembl VEP, DeepVariant, Delly and FreeBayes).

Variant effect prediction runs on Windows with vep-rs, the default VEP engine everywhere: install its environment (pixi install --locked -e vep-rs), build its cache with wgsextract vep download, and annotate with wgsextract vep run. Ensembl VEP (--engine ensembl) isn't available on Windows. See VEP engines.

Local paths passed to Java tools use native Windows separators, including references, inputs, outputs, interval files and temporary directories. You can still enter paths such as R:/data/sample.bam; the CLI converts them before launching Java so GATK does not mistake R: for a URI provider. Explicit URIs are preserved.

Commands needing pyBigWig (bigWig-backed vcf phylop, vcf gerp and their reference downloads), Ensembl VEP (--engine ensembl; the default vep-rs works), DeepVariant, Delly, FreeBayes, Cyrius, SMNCopyNumberCaller, T1K, ExpansionHunter, VerifyBamID2 (qc contamination), somalier (qc relate) or PacBio tools are not supported on Windows. They fail before processing inputs or creating output folders, naming the unavailable tool. PhyloP TSV/VCF resources remain supported. Parabricks --gpu modes require Linux with an NVIDIA GPU.

PharmCAT on native Windows#

vcf pharmcat runs natively. The pharmcat Pixi environment supplies Python, conda-forge's Java 17 and the same Windows Tools bcftools/htslib builds as the default environment; PharmCAT itself is its pipeline release, extracted as on the other platforms (see vcf pharmcat). The CLI runs the pipeline's Python script and PharmCAT's java -jar through that environment, with no shell wrappers, so paths with spaces work. Install the runtime and check it with:

pixi install --locked -e pharmcat
pixi run wgsextract deps check --tool pharmcat_python

typing cyp2d6 and typing hla don't run on Windows, so without --outside-call files made elsewhere the run logs "CYP2D6 not called" and the report has no CYP2D6 or HLA-A/HLA-B calls. The PharmCAT parity CI checks that a GIAB HG002 VCF gives the same phenotype.json on Windows and Linux, except for its timestamp.

GATK on native Windows#

Standard-read HaplotypeCaller uses native OpenMP AVX PairHMM and AVX2 Smith-Waterman on AVX2-capable x64 Windows CPUs. The URL/SHA-pinned GKL 0.8.11 sidecar supplies four static DLLs alongside unmodified GATK 4.6.2.0 and Java 17. No WSL, MSYS2 installation, extra OpenMP runtime or manual Java classpath is needed.

install_windows.bat prepares both the default and GATK environments. For a manual setup, install the locked GATK environment explicitly before calling; the CLI checks presence and does not install it for you:

pixi install --locked -e gatk
pixi run wgsextract vcf gatk --input "C:\genomes\sample.bam" --ref "C:\refs\reference.fa" --region chr20 --threads 4 --memory 512M --outdir "C:\results\gatk"

The log should include:

Intel GKL Utils loaded
Using the OpenMP multi-threaded AVX-accelerated native PairHMM implementation
Using AVX accelerated SmithWaterman implementation

If the sidecar or pinned GATK jar is missing or obsolete, re-run install_windows.bat or pixi install --locked -e gatk. A missing native-load message, Java Smith-Waterman, or LOGLESS_CACHING fallback means the accelerated path is not in use. Check CPU support and the preceding GKL load diagnostics; fallback results can differ numerically from Linux.

The matched-ISA public HG00096 chr20 validation produced 127,210 records byte-identical across all eight calls, including every numeric, depth, genotype and FILTER field. With one warmup and three measured repetitions on matched 4-vCPU/16-GiB AMD EPYC 7763 VMs, medians were 1420.883 s on Windows and 1450.530 s on Linux (0.97956×). This is a specific standard-read/AVX2 result, not a guarantee for every dataset or CPU: AVX-512 is not enabled in the Windows sidecar, VCF headers and compressed bytes are not parity targets, and the CLI retains its numerical/performance warning. Compression and Ultima's flow-likelihood engine still use Java.

The GATK native Windows smoke CI consumes the installed, locked sidecar without rebuilding it or downloading genome data. It checks native loading, all fields of a tiny synthetic call against the stock Linux AVX2 golden, and native PairHMM/Smith-Waterman unit parity. Java fallback or changed VCF fields fail the gate; this does not replace the full-chr20 release gate.

The CLI launches Java with the sidecar/GATK classpath. Launcher --java-options remain JVM options, including scatter workers' heap and CPU limits; Linux/macOS launching and default caller arguments are unchanged.

Cancelling commands#

Windows cleanup terminates the registered launcher and its descendants together, including Java workers. It does not use Ctrl+Break, which Java can ignore. Native GATK single-shard subprocess and stderr waits check back with Python every half second, so foreground keyboard Ctrl+C does not wait for Java to finish before the CLI's signal handler can terminate the process tree. The half-second interval is not a guarantee on total cleanup time; Windows must also stop the descendants.

Short read alignment#

The default --aligner auto uses native bwa-mem2 when the reference already has its index and the index fits in memory. Otherwise it uses BWA. To prepare the bwa-mem2 index for your reference, run:

pixi run wgsextract ref index --aligner bwa-mem2 --ref C:\path\to\reference.fa

Native full-human index construction is supported with the pinned windows-tools-8 bwa-mem2 2.3-wgse_2 package. It fixes the large-transfer and 64-bit-offset corruption tracked in #264. All five index files for the 3,217,346,917-base GRCh38 reference were verified byte-identical to a Linux-built index. Building it needs roughly 80 GB of RAM; the CLI checks its build-memory estimate before starting. Existing indexes and the verified published hs38DH index download remain supported. ref index, alignment and realignment prepare missing FASTA length metadata automatically with samtools. Direct build preflight refuses missing or incomplete length metadata rather than assuming the build needs no memory; complete BWA .ann metadata can also supply the length.

The human bwa-mem2 index occupies about 17 GB of RAM, with additional memory needed for reads, sorting and Windows. The CLI checks the reference's memory estimate before choosing it. --aligner bwa selects the lower-memory option; --aligner bwa-mem2 selects bwa-mem2 explicitly.

wgse-bwa and optional NVIDIA CUDA#

The default Pixi environment on Windows x86-64 includes wgse-bwa from windows-tools-12. When BWA is selected, align and realign use the validated wgse-bwa.exe from the environment. No manual PATH or configuration changes are needed. Run pixi run wgsextract deps check --tool wgse-bwa to see the installed path. To use a different build, set an explicit path in config.toml:

wgse_bwa_path = 'C:\tools\wgse-bwa.exe'

An explicit path takes precedence over PATH. If it is unusable, the CLI warns and continues with stock BWA. Stock BWA is also used when no native build is found or with --native-aligners off.

On Windows x86-64, align and realign use CUDA automatically when wgse-bwa reports CUDA available and the alignment fits. CUDA needs a supported NVIDIA GPU and driver, not Docker, WSL or a CUDA Toolkit installation. It is distinct from the Linux-only --gpu Parabricks option. Windows can charge CUDA allocations to system commit (RAM plus page file) even when physical RAM is available. Preflight can reduce sort memory to fit both budgets; it uses the CPU if either check fails or available commit cannot be measured.

Pass --no-prefer-native-gpu to force CPU, or set prefer_native_gpu = false in config.toml for future runs. --prefer-native-gpu overrides that setting for one run, but never bypasses either Windows memory check.

With windows-tools-12 and Segment Heap enabled, wgsextract align on 5 million HG002 read pairs took 100 s with automatic CUDA versus 189 s with forced CPU (Ryzen 9 9900X3D, RTX 5080, 16 threads). Both runs produced identical decoded BAM records: 99.73% mapped and 97.85% properly paired.

On the same host, wgsextract realign on a local HG002 BAM subset (19.47 million input records, below full-genome 30× coverage) took 154 s with automatic CUDA and 344 s with forced CPU. Both runs used windows-tools-12, 16 threads, and fresh output directories. Both produced identical decoded BAM records: 99.81% mapped and 99.12% properly paired.

wgse-minimap2 for long reads#

The default Pixi environment on Windows x86-64 includes wgse-minimap2 from windows-tools-13. With native_aligners = "auto", align and realign use it instead of stock minimap2 for long reads. No manual PATH or configuration changes are needed. Run pixi run wgsextract deps check --tool wgse-minimap2 to see the installed path.

The map-ont, map-hifi and map-pb presets can run their gap fills on CUDA. Check the driver, device and device-memory preflight with wgse-minimap2 capabilities --json. The CLI also checks available RAM and Windows commit; it uses the native CPU backend if CUDA is unavailable, the memory checks fail, or you pass --no-prefer-native-gpu (or set prefer_native_gpu = false). A failed or timed-out GPU batch is recomputed on the CPU. --native-aligners off uses stock minimap2. Short reads stay on the CPU. The CPU backend does not need the NVIDIA driver or CUDA Toolkit.

On Seraph (Ryzen 9 9900X3D, RTX 5080), eight-thread realign to hs38 produced the same 118,687 decoded records with upstream minimap2 2.31 and automatic CUDA; both retained all 86,935 primary read payloads including MM/ML. The test read 23 windows of 1.5 Mb from the public HG002 ONT CRAM (chr1–22 and X, BED start 20,000,000) and wrote indexed CRAMs with --chunk-size 512M --memory 256M. Outputs and temporary files were on a trusted ReFS Dev Drive with the Defender filter attached.

Upgrading from a WSL or MSYS2 setup#

Older Windows installs used a tool_runtime setting (windows, pacman, wsl, cygwin or msys2) and pacman_ucrt64_bin. The CLI now ignores these settings, and drops them from config.toml the next time it saves it. Rerun install_windows.bat to get the native tools.

Release test on Windows 11 (v0.8.5)#

v0.8.5 was tested end to end on a fresh Azure Windows 11 Pro 25H2 VM (build 26200, Standard_D16ads_v5: 16 vCPUs, 64 GiB RAM, local NVMe D:) in #554, as a standard user with no tools preinstalled.

  • CLI install. The release's source zip and install_windows.bat took 123 s and exited 0.
  • CLI smoke test. 49 steps covering every command family on the small hg19-mini HG00096 data: info, extract, microarray, lineage, bam, qc, align, realign, vcf snp/indel/gatk/annotate/filter/table, report and report-issue. All behaved as expected, including the documented refusals of DeepVariant, FreeBayes and VEP on native Windows. Only lineage y-haplogroup and lineage y-str failed, as they do on Linux: the mini reference's chrY is a 500 kb slice renumbered from position 1, so the hg19 positions these tools look up don't line up with it.
  • Server mode. wgsextract serve answered /v1/health, refused requests without the token (401) and paths outside --allow (403), and ran an info job to completion.
  • Desktop app. The Install Lab installed the v0.8.5 app, ran first-run setup by itself (87 s) and passed all 15 planned actions on the mini genome: mtDNA haplogroup H16a1 as published, 88.3% recall of the published SNPs in its 1 Mb chr20 slice, 93.6% GATK precision in the first 200 kb of that slice and 99.81% of reads mapped by align. The Report a problem preview was redacted. Uninstalling asked whether to delete the workspace: answering Yes removed it, answering No kept it, and both removed the runtime and app data. The installer is unsigned, as documented. Each run passed 24 of 26 checks. In both runs one failure was pixi, already installed by the CLI test. The other was the uninstall check's list of files left behind: in the Yes run, Store-app folders that come with the Azure image; in the No run, the workspace it kept on purpose, plus App Installer and Credential Manager files that Windows wrote (the app has no code that uses Credential Manager).
  • Auto-update. The v0.6.6 app found v0.8.5 through the bridge release in gui-for-cli-outdated, verified its signature, installed it and relaunched as 0.8.5 within about 30 s. A silent uninstall (/S) kept the workspace.
  • 30x genome. HG002 NovaSeq PCR-free 30x GRCh38 BAM (GIAB), realigned to hs38 with the default settings (16 threads):

realign used bwa, because there is no bwa-mem2 index for hs38. Unpacking the reads took 23 min and building the BWA index 58 min; aligning and sorting took the remaining 7 h 10 min. 99.70% of the reads mapped and 97.76% were properly paired.

v0.8.5 called vcf snp and vcf indel in a single bcftools stream on one core. After v0.8.5, #560 made them call contigs in parallel by default when --threads is above 1. The "Expected Wait" warning said 21 minutes for each (#583, fixed on main by #586).

Bugs found, fixed on main after v0.8.5:

  • #558: a config.toml saved with a UTF-8 byte-order mark (as Windows PowerShell 5's Set-Content -Encoding utf8 writes it) was rejected as invalid TOML.
  • #568: serve printed ConnectionResetError tracebacks when a client dropped a keep-alive connection.
  • #571: the report-issue preview redacted generic file names such as result and tool names such as gatk as if they were sample names.
  • #572: the Install Lab did not find the uninstaller's workspace question on Windows 11 25H2, which shows it as a child window of the wizard.
  • #586: the vcf snp and vcf indel "Expected Wait" was divided by the thread count even when calling ran in one stream.

Windows ARM64

Native Windows ARM64 (win-arm64) is being qualified separately in packaging/windows-arm64. It is not yet enabled in the locked installer. The installer refuses ARM64 before downloads or environment creation, including when invoked from an x64 terminal under Prism. Do not substitute x64 emulation, ARM64EC, WSL or x86 containers. GATK/GKL and DeepVariant are unavailable on this architecture in phase 1; they fail before caller execution instead of silently choosing Java kernels.
