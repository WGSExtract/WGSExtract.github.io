Developer setup

Set up a machine#

macOS or Linux:

git clone https://github.com/WGSExtract/wgsextract-cli.git
cd wgsextract-cli
./scripts/dev_setup.sh

Windows (PowerShell; no WSL or MSYS2 needed):

git clone https://github.com/WGSExtract/wgsextract-cli.git
cd wgsextract-cli
powershell -ExecutionPolicy Bypass -File scripts\dev_setup.ps1

The script needs only git (and the Xcode Command Line Tools on macOS). It:

  1. Installs Pixi for your user if it's missing. Pixi provides Python and every bioinformatics tool.
  2. Installs the default and dev Pixi environments exactly as locked in pixi.lock. The first run downloads a few GB.
  3. Installs just with pixi global install just if it's missing.
  4. Installs the pre-commit hooks (ruff, shellcheck, gitleaks, whitespace).
  5. Runs wgsextract --version, wgsextract deps check and the quick smoke tests.
  6. Lists anything else worth having: a git identity, the GitHub CLI (gh), and an AI coding agent.

Pixi 0.82.0 or newer is required (declared in pixi.toml, kept in agreement with CI). Setup checks existing installations before loading the manifest; it never updates them automatically. If yours is older, run pixi self-update and rerun setup.

deps check marks tools in optional Pixi environments (GATK, VEP, DeepVariant, ...) as missing. That's expected: install one when you need it with the pixi install command deps check prints. When the script installs Pixi or just, open a new terminal before using them (or add ~/.pixi/bin, %USERPROFILE%\.pixi\bin on Windows, to PATH). Rerun the script at any time; just setup does the same once just is installed. --skip-tests (-SkipTests on Windows) skips the smoke tests.

Pixi environments#

Optional tools live in separate environments. From a source checkout or the installed wgsextract-cli/app/, run pixi install --locked -e <environment> explicitly before use. Feature commands never install dependencies: missing tools name the exact install command, including the app manifest path so it works from any directory. Installed tools outside PATH launch with pixi run --no-install -e <environment>. You may also run a whole command inside its installed environment.

Other optional environments are documented with their features: hardware, ONT, MultiQC, relatedness, imputation and ACMG. Cyrius permits noncommercial use only, no distribution/modification, and is not bundled.

On macOS, bio-tools environments and the separate pharmcat environment use Apple's Accelerate BLAS so bcftools does not load LLVM OpenMP through GSL. Before starting workers, pytest removes only current-user, unwritten OpenMP registration files whose PID is absent. For other tools and manual cleanup, see OpenMP troubleshooting.

Benchmarking on macOS#

Setup creates .metadata_never_index in out/, scratch/ and tmp/ (safe to rerun). For existing indexed trees, also add those folders or the repository to System Settings → Spotlight → Search Privacy. Keep heavy benchmark inputs and outputs out of Photos libraries and Spotlight-indexed folders. Check volume indexing with mdutil -s / and thermal pressure with pmset -g therm before timing; wait for indexing and throttling to settle.

Make a change#

git switch -c my-change
# edit code
just run info --input sample.bam   # try the CLI from this checkout
just check                         # format, lint, typecheck, test
just ci                            # what CI runs; do this before opening a PR
git commit -am "Describe the change"
gh pr create --fill

just lists every recipe. Each wraps a pixi run task, so pixi run test and friends work without just.

With just, just run <args> runs the CLI. just test, lint, fmt, typecheck and check (all four) are aliases; just ci runs lint/type checks, regular tests and generated small/full-genome integration without formatting, keeping pytest scratch under out/.

PR/main CI is bounded and cancels superseded runs. A separate lint-only environment runs Ruff, workflows and strict mypy without reference downloads; genomic jobs cache public hs38. A CI policy test keeps the mypy exemption baseline for wgsextract_cli.core empty: don't add overrides that match it or relax the global strict configuration in pyproject.toml. Action updates retain full commit SHAs and version comments from allow-listed sources, not a duplicate validator SHA table. See CI routing.

The weekly Pixi refresh resolves within manifest pins, restores declared archive digests and validates the lock candidate with a read-only token. It force-pushes validated changes to fixed automation/pixi-refresh and opens/updates one PR; no change opens none and closes a superseded PR. CI waits for maintainer approval (“Approve workflows to run” or the PR-body command), then runs normal checks. It never auto-merges dependencies. Numerical-tool updates still need public small/full-genome byte-parity checks.

Real-data tests use pytest options or config:

pixi run pytest tests/test_smoke_real_basics.py \
  --real-input /data/HG002.cram --real-ref /data/reference/hs38.fa --real-region chr20

Options include --real-input, --real-ref, --real-vcf, --real-region, --real-targets, --real-fastq-r1/--real-fastq-r2, --fake-data and --full-data (see tests/conftest.py). Or set real_genome_test_path and real_genome_tests_enabled = true in [dev] at the end of config.toml. download_cache = true caches downloads under $XDG_CACHE_HOME/wgsextract/downloads (default ~/.cache/wgsextract/downloads), pruned after download_cache_ttl_seconds (default one week). Former top-level settings, including dev_download_cache and dev_download_cache_ttl_seconds, now fail with their [dev] replacement.

wgsextract qc fake-data generates BAM/CRAM/VCF/FASTQ for tests and reports; see testing workflows.

Filesystem paths#

Use pathlib.Path. Shared helpers accept strings/os.PathLike[str] (core.paths.PathInput); keep Paths during manipulation, converting at string-based CLI/config/tool-wrapper/public-return boundaries. Use input_stem/fasta_prefix for compound genomic extensions and append_suffix for .vcf.gz.tbi/.cram.crai sidecars. absolute_path normalizes .. without following symlinks; Path.resolve() compares real targets. Wrapper commands and samtools out##idx##index arguments stay strings; do not convert native Windows paths to POSIX spelling.

The desktop app#

The WGS Extract desktop app is in gui/. It has its own toolchain (uv, Node and Rust) and setup; see gui/devdocs/developer_setup.md. From the repository root:

just gui-setup        # install uv, Node and Rust if missing, and the app's locked dependencies
just gui-run          # build and serve the Web UI in a browser
just gui-tauri        # run the desktop app in dev mode
just gui-ci           # the app's lint and tests, as GUI CI runs them
just gui-package      # build this platform's installers into gui/out/release/tauri

Root ruff, mypy and pytest skip gui/; changes there run GUI CI instead of the CLI's CI, and changes elsewhere don't run GUI CI.

When you add or rename a command:

  • Give a new top-level command a tier (core, setup or advanced) and a short summary in COMMAND_TIERS in src/wgsextract_cli/commands/registry.py.
  • Give every runnable command an example and an outputs line in its command group's module under src/wgsextract_cli/commands/_help_catalog/.
  • Register its parser in src/wgsextract_cli/cli/registration/, keeping execution imports inside handlers. cli/_lazy.py defers loading command implementations until execution; help must not import scientific libraries. Add its required/optional external tools and runtime to NEEDS in the same registration module.
  • Run pixi run site-build to preview the automatically generated command reference and the cards on the site's CLI page.

The compact help index is not committed. just regen and developer setup warm it, and the first help --all --json after pixi install also builds it if needed. Managed installs keep it in the installation's writable cache so uninstall removes it; other installs use the platform's per-user cache. The cache expires when the package version or parser and registry sources change.

tests/test_help_index.py checks cache behavior; tests/test_site_references.py builds the site and checks the published references.

Keep command-specific messages with the code that uses them. If registration and implementation both need the same strings, use the group's lightweight module under src/wgsextract_cli/commands/_messages/.

Benchmark fixture ploidy#

The benchmark timing workload explicitly calls SNPs, indels and microarray sites with uniform diploid ploidy for generated data and the real mini-genome archive. Scaled, regional and low-depth fixtures cannot reliably infer sex; the benchmark is not a karyotype or genotype-accuracy validation. This override is passed only to those child commands and does not change the sample's declared/observed sex or weaken normal Unknown-sex refusal. Full-reference real-1x/real-30x runs retain build-specific ploidy.

VCF API specifications#

For any typed command, re-export its Params from the API group's module under src/wgsextract_cli/api/_exports/. This keeps api.SomeParams available to both Python callers and type checkers.

api/vcf.py remains the public import and dispatch facade. Its parameter declarations live in api/vcf_specs/: shared field helpers, calling, file operations and annotations. Update the responsible specification module when adding fields, and retain its explicit facade export. Parameter types keep their physical source modules for introspection; facade aliases keep pre-split pickle lookups working. Facade declaration order keeps the generated API reference stable without duplicating parameter descriptions beside their handlers.

Generated references and parallel PRs#

Run just regen (or pixi run python scripts/regen.py) after changing CLI/API help. It warms the compact discovery cache. The site build generates the public references and CLI cards separately; they are not committed. If a branch still tracks a retired generated reference, just regen-resolve stages its deletion after you resolve source conflicts. In site_src/cli.md, keep the <!-- command cards --> placeholder, not the old generated cards. It also generates the public sample-workspace JSON Schema from the output types in core/sample_document.py. Output types use TypedDict, dataclasses and Annotated constraints; core/output_schema.py rejects unsupported annotations. Its supported subset is TypedDict, dataclasses, Literal, Annotated, primitives, unions, lists and string-keyed dicts; Enum, tuple and Mapping fields are not yet supported. Dataclasses describe complete dataclasses.asdict-style projections: every field, including nullable/defaulted and init=False fields, is required in the output. ClassVar, InitVar and KW_ONLY pseudo-fields are excluded before resolving annotations, including postponed Python 3.10 hints. Real fields resolve in their declaring module and class/MRO namespaces. Generation never constructs instances or calls default factories, and does not infer field omission or custom to_dict behavior. Use an explicit serialized model when a custom writer changes the field projection. For recursive fields on Python 3.10, postpone the whole annotation (children: "list[Tree]"), not only the element (list["Tree"]): that version's get_type_hints leaves partial PEP 585 forward references unresolved. Definition names and extension-key policies are supplied explicitly to each generation call, never registered globally. Workspace reads retain unrecognised TOML data in WorkspaceState; new fact/override/output records are written through the typed document models rather than casting unvalidated loaded data to those types. Keep these committed: readers, release archives and freshness tests need them without running Python.

The generators run by scripts/regen.py write LF on every platform, and .gitattributes keeps their fully generated files at LF on checkout. The setup scripts configure the merge=generated driver assigned to those files. For an existing checkout, configure it once:

git config merge.generated.name "Keep generated references until regeneration"
git config merge.generated.driver true

This is an ours-style placeholder, not an automatic generator: a merge driver runs before all source files are merged, so regeneration there could silently use inconsistent sources. Merge locally with git merge --no-commit origin/main, resolve and stage source conflicts, then run just regen-resolve (or pixi run python scripts/regen.py --resolve). It regenerates all references from the combined sources and stages them; it refuses unresolved source conflicts. Review the diff, run the freshness tests and commit the merge. The same command resolves generated-file conflicts without the driver installed. Site command cards share a file with hand-written content, so resolve any site_src/cli.md conflict as a source conflict before regenerating.

GitHub does not execute custom merge drivers. If it reports generated-file conflicts, use the local workflow above and push the resolution; don't choose one side in GitHub's conflict editor or expect its Update branch button to regenerate. No freshness checks are bypassed. Re-run regeneration after every merge, even if Git reported no conflicts.

Help-size tests gate each command's JSON (12,000 characters maximum) and the average (3,000), rather than a global total that every new command changes. The JSON and text-index totals are reported as test properties, not gates; the text index's existing per-line width check still catches bloated entries. The compact discovery index has a separate 60,000-character ceiling and a 20,000-token approximation ceiling (word pieces plus JSON punctuation, without downloading a tokenizer model). Agents read this index first, then wgsextract help <command> --json for full schemas.

The CLI help document is not the server protocol. HTTP discovery uses GET /v1/ops (summaries) then GET /v1/ops/{op} (full Params schema); MCP tools/list must include its protocol-required inputSchema. Both use the same typed Params definitions as per-command CLI help, not the compact help index, so their invocation schemas remain complete.

Server response envelopes are writer-used TypedDicts in server/transport.py. scripts/gen_server_contracts.py --check checks the committed response JSON Schema bundle and result/report writer types. OpenAPI 3.1 and the GUI transport types are not committed. CLI developer setup builds OpenAPI under out/contracts/ and just regen rebuilds both. The GUI build regenerates the transport declarations from OpenAPI before compiling. Wheel and sdist builds include the generated JSON under the CLI's schema assets. wgsextract serve --openapi generates the same default document without reading a file. Keep GUI presentation types and tolerant parsing adapters handwritten: they are not wire documents. Loaded result/report documents remain opaque in the server spec until their own writer models drive their public schemas; a schema ID check is not full document validation. Job projections still omit unset fields and compact results still omit provenance and empty values.

The three read-only lookup inputs live in server/lookup_inputs.py. Their frozen dataclasses and annotated constraints drive both HTTP/MCP discovery schemas and request validation, and lookup readers consume the resulting typed objects. This deliberately supports strings, booleans, integers and string arrays; unsupported annotations fail closed. Optional None defaults represent omitted fields internally: explicitly supplied JSON null is still rejected. This input-specific adapter keeps its constructor/omission semantics separate from the output-schema generator's complete dataclass projections.

The "Start from what you have" paths in both come from JOURNEYS in registry.py. To retire a command, don't delete it: add it to DEPRECATIONS there with its replacement and the next minor version as remove_in, and add it under ## Deprecated in a release-note fragment in docs/release-notes/unreleased/ (see its README). A deprecated command keeps working, warns deprecated_command when run, and is listed apart in the help and docs.

Running state and worker threads#

What a running command reads (its result, progress callback, cancel token, settings, where its tools' stdout goes) is on the ExecutionContext in core/execution_context.py, a ContextVar, so concurrent library calls keep apart. Reach it through current_result(), report(), checkpoint() and settings as before. Start worker threads with context_thread or ContextThreadPoolExecutor, which run them in the caller's context (a future's done-callbacks in the context they were added in); ruff rejects a bare threading.Thread or ThreadPoolExecutor in command code.

Issue-report package#

Issue-report internals live in core/issue_report/: redaction.py sanitizes text, runs.py loads local run records and discovers sensitive names, and environment.py collects installation diagnostics. The package initializer assembles reports and fits GitHub links; existing core.issue_report and api.support imports remain unchanged.

Python module size ratchet#

pixi run lint checks Python files under src/, tests/ and scripts/. New modules must stay at or below 800 physical lines. The desktop app (gui/) keeps its own policy; generated run outputs, scratch work and environments are not scanned.

Existing oversized files have fixed, reviewable ceilings in scripts/python_size_baseline.json; exceeding one fails with python_size_exceeded. Split responsibilities rather than add or raise an exemption. The initial ceilings include the bounded positive growth already present in pinned, open pre-policy PRs, so introducing the guard does not break those in-flight changes.

After shortening, splitting or deleting an outlier, run pixi run python scripts/check_python_size.py --refresh and commit the reduced baseline. Refresh only lowers/removes existing ceilings: it cannot grandfather a new megafile or increase a budget, and refuses to write while a new/growing module violates its ceiling. Removed files require their obsolete entries to be removed (python_size_stale_baseline); remove only that entry if other budgets still reserve in-flight work. Global refresh also removes exemptions for files reduced to 800 lines or less. Wait for reserved pre-policy versions to land before globally refreshing their budgets; individual ceilings may be edited downward in the meantime.

The same guard runs in pre-commit, PR/main lint and exact-head generic certification. It uses no network, extra dependencies or environment settings. For a separate checkout, use the run-specific --root/--baseline arguments.

Write tests#

A good test fails when the behaviour a user relies on breaks, and survives a refactor that keeps that behaviour.

Large DeepVariant, native-aligner, realign, personal-report and server/path suites are divided into focused test_<family>_<topic>.py modules. Their original test_<family>.py modules keep shared helpers and function-scoped fixtures, so existing imports and fixture behavior remain stable. New integration modules must retain their CI tier. Imported fixture aliases preserve autouse behavior too: report siblings retain served_lists so their gene-list downloads stay isolated behind the fake network. Modules using the shared out/fake_30x fixtures also retain a direct ensure_fake_data import: the loadgroup scheduler uses it to keep shared-data generation on one worker, even when the fixture itself is imported. The standalone test_server_shared_data.py guard names its source inputs with explicit repository-relative paths, so affected-test selection runs it whenever those consumer modules change. Its companion test_server_shared_data_routing.py checks that selection and runs when the worker guard changes; both guards stay outside the CI-only test list.

CI routing and workflow-policy tests also have focused landing/required-gate and readiness/path-filter siblings. Original modules retain shared helper owners; all siblings stay in the CI-only and documentation selections, so splitting tests never removes their checks from readiness or certification.

  • Extend a test module and reuse its fixtures first. Add a test file only for a new feature area.
  • Keep parametrization to about five cases per test. Use more only when the cases are the scientific contract, such as expected coordinates for each reference build.
  • Assert observable behaviour. That means:
    • output files and their content
    • exit codes 0/1/2/3
    • the result manifest
    • structured warnings
    • documented CLI and API behaviour
  • Use real tools on tiny data. Prefer the fake genomes and fixtures with real samtools and bcftools. The helpers live in tests/htslib_helpers.py, tests/fake_tools.py and tests/smoke_utils.py. For Pixi environments, the fake_pixi fixture runs a stand-in pixi with fake environments in a temporary folder. For disk-space preflights, tests/disk_volumes.Volumes puts folders on fake volumes with a set amount of free space and makes inputs look bigger than they are.
  • Mock only true boundaries: network, containers, GPU, very slow tools, the OS or platform, and the clock. Don't patch private helpers (_name) or the command runner to record what would have run.
  • Assert argv only where the flags are the scientific contract. For example, a caller's ploidy or a minimum mapping quality. Assert just those flags, with a # contract: <why> comment.
  • Check message codes or key facts, not whole prose. Help text is checked once, by the generated-help and doc tests.
  • Name the bug in each regression test (#123 or a short description), and check the symptom the user saw.
  • Keep the PR fast tier small. Reserve it for regressions that guard security, data correctness, or code changed in roughly the last 30 days. Put other regressions in the nightly tier. CI marks whole modules in NIGHTLY_ONLY_MODULES in scripts/ci_test_tiers.py; don't move a shared module out of the fast tier if it contains tests that need to stay there. Directly affected tests still run on the relevant PR.
  • Don't restate constants, defaults or re-exports.

pixi run test-smells --check fails on private-internal patches or whole-argv asserts on added or changed lines under tests/, compared with the merge base with origin/main. Without --check it only reports findings. PR lint runs in blocking mode on the PR's changes; it ignores untouched files and existing findings on untouched lines.

Make a change with an AI agent#

The project is developed with AI coding agents. AGENTS.md holds the rules they follow: test and run what they write, run ruff and mypy, keep outputs in out/ or tmp/, keep defaults unchanged.

  1. Install an agent, for example GitHub Copilot CLI (npm install -g @github/copilot), and start it in the repository: copilot.
  2. Pick an issue from the good first issue list and tell the agent the outcome, how to check it, and where to stop. For example:

Fix issue #N. Add tests that fail without the change, run just check, then open a pull request that closes the issue.

  1. Review what it did: read the diff (/diff in Copilot CLI, or git diff), and check that the tests would fail without the change. Run the command yourself on real data when you have it.
  2. Have it push and open the pull request, then watch CI (gh pr checks --watch). Paste failures or review comments back to the agent until it's green.

A job that fails with Upstream package mirror unreachable couldn't reach Ubuntu's package mirrors; that is an outage, not your change. Ubuntu packages come through .github/actions/apt-install, which tries several official mirrors, gives up within minutes, and installs from its cache when it has one. rerun_lost_runners.yml reruns such jobs up to twice, normally recording each request in the current week's pinned CI flake ledger. Audit outages are logged without blocking runner recovery. It also recovers lost runners, reports confirmed flaky tests as bugs, and blocks retries matching red main. See CI failure observation and retries for the policy and the audited landing-script command.

Keep each change small and state how you'll verify it. Most problems show up when the result is checked against real data, not in review.

Retire stale agent worktrees#

The post-work cleanup checklist does not schedule itself. On a Linux host, run these commands from the primary checkout on main:

python3 scripts/cleanup_worktrees.py                   # offline audit, no removals
python3 scripts/cleanup_worktrees.py --github          # verify eligibility only
python3 scripts/cleanup_worktrees.py --github --apply  # retire eligible worktrees
python3 scripts/cleanup_worktrees.py --github --trim-caches  # preview cache trimming too
python3 scripts/cleanup_worktrees.py --github --inspector --include-detached  # preview detached cleanup too

--github uses an existing authenticated gh session to request PR metadata from github.com. Branch names, commit IDs and worktree contents are matched locally, never uploaded. A candidate must live directly under scratch/. A checkout on a branch must exactly match the head of its latest PR from this repository, merged into main at least a day ago and authored by the authenticated account. Git removes the worktree without --force; the branch stays. An authentication or state error stops the run. The private JSON report in out/worktree-cleanup/ records skips, removals and errors.

Detached checkouts are skipped unless you pass --include-detached. Their exact HEAD must be reachable from the local origin/main tracking ref (the tool never fetches it), or match the head of a latest same-repository PR authored by the authenticated account and merged into main or closed against main at least a day ago. Before removing a detached checkout, apply saves its exact commit locally under refs/worktree-cleanup/detached/<head> so even an unmerged PR tip remains recoverable without GitHub. The report gives the recovery ref; for example, git worktree add --detach scratch/recovered <ref> restores the checkout. A detached checkout with an in-progress Git operation or older commits recoverable only from its HEAD reflog is retained. The inspector is restricted to the same direct children of scratch/; sibling coordinator checkouts such as ~/src/wt-cert42 are out of scope. The schedule template does not opt into detached cleanup.

Dirty, locked, active or linked worktrees are left alone. Tracked files must also match the exact committed Git blobs byte for byte, except that files up to 1 MiB explicitly marked text eol=crlf may match after converting uniform CRLF endings back to LF. This check does not rely on Git's cached file metadata. Other line-ending changes, smudge filters, and submodules can retain a checkout even if Git reports it clean. Activity is checked through Linux /proc across process UIDs. If Linux hides or denies inspection of a process, the run reports the error and does not remove unverified worktrees. Use the optional inspector below when unprivileged process visibility is insufficient. Use git worktree lock to reserve a checkout that might be eligible for cleanup, including while a job is queued: the process scan cannot see reservations that have no process using the path. Do not start work in an eligible checkout during cleanup. Symlinks are checked in this repository and its registered worktrees, including shared Git metadata and each checkout's effective core.hooksPath. If a symlinked Git metadata directory could hide dependencies, cleanup keeps the candidates. If any hook.<name>.command is configured, cleanup retains every candidate and reports the hook key: arbitrary hook commands can depend on paths that cleanup cannot verify. Lock a worktree if a hook script in a hooks directory or another project depends on its files. Nothing manages your reference library. Samples and other unknown files block removal. With --trim-caches --apply, the same PR and activity checks allow trimming verified generated Pixi, Ruff, mypy and pytest caches in retained worktrees. Unrecognized cache contents, unlocked Conda packages and links to a cache block trimming that cache. Pixi package files must match local installed Conda or wheel checksums; missing or mismatched checksums retain the environment without fetching metadata. Only the named cache directories are deleted; the checkout, branch and other files stay. Python bytecode blocks worktree retirement unless it can be reproduced from tracked or archived source. Unlisted bytecode in Pixi environments must match bytecode regenerated from verified installed source. A matching header is not enough; caches from another Python version or a source-rewriting tool such as pytest may therefore be retained. The report distinguishes cache trimming from worktree retirement. Small UTF-8 logs under out/ and recognised Python, shell, Lua and R source files under scratch/ (1 MiB per file, 32 MiB total) are copied to a private, local directory in out/archive/ without following links. They are not executed. Do not put secrets in run logs or scratch sources.

Install the read-only activity inspector (Linux administrator)#

Linux can hide the cwd, mappings and file descriptors of services and login processes even from other processes of the same UID. The optional inspector reads this state across process UIDs without granting the cleanup command or Sheprd any elevated permissions. It accepts only inode-verified registered worktree names in one repository, checks the local Unix peer UID, and returns matching numeric PIDs or an unverifiable result, never process paths or arguments. The service cannot run Git, remove a checkout, or run caller-supplied commands. If a process's mount namespace or view of the root cannot be safely compared, it does not certify inactivity. A private root or masked /home alone does not prove inactivity: the inspector still checks retained descriptors, mappings, working directories and invocation paths, and rejects visible mount aliases.

From the separately reviewed revision, as the ordinary repository owner, stage the exact committed blobs and prepare local settings under out/. Verify pwd -P is the registered primary checkout and id -u is its non-root owner:

reviewed=FULL_REVIEWED_COMMIT_SHA
mkdir -p out/worktree-inspector-install
git show "$reviewed:scripts/worktree_activity_inspector.py" \
  > out/worktree-inspector-install/inspector.py

Before enabling any cleanup schedule, run python3 scripts/cleanup_worktrees.py --github --inspector from the primary checkout without --apply. Verify it identifies a live test process as busy and reports a clear, otherwise eligible worktree accurately. When the socket is unavailable, unverifiable, or serving a different inspector digest, --inspector never falls back or removes worktrees. Local inspection checks each live Linux task and rejects external bind mounts of the checkout or its contents. It stops if any task's filesystem view or references cannot be verified; use the installed inspector on such hosts. To suspend inspection, disable the socket and stop the service; pause the Sheprd schedule as well.

Enable or disable daily cleanup on a machine#

Scheduled cleanup is off by default. The plan in scripts/worktree-inspector/ is a template outside Sheprd's automation directory. Enable it only on a Linux machine you choose (for example, lin-big-omarchy), as the owner of the primary checkout on main. Leave it off on other hosts. First verify the installed inspector and its busy/clear results as described above. Make sure the owner's Sheprd automation service is running, agent-coord is available, and gh is authenticated for the repository.

mkdir -p .herdr/automations
install -m 0644 scripts/worktree-inspector/stale-worktrees.luau .herdr/automations/stale-worktrees.luau
/usr/bin/sheprd-automate repo add "$PWD"
/usr/bin/sheprd-automate check .herdr/automations/stale-worktrees.luau
/usr/bin/sheprd automation approve .herdr/automations/stale-worktrees.luau
/usr/bin/sheprd-automate status

The owner must approve the exact plan in Sheprd; agents must not approve it. Confirm status shows the next run. To turn scheduling off on that machine, use sheprd-automate disable SCRIPT, with the script ID from sheprd-automate status, and confirm no next run is listed. If a run is already active, sheprd-automate stop RUN stops it; disabling prevents future runs. To turn the same approved plan back on, rerun the prerequisites and use sheprd-automate enable SCRIPT.

The scheduled run uses GitHub explicitly, runs no agents, and reports success or failure in Sheprd. It retires eligible worktrees and trims verified caches in retained worktrees, without pulling main or installing anything. If the inventory helper changes, update its SHA-256 in the janitor. When the janitor changes, update its hash in the template. On each enabled host, disable the old plan, copy and check the new one, and have the owner approve it before enabling it again. An inspector upgrade also needs a separately reviewed administrator install and matching digests.
