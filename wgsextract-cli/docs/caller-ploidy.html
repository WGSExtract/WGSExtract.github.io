Sex/PAR policy in model-based callers

DeepVariant, Clair3 and GATK use the same sample workspace sex override and coverage-based inference as bcftools calling. The detected fact and any explicit override remain separate in the workspace. An unknown sex produces the structured caller_sex_unknown warning and uses the female policy, matching bcftools. Autosome-only requests do not need a sex scan. This remains true with installed M/F tables when their selected policies agree. Sex/mitochondrial aliases (including RefSeq X/Y and M/chrMT) resolve consistently for table lookups; the original FASTA names remain in caller inputs.

The reference library's ploidy file wins; otherwise a confirmed GRCh37 or GRCh38 build uses the same bcftools table as vcf snp. A file or folder name or contig count alone does not select a build-specific table. For a custom reference with no confirmed build, put its policy in the library's ploidy.txt. The table's coordinates are 1-based inclusive, translated to half-open BED intervals at each boundary. Male X is haploid outside the table's PAR intervals and diploid inside; autosomes remain diploid. The bcftools contract makes male Y haploid (including its PAR copies), female Y excluded, and mitochondrial calls haploid. This is not a genome-wide haploid switch. Other sex-chromosome builds require a library ploidy file. Custom tables must be unambiguous and specify ploidy 0, 1 or 2. Single-sex tables without a sex-neutral fallback, or sex labels other than M/F, are explicitly refused rather than silently interpreted as diploid.

  • Google DeepVariant: uses --haploid_contigs and --par_regions_bed; the PAR BED is omitted when the selected haploid contigs have no diploid PAR intervals (for example chrM or male non-PAR-only chrX/chrY calls), because DeepVariant cannot read an empty BED. Haploid contig handling still applies. Ploidy-zero intervals are excluded from its region selection. The generated BEDs are atomically published, immutable, content-addressed inputs in .deepvariant.policy beside (not inside) its cleaned work folder. Concurrent planning and work cleanup cannot rewrite or delete an active run's policy. Google's recalibration suppresses heterozygous non-PAR genotypes but retains homozygous diploid-encoded GT fields (0/0, 1/1), not single-allele GT.
  • CPU GATK: calls haploid and diploid interval sets separately, using --sample-ploidy, then gathers and sorts the VCF. Partitioned calls cannot currently be combined with --scatter. Whole-genome CRAM 3.0 remains direct CRAM input. Whole-genome CRAM 3.1 requiring ploidy partitions must first be converted to BAM, rather than silently staging almost the whole genome as temporary BAMs. Bounded regions retain compatibility staging.
  • CPU Clair3: calls each ploidy interval set separately, with --haploid_precise on the haploid set. That mode retains homozygous-alt haploid calls, rather than converting every heterozygous prediction to ALT. Without an explicit region, it retains its chr1–22/X/Y default scope rather than extending calls to ALT/decoy contigs.
  • Parabricks DeepVariant (--gpu): pbrun has --haploid-contigs but no PAR regions option, so it calls each ploidy set separately, like GATK: one run over the diploid intervals (autosomes, the PARs and a woman's chrX), and one over the haploid intervals (a man's non-PAR chrX and chrY, and chrM) with --haploid-contigs naming their contigs and --interval-file keeping it off the PARs. Ploidy-zero intervals aren't called. Each run checks the GPU's free memory just before it starts. Like Google's, its haploid calls keep diploid GT encoding (1/1).
  • wgse-deepvariant 0.4.0+: receives --haploid_contigs and --par_regions_bed for both make_examples and postprocess_variants. Like Google's pipeline, it removes heterozygous probability mass before assigning GT, GQ, QUAL and FILTER, including multiallelic sites, and computes haploid reference confidence before forming gVCF blocks. Haploid calls keep Google's diploid GT/PL encoding (1/1, not 1). PARs remain diploid. Unlike Parabricks, the native engine accepts PAR intervals, so one resumable run covers both ploidies without separate caller partitions. Older builds refuse non-diploid policies rather than silently ignoring them.
  • GATK --gpu and Clair3 --gpu: explicitly refuse requests requiring non-diploid handling until those paths are qualified. Diploid-only regions still work. For Google's pipeline rather than the native engine, set deepvariant_native = "off" in config.toml.

GATK, Clair3 and Parabricks DeepVariant outputs are clipped by variant POS to the partition, so a call overlapping a boundary cannot be emitted by both partitions. With --reference-evidence gvcf each partition's gVCF blocks are also cut at its edges before the parts are gathered (see reference-evidence.md). Interval-restricted assembly and Clair3's haploid filtering may differ from other callers; the shared ploidy contract is not a claim of scientific parity. Regression tests use real fixture alignments and real samtools/bcftools, replacing only the expensive caller processes. They cover both sides of GRCh37/GRCh38 PAR starts, whole-reference and bounded requests, and male/female/unknown sex.

Public bounded qualification#

On 2026-11-14, Google's DeepVariant 1.10.0 CPU image called public male HG00096 30x GRCh38 CRAM against hs38DH over chrX:2770000-2790000 (crossing the PAR/non-PAR boundary) and chr20:1000001-1010000, using two CPUs. The persisted make_examples and postprocess_variants invocations both received --haploid_contigs chrX and the generated PAR BED. Of 89 records, the 17 non-PAR X records were homozygous (10 1/1, 7 0/0); the PAR retained 23 0/1 calls and the autosome retained 28 0/1 calls. This qualifies the bounded Google GRCh38 path, not whole-genome accuracy, GRCh37, native engines, Clair3 or GATK scientific parity.
