CI routing and cache budget

PR area checks diffs the PR's base...head, not just the latest commit. --no-renames includes deletions and both sides of moves. Unknown paths run the full CLI matrix; mixed PRs run the union of their areas.

When moving modules, audit workflow paths filters as well as the import graph and ownership/review path lists. The remote-resource/real-chip concordance workflow covers both remaining flat core/microarray_*.py modules and the core/microarray/** package; Markdown exclusions still apply.

Remote-resource URL probes compare the resolved inventories at the PR's base and head (including composed URLs and version changes), checking only added URLs or changed mirror SHA-256/size pins. Code-only changes probe no unrelated upstream hosts. Real-chip concordance retains its repository-hosted PR fixtures. PRs changing core/annotation_resources.py also run the live SpliceAI format and known-score tests. PRs changing core/gene_lists.* or the assets/report/gene_lists.* manifests run the live gene-list download/pin tests; changes to their corresponding live test modules select those tests too. These behavioral checks are separate from URL probes: an unchanged URL does not excuse validating a changed parser or resource contract. Nightly runs check all upstream URLs (including restricted resources and reference-genome alternatives), every mirror URL, and GitHub's published asset SHA-256/size against the checked-in manifest. They also run the live format, SpliceAI-score and gene-list checks. Byte-level verification runs at publication and on every mirror download, not by downloading ~1 TB each night. See download mirrors and source rights for the audit, restricted-resource policy and manual publication/activation procedure.

The changes job also runs scripts/output_contracts.py check --base <base> with the full history it already fetched: about a second, no extra runner. It compares the merged tree's output schemas with the previous release's pinned contract baseline as it is on the base, so a PR cannot edit a baseline to hide a removed stable field (output contracts).

Drafts run no validation runner jobs, including documentation and secret checks. The API-only collaborator Copilot-review requester is the deliberate exception: it can request a draft review on opened, skips the readiness request when Copilot already reviewed the head, and never checks out or executes PR code. The default-branch ruleset also reviews owner drafts when they are opened, but not later pushes; agents request a fresh draft review after pushing (gh pr edit N --add-reviewer @copilot) and handle its threads before readiness (#1281). Trivial site/docs PRs need one review, not both a separate independent review and Copilot. Readiness remains the point where validation starts, so draft review rounds no longer rerun the matrix. Before gh pr ready, run pixi run lint, the routing/workflow-policy tests, relevant product tests and type checks, documentation freshness checks if docs changed, and pixi run pre-commit run gitleaks --all-files locally. The former draft product subset was test_microarray_vendor_formats.py and test_table_writer.py; use relevant tests rather than relying on remote draft validation. ready_for_review recomputes the complete diff and runs the same area-selected checks as a ready PR push.

GitHub Actions has no workflow-level if. Job-level draft conditions are evaluated before runner allocation (and before expanding a matrix); reusable workflow callers have the same gate. Skipped workflow records may appear, but use no runner. Every PR workflow includes ready_for_review. The shared os_tests.yml suite also gates its matrix job on the inherited draft payload, in addition to the PR area's gates on its OS callers. Workflows with cancelling concurrency retain a runner-free converted_to_draft event in the same concurrency group to cancel in-flight ready runs.

Draft-payload events other than converted_to_draft use a separate -draft concurrency group. GitHub may deliver a draft synchronize event after ready_for_review; its skipped jobs must not cancel the full ready run. This isolation applies to every PR workflow with cancelling concurrency, not just area routing. Ready pushes still supersede earlier ready runs, and converted_to_draft deliberately enters the ready group to stop active work. Draft summaries also use a different check name from required: GitHub accepts skipped checks as passing, so a delayed draft suite must not satisfy the ready run's merge requirement while its selected checks are still pending. Workflows triggered directly by pull_request key these groups on the PR number. Their non-PR invocations use a unique run ID and never cancel each other. No live-state lookup runner is needed: drafts still allocate zero validation runners, and readiness always retains its own full run.

Test dependencies take precedence over area exclusions. The router scans the root test suite's imports, path literals, composed pathlib paths and directory globs without executing tests. Inputs read only by the lightweight docs modules select that pytest job; other referenced inputs select their affected test files. The map is deliberately conservative, including some fixture-data literals. Product Python changes, including native and GUI/site Python, select CLI pytest and explicit changed-file lint. Known docs/CI generator scripts and lightweight test modules select their own checks instead of the full CLI matrix. CLI Python retains root Ruff/format rules and the existing strict CLI mypy gate; GUI Python retains its own compile gate and adds fatal-error Ruff checks without imposing unrelated root formatting.

Weekly test-usefulness review#

The Monday workflow reads existing hosted PR, merge-queue and nightly JUnit artifacts from the previous completed UTC week. It does not rerun or edit tests. It updates or reopens one bot-owned efficiency issue and attaches a JSON file with pass/fail/skip counts, cumulative and median test time, and source change dates. Missing or overwritten artifacts, fork runs and tests removed from the current checkout limit the sample. The report samples at most 40 pre-merge artifacts per OS and stage, prioritizing failed runs and comparisons at the same SHA, and reports what it left out. It includes all available scheduled nightly JUnit artifacts. Times are summed JUnit durations, not saved runner wall time.

  • Move to nightly needs a test function still present in the checkout, no recorded failures, at least 15 pre-merge passes across five runs, and at least 120 seconds on OS/suite combinations where the same case also passed at night.
  • Possible flakes failed before passing at the same tested SHA, stage, OS and suite. Tool or runner failures can also produce this signal. PR comparisons are separate: the same PR head can run against a different base, so it does not establish an unchanged checkout.
  • Merge or delete suggestions use same-scope test bodies with the same signatures and marks, at least five shared passing runs and no observed failures. Identical bodies are deletion candidates; a one-literal difference suggests parametrization. Check intent and fixtures first.

Source dates come from the newest available Linux nightly coverage map from the last seven days and the main branch's Git history. The map attributes executed source files to test modules, not to individual cases. A missing attribution is unknown, not evidence that the test covers nothing.

Test-suite growth budget#

Hosted Ubuntu ready runs summarize regular pytest JUnit once, combining shards where needed. This is advisory and adds no test runs, artifact downloads or required checks. Fully certified or cache-skipped tests have no new timing evidence. Optional E2E JUnit, other platforms and GUI/native jobs are not part of this budget. The weekly review compares actual totals from the newest usable full Ubuntu nightly in its window, or reports that none was available. It checks unsharded JUnit against the archived scope, excluding remote-only modules.

The budget counts JUnit cases (including skips and parametrizations) and sums case seconds, not parallel wall time. Each module belongs to the first matching selector bucket: CI policy, docs & CLI reference, optional-tool modules, nightly fallback exclusions, CLI integration, or regular CLI. The full suite has its own target. The initial baseline comes from Ubuntu nightly 45876381962. Runtime targets add 15% (at least 10 seconds) and count targets add 10%, rounded up to a multiple of five.

Ready estimates retain baseline costs for unmeasured modules still in the tree and substitute measurements for modules that ran. Changes to which cases skip cannot earn speedup credit; the candidate check ignores timing changes for these modules. Missing or invalid timings make the receipt unusable. The summary marks candidate regressions only when an area grows to more than 125% of its runtime budget and the full-suite projection also grows. Count-only overruns are advisory. Treat estimates as a cue to inspect fixtures and execution scope, not proof of a slowdown. Before making the signal blocking, validate it on comparable runs, especially the noisy CI-policy bucket. Prefer shared fixtures or parametrization that actually reduces cost; the separate test-smells lint still checks how tests are written.

To propose a rebaseline, download the intact tests-ubuntu-all artifact from an existing successful, unsharded full Ubuntu nightly, then run:

gh run download RUN_ID -n tests-ubuntu-all -D out/budget-nightly
python -m scripts.ci_test_budget --nightly-artifact out/budget-nightly \
  --calibrate-run RUN_ID

Review the resulting module and target diff; do not rebaseline just to clear an individual PR's overrun.

Coverage#

Cheap optional-tool integrations (#1199)#

optional_tools.yml runs exactly one Ubuntu x64 job for selected contamination, FreeBayes, LongTR, modkit and ExpansionHunter-dependent tests. The PR router intersects the known affected test files with these suites; an uncertain fallback alone does not allocate an optional-tool runner. Changes to this workflow, its PR caller/router, runner, Ubuntu CI or the shared Pixi setup also select the integrations. Drafts and merge groups do not run this lane. Nightly and release Ubuntu run all five suites. Manual dispatch of optional_tools.yml validates just this small lane on a branch. Before the new workflow reaches main, dispatch the existing ubuntu_ci.yml with optional-tools-only=true on the branch instead. This explicit manual override skips its normal jobs; default dispatches, PRs and schedules retain their existing coverage.

The existing pinned Pixi action installs dev verifybamid2 freebayes longtr modkit expansionhunter under the separate lockfile-keyed optional-tools cache family, seeded only from main. Fixtures are synthetic: no reference bootstrap, full genome or sample download is needed. Every selected tool must resolve before pytest; every JUnit report must contain executed tests and zero skips/errors/failures. With complete certification, the Linux x64 attestation covers the same no-skips command and optional environments; regular pytest with skipped tools does not count. This lane never reuses passed-test hashes.

FreeBayes runs its six caller cases, LongTR its tiny repeat suite, and modkit its two BAM/CRAM parity cases. ExpansionHunter's prefix-gated hg19 catalog regression uses its existing fake caller boundary; it is not a real caller qualification. Other tests keep their existing OS coverage. Measure hosted setup/test duration in the workflow run rather than assuming a warm-cache cost. Large Clair3/model-backed native DeepVariant integrations and real-data suites requiring external inputs remain separate follow-ups, not silent new downloads.

Setup checks on PRs and the daily backstop#

PR installer checks and the Ubuntu app-bundle command test run only when the complete diff touches their setup inputs: installers, packaging, GUI files, Pixi/project manifests, CLI parser/registration, workflow/actions or Install Lab/bootstrap scripts. Parser/registration inputs remain covered because they can invalidate the app's bundled command lines. The bundle check also retains its affected test_cli_parser.py trigger: API wrappers and command-registry dependencies outside cli/ can change the bundled command contract even when installer setup is unrelated. Thus a CLI edit unrelated to setup and the parser contract runs zero OS-installer steps and zero Ubuntu app-bundle checks rather than four installer steps and one app-bundle check. Install Lab and the Tauri installer lifecycle suite are separate release gates; no PR label schedules them.

The four OS workflows run daily on the latest main: Ubuntu at 08:23 UTC, Windows at 08:41, macOS at 08:47 and Linux ARM64 at 08:53. Each also supports workflow_dispatch for on-demand validation. nightly_guard.yml now plans duration shards for Windows, macOS and opt-in balanced Ubuntu dispatches. A missing plan falls back to the normal full suite. Scheduled runs never skip coverage because the SHA previously passed. Ubuntu's default serial, uncached run still refreshes the passed-test cache and selector observation map; scheduled failures keep the existing red-main issue and miss attribution. The queue requires its routed smoke matrix, including Windows for CLI runtime changes even when PR selection discovers no consumers. It uses the merged tree and does not reuse passed-test hashes or writer attestations.

Conservative pure-move PR selection (#1045)#

scripts/ci_moves.py inspects Git's complete base...head diff with 100% rename detection. It uses the actual merge base and reads both Git blobs. The cheaper path requires at least one exact rename and only Python files under src/wgsextract_cli/; every other edit must have an identical AST after removing import and from statements. Definitions, values, control flow and docstrings must remain identical. Entry-point moves, changed assets/tests/configuration, partial renames, parsing errors and uncertain module mappings retain normal fail-open selection. Import-only edits without a move retain normal selection.

The narrow set contains tests whose import closure, including conftest/autouse fixtures, reaches moved modules or modules with rewritten imports. Unsafe importer consumers retain the normal selector's inclusion/fail-open rules. Remaining old-name imports, deferred literal imports or renamed-away file readers force normal selection instead of silently omitting consumers. Whole-source recursive globs are not removed-path references when both sides of a byte-identical rename remain inside the scan. Their scanner tests and importing consumers still run; literal removed paths and narrower directory globs retain the normal-selection fallback. Before pytest, every selected OS imports the surviving changed modules and collects the full suite; collection logs are uploaded even on failure. If no test imports the moved modules, the existing tiny smoke pair still supplies the runner for import/collection validation. The merge queue never uses this optimization: full Linux and code-selected Windows remain its safety net, with only their existing passed-on-main test-cache exclusions. Writer platform certifications cannot skip these hosted move checks: their current commands do not yet attest import/full-collection validation.

Writer self-certification#

One-time machine / checkout preparation#

Use the Pixi version pinned in .github/actions/setup-pixi/action.yml (or a compatible version exposing locked wheel URLs and SHA-256 values). Ensure pixi is on PATH in non-interactive shells too; an unconfigured mise shim is not a working Pixi installation. Install environments explicitly, just as CI does:

pixi install --locked -e default -e dev
just certify-setup

certify-setup downloads the exact PyPI wheels in pixi list --locked, checks their lockfile SHA-256, retains them under out/certify/inputs/wheels/, and validates the installed environments against them. It does not install tools, rebuild dependencies from source, change the lockfile, or publish attestations. Re-run it after lockfile updates and for each new checkout; Pixi environments are non-relocatable and editable packages must refer to that checkout. Already verified downloads are reused; incomplete or incorrect downloads never replace a verified archive.

For full Ubuntu/macOS product suites, install the supplemental environments needed by the selection (normally vep-rs; also delly on macOS; imputation, pacbio, phasing, and somalier for their routed tests), then retain their wheels too:

pixi install --locked -e vep-rs
just certify-setup -e default -e dev -e vep-rs --reference

Repeated -e replaces the default environment list. --reference prepares the pinned bootstrap, liftOver chain and full hs38 FASTA in one host store, then symlinks reference in the checkout to that library. The store defaults to out/shared/certification-reference/ in the primary checkout. To put it on another disk, set an absolute path in the primary checkout's out/shared/config.toml before preparing it:

certification_reference_store = "/data/wgse-certification-reference"

Keep the store outside linked worktrees. Reading this optional configuration requires Python 3.11 or newer; offline cleanup with the default location still works on Python 3.10. The store keeps separate versions when the pins change. Setup checks the SHA-256 of the retained release archive, extracted assets, pinned chain and catalog FASTA once per version. Certification checks that the verified files and indexes have not changed since then; it neither downloads nor rehashes unchanged shared data. Treat the linked library as read-only: use a separate --ref directory for experiments that write to it. If a verified reference or index changed, setup and certification refuse to reuse it. Stop jobs using that version, move the version directory named in the error aside, then rerun just certify-setup --reference to rebuild it. The initial setup can download several GiB; run it under the resource coordinator on shared hosts.

For a new worktree on an already prepared host, just certify-setup --link-reference links the library offline without preparing wheels. Existing libraries are not overwritten. To reuse the shared library, move a local reference/ aside; an explicit reference_library must either be the worktree's reference or point to the pinned library. Legacy libraries with a retained per-checkout bootstrap still work, but must be checked from scratch on each certification. just certify-setup --link-hs38 /absolute/path/to/hs38.fa.gz is an offline way to replace an individual ignored FASTA in a linked checkout: it checks the full SHA-256, leaves nonmatching files and sidecars alone, and should be run only while nothing is writing to that path.

Each checkout still needs its wheel archives. Generic-only and CI-policy-only certifications do not need reference setup.

Certifying a PR#

Keep owner PRs in draft while reviewing. Run the scoped local preflight, batch fixes, and finish the review of the current pushed SHA before requesting certification. Review is settled when the current-head review is complete, no newer review is pending, all actionable threads are handled, and no required approval is outstanding. The review-start-timeout exception requires a clean independent review and a readiness note. Do not certify each round. Attempt each eligible layer once on that head, reuse only valid evidence for that SHA, and cancel stale work. Do not refresh a mergeable PR merely because main advanced. If a necessary fix or refresh changes the SHA, return to draft and settle review again before certification or a new ready matrix.

Use the existing ready router, not a separate path allowlist:

Routed workLocal candidates beyond generic
CLI source/tests, shared runtime inputs, assets/native files read by CLI tests, or broad fallbackNon-empty CLI lanes: Ubuntu → Linux x64; macOS → macOS ARM64; Windows → Windows x64; ARM64 → Linux ARM64. Routed optional integrations add Linux x64 for CLI changes.
Prose, docs, site or CI policy/workflows without CLI inputsNone. Keep routed docs, site, policy, OS smoke and optional-tool checks hosted if not covered. The owner prose fast path still applies.
GUI/native-only without CLI inputs, or pure movesPreserve the separate GUI/native gates and hosted move guards.

Mixed diffs take the union; a policy or site edit cannot mask a CLI input. Choose an immediately available slot of the exact native platform with prepared inputs. Otherwise record hosted fallback, without provisioning or retrying on that head. A local test failure is actionable, not a host-unavailability exception. Keep ready admission and the passing current-head hosted required verdict; jobs without matching evidence still run hosted.

On a clean checkout, use just certify --generic-only for generic and just certify --platform-only on each selected native host. On shared Linux hosts use agent-coord run --cores 4 --mem 8G --label "PR certification" -- just certify --generic-only for generic (substitute --platform-only for the native layer). The host platform is detected, never overridden; Linux x64 cannot certify ARM64, macOS or Windows. All selected tests run locally in full, without CI's passed-test cache. Lint, strict typing, changed-file lint, routed docs/site checks and the selector's complete affected CI-policy union form the generic layer. Logs/JUnit live in out/certify/<sha>/<layer>/; successful exact-head statuses include machine, test count, duration and the full log SHA-256.

Certification never provisions its execution environments, including inside the nested pytest runner (the installer regression still exercises its own isolated installation sandbox, exactly as CI does). Prepared default/dev environments are mandatory, with vep-rs for Ubuntu/macOS, gatk/vep-rs for Windows, vep for Linux ARM64, and the routed supplemental tools. Installed conda URLs/builds/checksums and Python versions/RECORD integrity must match pixi list --locked. Retain each pinned PyPI wheel as out/certify/inputs/wheels/<sha256>.whl: validation checks its lock SHA-256 and compares installed files with the wheel, without downloading or installing it. Missing archives refuse certification. Editable Python packages must point to this checkout. Dependency updates require explicitly refreshed environments and just certify-setup artifacts matching the new lock; stale versions or changed wheel URLs/hashes cannot reuse old provenance. Both layers enforce this. Ubuntu/macOS full suites also require the retained bootstrap archive at out/certify/inputs/wgsextract-reference-bootstrap.tar.gz with its pinned SHA-256, byte-matching installed bootstrap support files, the pinned hg19-to-hg38 chain and pinned hs38 genome. Retain the bootstrap archive separately when preparing certification inputs: the normal bootstrap command removes it after extraction. Missing or unprovable reference inputs refuse certification with the missing path and setup command; no downloads occur during certification.

The router executes only the verifier from the PR's base SHA, before checking out PR code, with isolated Python. A missing base verifier or any change to the verifier file falls back to hosted checks. Therefore the bootstrap PR adding the verifier cannot itself skip hosted tests; its first trusted skip can happen only after landing. Forks are excluded before the verifier executes. The verifier accepts only the latest successful status on the exact same-repository head, created by an account with write, maintain or admin permission. Missing permissions and API errors fail closed. Writers can already push to main: this is an attestation at the same trust boundary, not proof against a malicious writer. CI needs statuses: read and the collaborator-permission API's Metadata: read (implicit in GITHUB_TOKEN); local gh needs commit-status write and PR-comment write access. No privileged token is given to PR code.

Generic classification rejects uncertain imports/fixtures, subprocess/tool use, platform branches, concrete pathlib operations, permissions, signals, symlinks and line-ending behavior. Currently no existing module is proven generic under these deliberately strict rules; modules remain platform-sensitive until proven. Uncertified generic tests run once on Ubuntu; nightly retains full coverage. When local-ci/generic and every routed platform status pass on the exact head, the PR area workflow skips its hosted test suites. Ubuntu tests require both local-ci/linux-x64 and local-ci/generic; each other OS can still use its own attestation when certification is partial. Missing, failed or pending attestations fall back to hosted checks for the missing layers. Linux x64 is also required when optional-tool tests are routed. Non-test gates still run as configured: routing, lint, type checks, site/contract checks, gitleaks and CodeQL. Separate GUI and security workflows are not replaced by CLI statuses. The required and ready-gate verdicts still require successful routing and hosted gates. Merge groups never consume attestations. Setup refusals, missing inputs and interruptions clear pending attestations with error (“Not certified … hosted CI covers this SHA”), not failure. Only a test runner report containing failed tests produces failure. Landing still requires the passing hosted ready run; non-success local attestations never make that otherwise-passing run fail the landing gate.

Remote certification on owned hosts#

Register SSH aliases and their native platforms in a controller-side config.toml (keep the file outside the Git checkout, or ignore it locally):

[[certification.hosts]]
alias = "windows-host"
platform = "windows-x64"

[[certification.hosts]]
alias = "windows-backup"
platform = "windows-x64"

[[certification.hosts]]
alias = "mac-host"
platform = "macos-arm64"

Push the branch, then run on the controller:

just certify --remote windows-x64 --remote-config /path/to/config.toml --platform-only
just certify --remote macos-arm64 --remote-config /path/to/config.toml --platform-only

--remote accepts a registered alias or a platform. For a platform it tries hosts in listed order and skips hosts that fail the SSH, checkout, disk or native-platform probe, or whose controller lock is busy. It does not retry a failed or interrupted test on another host. Only hosts listed in the remote-hosts configuration file are eligible; there is no built-in fallback. If --remote-config is omitted, the controller reads config.toml in its working directory.

The controller enforces the same clean, pushed, same-repository open-PR and writer checks as local certification. It holds a local agent-coord lock named for the selected alias and bound to the controller PID, including for Windows workers. All controllers sharing a coordinator must use the same alias for a machine. SSH requires a known host key and noninteractive authentication. SSH agent, port and environment forwarding are disabled. Workers need neither gh nor a GitHub token; configure the worker checkout for public HTTPS, without credential-bearing remotes or extra Git hooks.

Prepare an isolated clone at ~/src/wgsextract-cli on each registered machine and ensure Git and locked-compatible Pixi are on the SSH user's PATH. POSIX workers need python3; Windows uses OpenSSH and PowerShell with Python from pixi install --locked -e dev in that clone. No administrator access is needed. Check the worker's resource coordinator before preparing inputs. If agent-coord is present on the worker, the test invocation uses its resource lease and a worker-side wgsextract-certification lock. On hosts without it, coordinate explicitly with anyone else using the machine.

The bootstrap fetches the exact pushed head and base SHAs over public HTTPS and creates ~/src/wgsextract-cli/scratch/certify-<head-sha> as a detached worktree if absent. Branch names never enter the remote command. Remote certification uses the same native platform or generic commands as local certification. Prepare locked environments and retained inputs separately from ready admission; if required inputs are absent, fall back to hosted checks rather than provisioning or retrying for that head. Use --prepared-only for coordinated remote attempts; the test phase uses --no-install.

The worker's filesystem must start with 30 GiB free. A one-second watchdog stops the worker below 26 GiB to preserve the 25 GiB reserve. Loss of SSH or 30 seconds without a five-second controller heartbeat cancels setup and tests using a Windows kill-on-close Job Object or the worker's and observed descendants' POSIX process groups. A fresh SSH connection confirms cleanup before the controller unlocks the alias, including after a transport failure or SIGTERM. If confirmation fails, the controller skips the explicit unlock. The coordinator releases the lock when the controller exits, even after SIGKILL. The worker admits only one bootstrap at a time and refuses retries until the previous run's cleanup is recorded. If the worker supervisor failed before recording cleanup, confirm the matching run and its descendants have stopped before removing active from ~/src/wgsextract-cli/out/certify/remote-control/. The worker checks the native platform, clean tree and HEAD before and after execution. Logs stream to out/certify/<sha>/remote-<alias>/<layer>/run.log; only the controller publishes local-ci/<platform> and (if requested) local-ci/generic, with the alias and full log SHA-256. Missing or mismatched results produce no successful status. Tests that actually fail produce failure; refusals and interruptions during a run produce error.

Windows x64, macOS ARM64 and Linux ARM64 statuses can replace their routed suite or workflow-only smoke, not a different platform or the package and real-data benchmark smoke. Edits to remote certification route its supervisor regressions to native OS smoke jobs even without a product-code change. Linux x64 certification requires the locked environments for affected optional integrations, in addition to the normal platform inputs. The fresh Windows imputation install stays hosted when affected, even with a passing certificate; certification validates tests against the environment already on its host. Pure moves still run hosted merged-tree import and collection guards. Sparse selected PRs save less.

Decisive test selection rollout#

#1339 (decisive test selection) changes the selection policy in stages.

  1. Collect a versioned dependency map on trusted Linux x64 main/nightly runs. Record the source SHA, run and attempt, platform, interpreter, lockfile, and test/tool profile. Report missing or incomplete evidence explicitly.
  2. On ready PRs, report what the decisive selector would choose next to what the current selector chooses. Record the diff/base/head and tested tree, map provenance, selected and omitted test files, rule reasons, and unmatched inputs. The report does not control test or job selection, cache reuse, certification, or the required result.
  3. Enable symbol selection only for regular Linux x64 pytest after stage 2 lands and the gate passes draft review, local checks and certification. The owner approved enabling it without a 20-PR wait. The gate verifies its map on its own PR and retains current selection if the map is missing, stale, incompatible or the analysis fails. A passing shadow report cannot show that a test absent from both selections passed. Keep the existing selector for other platforms.

The decisive rules cover the complete diff, including both sides of moves and the base tree for deletions:

Changed inputSelect
Observed Python function bodyTests that executed the function
Module/class initialization, imports, signatures or defaultsObserved module users and literal importers
New or unobserved functionTests of known callers within two static hops, plus explicit symbol and module consumers
New Python moduleTests of the head's importers and callers with local imports
Shared helpers and fixturesHelper callers and fixture users; autouse fixtures select their directory scope
Data or generated filesObserved and static readers
Package/tool manifests or locksUsers of the changed packages or tools in the affected environments
Native, packaging, shell or CI inputsDeclared tool/package families, static readers and existing routes

Always include changed or added tests and applicable contract tests. A universal dependency such as root pytest configuration, the interpreter or a root autouse fixture can select the entire lane; name the scope in the report. An unmatched input is a gap to investigate. Before relying on the new selector, give it a declared consumer or contract test, or record a reviewed reason why it has no runtime effect. Unknown inputs do not implicitly select every test under the decisive policy.

The daily backstop runs the full regular Ubuntu suite on latest main without reusing a prior push's pass. It refreshes the existing test-result cache (#915 (passed-test cache)). Main pushes can avoid repeating that exact SHA's queue passes, but not the files the queue skipped. Keep test-selection receipts for the tested trees. If the backstop fails, rerun only the failing tests on first-parent main trees since the last comparable full pass to locate the first reproducibly bad commit. Do not infer a miss from timing or from a single failure: distinguish omissions from flakes, runner failures and interactions between merges. File a ci-automation issue for a confirmed omission, naming the PR, failing test and selection rule, and requesting a selector regression. This does not replace other OS, smoke, installer, certification, or merged-tree guard coverage, including python-size.

The replay estimated 39.2% fewer regular Ubuntu pytest minutes and retained all 140 independently identified test targets and the known escape tests and guards. The historical replay is a cost estimate, not evidence from live shadow runs.

Current per-test PR selection#

scripts/ci_select_tests.py selects individual test files, not whole areas. Its AST import graph follows transitive imports, relative imports, from package import submodule, and package initializers. Literal command_handler targets and the finite CommandRegistration registry from #804 (lazy CLI startup) are resolved without importing application code. Unresolved dynamic imports conservatively include their readers; if a CLI entry-point test reaches one, selection fails open to all. Literal module names used by subprocesses and patch targets also participate. Applicable conftest modules are implicit imports of every test. Shared helper imports therefore participate transitively too, including sibling test modules used as helpers; their literal file inputs propagate to importers.

Tests are selected when they reach a changed Python module, directly change, or read a changed path/glob recorded by test_inputs. Changes to conftest, helpers, shared fixtures, the dependency manifests/lockfile, deleted modules and unknown paths trigger broad fallback. The server-specific tests/server_helpers.py, tests/server_data.py and tests/server_path_cases.py are an exception: their callers and fixture users import them explicitly, so a change selects their transitive importers and any literal readers. HTTP limits and job-log tests live in tests/test_server_http_limits.py; reference-library and dependency queries live in tests/test_server_queries.py. Both are routed by those imports in the same way as other server test modules. On ready PRs a broad fallback means the fast tier plus known affected tests; diagnostic and local certification selection can still request the full suite. Eager package initializers can legitimately connect many tests: this selector does not pretend a lazy runtime dispatch is narrower than the static graph. The current shared fixture helper imports the typed API, whose eager package initializer connects almost all application modules. Those changes can select the whole suite even without the explicit all fallback. Narrowing that shared dependency requires a separate fixture/API refactor, not dropping edges from this safety graph. Non-Python application resources currently fail open because the test-input scanner does not inspect runtime resource consumers. Explicitly declared generated documentation inputs retain their freshness lane.

The changes job publishes tests and per-OS selections as JSON test-file arrays or all. The four OS wrappers forward these inputs to the shared os_tests.yml workflow, which passes them through scripts/ci_run_tests.py to pixi run test-ci; the duration plan and the Ubuntu-only partition apply within that set. Empty selections skip jobs, and empty partitions exit successfully. Selections are validated and passed as argv, never evaluated as shell text. Explicit paths are filtered using the test-ci task's ignore rules so generated-genome and real-data suites remain exclusively in their dedicated steps.

Non-Markdown .github/** and scripts/ci_*.py changes select actionlint and the CI policy/routing/readiness regressions, not the CLI matrix or Install Lab. ci_tests includes their actual transitive script/action readers as well as the baseline policy checks; the CI job executes that complete selection on four pytest workers and reports the slowest tests. Changing an OS matrix workflow additionally exercises only that OS in one lightweight smoke job; changing shared os_tests.yml exercises all four OS smoke jobs. Mixed product/CI changes union their coverage. Declared docs freshness modules join a product selection before the docs lane is suppressed. Extra generated-genome, imputation, ONT and Windows vep-rs checks run only when their test files are affected. The queue instead runs import and test collection plus a bounded smoke cross-section on affected CLI areas. Nightly, manual and release candidate runs retain full-suite coverage.

The selector gives tests the transitive dependencies of their conftest.py files. Keep shared home/config isolation in tests/home_isolation.py without application or CLI subprocess imports. Tests that launch the CLI still reach its entry point through the literal subprocess target in tests/smoke_utils.py. The selector builds its own policy names from the app package prefix: they name modules the selector recognizes, not modules the selector executes. Real dependencies shared by fixtures still count: core configuration can still reach the CLI through the public API.

Test result cache#

On top of the selection, scripts/ci_test_cache.py (#915, Bazel-style test result cache) skips a PR's test files whose exact dependency hash already passed. A test file's hash covers:

  • every tracked file whose change would make select_tests pick it (its import closure, conftest dependencies and declared file inputs, evaluated one file at a time with the selector itself);
  • every file whose change makes the selector fall back to all (pixi.lock, pixi.toml, pyproject.toml, runtime resources, shared fixtures and helpers, unknown paths);
  • how tests run: os_tests.yml, the four OS callers, setup-pixi, the runner, tier and cache scripts;
  • the test file's identity, the job (OS, tier, shard, OS-independent skip), Python version, platform and runner image (ImageOS, ImageVersion). Coverage flags are excluded.

Equal hashes therefore mean the two trees differ only in files the selector would not run that test for, so a cache skip is never less safe than #914's selection (a regression test checks this for edits, additions and deletions). Hashes only see files that exist; each recorded pass also keeps the names of its tree's files whose deletion selects all, and a pass is reused only if none of them has since been deleted.

Each os_tests.yml matrix job keeps one manifest of passed hashes:

Security. GitHub scopes caches by ref: a PR run writes only to refs/pull/<n>/merge, readable by later runs of that PR alone, and can read the base branch's (main's) caches. Only schedule and workflow_dispatch runs can write main's scope. A PR therefore cannot poison what main or other PRs read; at most it can skip its own tests, which its own workflow edits could do anyway. The merge-queue smoke does not read or write these caches. Nightly reruns the full suite, including tests not selected before merge, at the latest main SHA.

Each test job's summary lists the cache-skipped files, where they passed (main or pr) and their hashes. Each job's tests-<os>-<label> artifact also holds test-scope.json: the files selected for that job and, for each cache skip, where it passed. To estimate savings, run pixi run python scripts/ci_cache_replay.py --limit 60 --junit <main pytest.xml...>; it replays consecutive ready runs of merged PRs.

CodeQL language scoping on pull requests (#1373)#

Drafts cannot enter the queue and need no required result. The landing validator rejects cancelled runs because GitHub counts a skipped required check as passing.

Auto-merge never enqueues a PR that conflicts with its base, and GitHub doesn't say so (#1281; one such PR waited about three hours). After every main push, every three hours and on manual dispatch, Auto-merge conflict watch (auto_merge_watch.yml, one five-minute API-only job running scripts/ci_auto_merge_watch.py from main) labels each open PR whose auto-merge is enabled and whose mergeability is CONFLICTING auto-merge-blocked, creating the label if needed, and comments asking the author to merge the base branch. It comments before labelling, once per PR head per blockage: a hidden marker in its comment names the head, and only a marker newer than the label's last removal counts. So a failed run retries without repeating the comment, while a new head that still conflicts, or a conflict that returns after clearing, is announced again. One PR's API failure doesn't stop the others; the run fails at the end. The label is removed when the conflict is gone, auto-merge is turned off, or the PR closes or merges. It waits for GitHub to compute an auto-merging PR's mergeability after a push and leaves it alone if that stays unknown. --dry-run reports without changing anything.

Ready admission#

The Free plan runs at most 20 hosted jobs at once and GitHub gives queued jobs no priority, so a burst of ready PRs starves the merge queue (#1373). Before gh pr ready, agents run python scripts/ci_capacity.py --wait --pr N. It reads PRs, workflow runs and jobs through gh api (read-only) and exits 0 when admission is fine. The priority label, added to PRs from non-bot collaborators with write access other than theontho, lets the named PR skip the capacity gate. Other PRs exit 3 (hold) while a priority run can still need a runner, a priority queue entry is not yet MERGEABLE, any merge_group job is queued, or more than --max-ready (default 4) ready-PR area matrices are in flight. An empty job list or a running routing job can precede a matrix fan-out, so neither indicates spare capacity. Once required is the only unfinished job in a ready PR area run and already has a runner, that run no longer blocks admission. Unknown workflows reserve capacity until they complete; the coordinator can cancel unstarted agent runs, not reclaim runners from agent jobs already running. --wait polls with exponential backoff, polling a last time at --timeout seconds; --json prints the counts. Use spare capacity without delaying queue work or priority authors; don't infer spare slots from jobs that haven't fanned out. The check reserves nothing: each supervisor waits until its previous admission is visible before checking the next one. Concurrent supervisors can overshoot --max-ready by at most one run each.

Fast path for collaborators#

  • priority is added to PRs from human collaborators with write, maintain, or admin access, except the agent account (theontho). It is added when you open, reopen, mark ready, or convert the PR to draft. You can remove it until the next of those events; pushes do not restore it. With it, you can ready your PR without waiting for agent capacity, and agents reserve runners while your CI can still schedule jobs or your queue entry needs checks.
  • Add hands-off if you want to handle everything yourself, including CI reruns. Add land-asap when you're done: owner-account agents may rerun cancelled or lost-runner jobs and enqueue your ready PR at the front once checks pass. hands-off takes precedence. Without land-asap, agents may only move your existing queue entry after you enable auto-merge or enqueue the PR yourself. Agents never push to, ready, or review-fix your PR.

To skip the hosted macOS lane, usually the slowest, run just certify-setup and then just certify on your own Mac on the exact pushed PR head. See Writer self-certification for setup and reference requirements. Batch review fixes into one push to avoid rerunning the full selected matrix after each fix.

Target steady state is roughly 6.6–7 GB, leaving headroom for CodeQL-managed caches and lockfile rollover. This is a size plan, not an asserted measured post-deployment size. Old keys also age out after seven days unused.

The Actions cache hygiene workflow runs daily on main. It removes a stale Pixi lock key only after the current lock has a cache for the same OS, architecture, Pixi version, scope, workspace path and cache archive version. It preserves equivalent checkout line endings. It keeps two recent CodeQL overlay bases for each configuration plus any for the exact main tip, and three passed-test cache generations for each suite on main and on each PR. Other PR-ref keys and unknown families remain untouched. Preview the plan in a manually dispatched cache_hygiene.yml run on main; set apply to delete. The summary records before and after repository cache bytes and the entries removed. Main moving during the cleanup stops further deletes.

The shared OS suite downloads hs38.fa.gz from v0.1.0 and its samtools dictionary, .fai and .gzi from ci-hs38-1. It verifies both SHA-256 pins in scripts/ci_hs38.sh before installing the files beside the bootstrap's support data, then uses the indexes to read a region before running tests. Updates to the installer invalidate passed-test hashes. CI does not rebuild indexes or fall back to upstream mirrors. To refresh the indexes, dispatch Mirror reference genomes with ci_hs38 enabled and a new ci-hs38-N release tag. The hosted job builds against the pinned FASTA and publishes just the index bundle. Update the tag and archive SHA-256 together; retain the old release for older CI revisions. Once this change lands and older runs have finished, obsolete hs38-v1-* Actions entries can be deleted without removing any other cache family.

Only each OS matrix job seeds its CLI Pixi cache; other jobs restore that same set and install any missing optional environments without saving duplicate sets. Pixi keys include the whole lockfile hash, pinned Pixi version, OS, architecture, scope and workspace-path hash (Conda environments are not relocatable). No prefix fallback restores an incompatible environment. npm and Cargo retain only downloads, using their respective lockfile hashes. PRs never save these caches, even on a cold miss.

The liftOver data cache retains a checksum-verified read fallback to old run-id keys, so UCSC outages cannot break the migration. Main seeds the canonical checksum-only key from either a verified fallback or a verified download; no new run-id keys are written.

Every workflow installs Pixi through .github/actions/setup-pixi, which pins the release executable by version, platform and SHA-256. Main seeds the executable cache separately from the project environment; every consumer checks the digest, and a cold download has bounded retries. The action validator rejects direct prefix-dev/setup-pixi steps. Pixi-binary-only build jobs pass install: "false" to skip project environment caching. A binary-only Windows ARM64 job keeps the Pixi and vcpkg caches warm on a schedule without starting native qualifications. The vcpkg bootstrap verifies the native executable against its own digest and checks that its release tag matches the pinned ports checkout. Manual mirror/bwa qualification jobs and the Copilot setup use the same read-only CLI environment cache rather than creating additional partial environment sets. Release verification installs its immutable tag's environment without caching; an unpublished old tag can predate today's local CI helper actions, so Pixi comes from the run's own commit before the tag is checked out.

The desktop app's workflows and the Copilot setup install its toolchain through .github/actions/setup-gui: Node and npm ci, and on request Rust, Tauri's Linux libraries or the CLI's Python dependencies. It holds CI's only Node pin; the validator rejects direct actions/setup-node steps. gui-build.yml can build an older ref, so it replaces that ref's .github/actions with the run's own before using it. gui-dev-setup.yml deliberately bypasses it: it tests the app's own bootstrap on runners without user tools.

CI Ubuntu, CI macOS, CI Windows and CI Linux ARM64 keep their own triggers, concurrency groups and workflow names, but run the CLI suite through one reusable workflow, os_tests.yml. Its os input selects the installer checks, Windows imputation and vep-rs, and ARM64 checks; reference: true (Ubuntu and macOS) adds the hg19ToHg38 chain and hs38 reference library. Each regular matrix collects both tiers. Its lead job reports as test-ubuntu / all on main and ubuntu / test-ubuntu / all in PR area checks (likewise macOS and Windows); ARM64's single job is native-arm64 / native. Each job uploads tests-<os>-<label>. The workflow has no concurrency group of its own, so the OS calls in one run never cancel each other. The release-only package and benchmark workflow keeps its smoke (OS) jobs. The required and Ready PR area checks names are unchanged. Failure observation, red-main matching and flake-ledger retries use normalized PR/main job names, including the shard label.

Reading the Linux shadow report#

On ready PRs that run regular Ubuntu x64 pytest on a hosted runner, the test-selection-shadow artifact records advisory selections: decisive, tight, symbol, widely-called helpers and line. The job summary shows the current selection, per-candidate files and timing estimates, and omitted observed failures. The artifact contains the full file sets, rule reasons, exact tested merge tree and parents, and the regular pytest receipt. Separate generic, smoke, and installer jobs are outside this comparison. A certified or path-skipped Linux job produces no hosted comparison; missing evidence does not count as a pass. For eager import changes, the symbol and helper arms also record a separate non-gating package import probe and keep observed callers of changed bindings.

Scheduled Ubuntu runs execute the full regular suite even when the same main commit passed earlier that day. They write a versioned Python coverage-context map and per-file test timings. PRs can restore that read-only map. An absent map, incompatible lock or unreachable source SHA is reported explicitly. Test-minute estimates sum recorded pytest durations; they omit unmeasured files and are not wall-clock predictions. Python tracing does not measure external tools or every file reader, so an unmatched input is a measurement gap to investigate, not permission to change CI selection.

The line shadow uses a separate linux-line-impact-map artifact and read-only cache. It reuses the C-tracer contexts from the same successful scheduled or trusted full manual Ubuntu run; it adds no tracing to PRs. The gzip payload contains tracked package paths, positive line offsets, and integer IDs into a test-file table. It contains no source text or parameterized test names.

The line map must match the symbol map's run and attempt, be no more than 48 hours old, and match the tested base's tracked source, test and other input fingerprints (including fixtures outside tests/). The initial shadow only narrows a modification to one existing function body when every edited preimage line has attributed callers. Changed test files and independent routes such as contract tests remain selected. Insertions without a preimage, mixed input changes, and missing or incompatible evidence retain the enforced selection with a reason. Tests that cover the same lines are not interchangeable. The line arm imputes missing per-file durations with the longest measured file and uses that same estimate for its comparison with the enforced set.

Every candidate includes the newline source scanner for changed package Python, and the tool-contract scanner for command or CLI Python changes. The historical oracle's narrower writer-only rule added 19 file-runs and recovered six complete misses; the broader source rule trades a few more short runs for coverage of writers that are moved or indirect. Shared-base failures, such as the tabix failure from the step-resume PR and the unrelated PowerShell qualification failure from GUI/installer preflight, do not justify adding edges from those PR changes. Both belong to the nightly backstop. A newly observed omission in a PR report must be triaged for origin, retries and incomplete runs before it counts as a miss.

Linux symbol gate and daily failure replay#

The symbol gate changes the regular Ubuntu PR pytest input, not the jobs, certificates, other OS lanes, or merged-tree checks. The repository Actions variable CI_DISABLE_SYMBOL_SELECTION=true restores legacy Linux selection for newly started runs; rerun a job to apply it to an in-flight PR. A missing, stale (over 48 hours), incompatible or unavailable map retains the existing input and emits a warning. With a usable ancestor map, the gate adds tests introduced or changed since recording and observed users of intervening source changes. For an unobserved Python module, it also follows the static import closure at the map commit and tested base, so tests of newly added and deleted modules can still be selected. If an intervening module has no resolvable test importers, or the drift includes an unobserved package initializer, non-Python source, unresolved dynamic imports, interpreter configuration changes or changed test harness inputs, the gate keeps the legacy selection. A universal scope on a ready PR exercises the routed fast fallback without cached passes (universal-fast); nightly still runs all tests. The gate's own PR runs the same planner against its synthetic merge tree even if regular hosted pytest was certified. The advisory reports remain available and distinguish legacy-selected, enforced and actually observed files.

Main pushes do not run the OS pytest suite. If the cron run is delayed or missing, run gh workflow run ubuntu_ci.yml --ref main (leave optional-tools-only off). Both triggers run the full regular suite without skipping from either result cache. A passing run refreshes main's test cache and exports the Linux observation map as a seven-day workflow artifact, separate from the evictable Actions cache. Dispatches on other refs cannot publish that map. The Ubuntu jobs and activation canary use a read-only Actions token to find the latest compatible artifact from a successful scheduled or full manual Ubuntu run on main. The artifact digest, run and attempt, source ancestry, Pixi lock, Python version, and 48-hour freshness limit must all match. Absent or incompatible artifacts leave the legacy selection in force. The merge queue does not change its test selection based on this map. Where the suite provides pytest node IDs, the failure replay reruns only those cases; a collection error instead replays its one test module. It checks first-parent trees in order since the last verified passing scheduled or full manual run on main, requires a clean baseline and repeats the first matching failure signature. It will not automatically attribute skipped cases, a dependency-lock change, unobserved trees or an unrelated shared-base failure. To open a ci-automation miss, the first bad commit must map to a PR whose passing run records an enforced symbol omission on the identical Git tree; the legacy selection must have included the test. Logs explain unverified outcomes and the stable case marker deduplicates a confirmed miss across nights.

When nightly replay finds a reproducible failure on the exact Git tree from an eligible line-shadow receipt, linux-selector-line-recall and the nightly job summary compare how many failing test files the symbol and line sets included. A file with multiple failing cases counts once. No matched failures means recall is unavailable, not 100%. This score is advisory and does not publish issues or affect any gate.
