Download mirrors and source rights

Explicit downloads prefer byte-identical GitHub release copies when src/wgsextract_cli/assets/resource_mirrors.json contains published SHA-256 pins. Merely inspecting resources does not contact GitHub. Each downloaded part and the assembled file are verified before installation. An unavailable or corrupt mirror produces MIRROR_FALLBACK and tries the original URL. Immutable upstream copies must match the published snapshot too. Entries with upstream_mutable: true (ClinVar weekly files and refGene maps) may fall back to changed upstream bytes, with an UPSTREAM_VERSION_DRIFT warning rather than failing every time the original publisher updates them. An explicitly supplied SHA-256 remains strict even for mutable sources. Cancellation never starts a fallback download.

Mirror parts use stable DEST.mirror/partNNNN staging paths so interrupted, URL-bound .partial transfers resume on the next attempt. Completed parts stay in DEST.mirror/assembled: a restart verifies its prefix against each pinned part SHA-256, truncates incomplete/corrupt trailing bytes, and appends only the remaining parts. It does not download the verified prefix again. An existing upstream DEST.partial takes precedence over starting a mirror. A successful mirror install removes its staging directory and orphaned upstream partial markers; a successful upstream fallback also removes all abandoned mirror staging.

Publishing and activating a snapshot#

The download-resources-1 snapshot is activated for all 41 approved resources, with 517 pinned parts totaling 928,055,212,641 bytes. The 30 upstream-only or already-hosted entries retain their existing download behavior and redistribution decisions.

Like the reference-genome publisher, Mirror download resources is a manual GitHub Actions workflow. Large payloads are streamed on CI, not a developer's laptop. Every asset is at most 1,900,000,000 bytes (below GitHub's 2 GiB limit). Splitting is binary concatenation, not recompression or a scientific transformation. Each part uses a separate bounded HTTP Range request; a short connection resumes at its last received byte. The response is closed before uploading that part, so an upload cannot leave a long upstream connection idle. Transient failures wait with exponential backoff and jitter; 429/503 responses honor Retry-After (seconds or HTTP date). Five consecutive failures without new byte progress exhaust the retry budget. Range progress resets that budget; whole-file restarts reset it only after reaching a new high-water mark, so repeatedly downloading the same truncated prefix cannot retry forever. Sizes, Content-Range and source ETag/Last-Modified preconditions protect the snapshot; local part hashes are checked against GitHub's uploaded SHA-256/size before the final whole-file SHA-256 record is published.

Normally only one part is staged, uploaded, then deleted: no per-contig 72 GB scratch copy is needed. If a host ignores Range, the publisher can stage a complete file only up to 10 GiB, with space for a part plus a 2 GiB free-disk reserve. Larger/non-fitting downloads fail clearly with RANGE_REQUIRED, not an unbounded runner-disk download.

Audited licence/terms bytes are committed in src/wgsextract_cli/assets/resource_terms/, with source URLs, retrieval dates and SHA-256 in sources.json. Publication uses these verified snapshots without depending on live terms-page availability (including Creative Commons legalcode pages). A live fetch, when needed, uses the payload User-Agent and normalizes GitHub README links to raw content; HTTP errors can fall back to an available committed snapshot. New records retain the audit-snapshot provenance. Keep the explicit AlphaMissense relicensing explanation in the NOTICE as well as the original data header.

The publishing step explicitly uses Bash with pipefail, so logging through tee cannot turn a Python failure into a successful job. Failure evidence is uploaded even when the job fails.

  1. After the publishing workflow reaches the default branch, dispatch it with release tag download-resources-1. Start with gene-map-hg19,gene-map-hg38 to smoke-test publication, then the remaining approved IDs. Empty selection selects every approved resource. Non-redistributable entries cannot publish.
  2. The release keeps per-resource JSON records (upstream URL, version, retrieval date, complete-file SHA-256/size, ordered part SHA-256/sizes), attribution notices and source-licence snapshots. Data/records are never overwritten. A failed transfer can rerun against the same snapshot; if an upstream file changes, choose a new release tag, not --clobber. Completed, verified records are returned before any terms/payload fetch; rerunning download-resources-1 preserves the first dispatch's 11 completed resources rather than rebuilding or overwriting them.
  3. Download the release's *.record.json assets into out/mirror-records/. Run pixi run python scripts/mirror_download_resources.py activate --records out/mirror-records --tag download-resources-1, inspect the pins, and submit the updated JSON catalog in a follow-up PR. Entries without activated pins deliberately retain upstream behavior.
  4. Run the mirror behavior and remote-resource checks against the updated catalog before merging the activation PR. Keep the issue open until the approved assets have been published and their pins activated. Do not claim that merging the publisher alone mirrors data.

Nightly URL checks cover all upstream URLs, including restricted resources and catalog alternatives, plus every published mirror part. GitHub's published asset SHA-256 and size are compared with local pins without downloading ~1 TB each night. Complete byte checks run during publication and every on-demand mirror download. PR URL probes compare resolved inventories at base and head and visit only added/changed URLs; an unrelated upstream outage cannot block a PR. See CI routing. Changes to annotation resource code retain live SpliceAI format/score tests; changes to gene-list code or manifests retain live gene-list downloads and pin checks on PRs, even when their URLs did not change.
