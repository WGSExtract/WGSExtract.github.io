A 30x genome on a 16 GB Apple M1

This page preserves measurements on the smallest Apple Silicon Mac, with the default settings of each recorded version (#549). Automatic RAM-aware backend selection has since changed; see current defaults. Every figure is measured unless labelled otherwise.

The computer#

  • Mac mini, base Apple M1: 4 performance and 4 efficiency cores, 8-core GPU, 16 GB of unified memory, internal SSD.
  • macOS 27.2. It is someone's everyday Mac: their desktop apps stayed open, so about 10 GiB of RAM was available when runs started, and macOS already held about 0.6 GiB of swap.
  • WGS Extract from a source checkout with Pixi, as developer setup describes, plus the macos-aligners-11 builds of wgse-bwa, wgse-bwa-mem2 and wgse-minimap2 on PATH (Apple Silicon).
  • The README installer also worked (55 s). Its last step opens Finder, which fails harmlessly over SSH.

Times are wall-clock. Peak memory is the largest resident set of any process (/usr/bin/time -l) and, for long steps, the summed resident memory of all the user's processes, sampled every 5 s.

Summary#

A whole genome went from a BAM file to a personal report in 7.3 hours in the original trial on the base 16 GB M1, with default settings and its owner's apps still open. The historical GPU-policy repeat at main 992ee758 took 7 h 25 min, including cold reference indexing and interrupt recovery. Both completed, but completion does not mean alignment fits in RAM: that policy swapped heavily (#747, low-memory realignment). HG002 was sequenced to 35x, not 30x; neither trial measures a 30x duration.

  • Historical timing. GPU realignment took about 6 hours; SNP/indel calling took 68 minutes in the original trial. These GPU-paced figures are not predictions for the current automatic CPU fallback, which can be substantially slower: the RAM-adaptive whole alignment measured 13 h 38 min, versus 5 h 24 min for the prior Metal alignment stage.
  • Memory. Concurrent RSS peaked around 10 GiB only because macOS compressed and swapped memory. The historical GPU alignment moved about 1.1 TiB of swap-out traffic, not just a few GiB of occupied swap (#747). That run's working-set estimate was about 22 GiB, above physical RAM.
  • Disk. The 35x run's normal refusal check required about 204 GiB free with the input and reference already present. The observed 166 GiB scratch-plus-results peak is not a space recommendation; see the planning advice.
  • Accuracy. Against GIAB v4.2.1, bcftools SNP calls have 99.1% recall and 97.5% precision, and indel calls 95.2% recall and 95.3% precision. 27 of the 29 Y-STRs it called match NIST's values for HG002.

Defaults for 16 GB#

Automatic wgse-bwa GPU selection now requires the pipeline estimate to fit physical RAM less OS headroom. It first lowers sort memory, down to 256M per thread. If no concurrent GPU plan fits, paired Metal BWA can instead align into a compressed checkpoint, then mark duplicates and sort after BWA exits. This staged plan still must fit the physical-RAM budget; CPU remains the fallback when even staging does not fit. an also-over-budget CPU sort is capped at 256M without increasing smaller requests. Concurrent plans keep their workers; every plan retains fixed K100M for record identity. Low momentary available memory alone does not force a large-RAM host onto CPU; streaming realignment retains its available-memory guard. --prefer-native-gpu (or prefer_native_gpu = true in config.toml) opts into speed only after normal GPU sort step-down fails. At that point explicit --memory is retained; default/config memory is capped at 256M, subject to general sort limits. --no-prefer-native-gpu disables the config preference for one run.

A whole short-read genome on this Mac normally uses staged Metal when the concurrent pipeline is too large. The manifest records alignment_mode="staged_metal" and native_aligner_backend_reason="memory_budget_metal_staged". Staged alignment uses the per-stage thread plan; K100M remains fixed. Postprocessing uses compressed level3 BAM chunks, with up to 2 GiB per sort thread (stepping down to 256M when needed to fit all workers), followed by a bounded merge. Generated FASTQs are removed after the validated alignment checkpoint unless --keep-fastq; user-provided FASTQs are never deleted. Failed stages retain checkpoints in the reported workspace for unchanged-input recovery. Resume checks the input files, reference indexes and alignment settings; unrelated files in the working directory do not affect it. If an index changed or the checkpoint predates these checks, move the reported workspace aside before rerunning.

Whole HG00235x validation for #872 (low-memory Metal) retained all835,260,415 ordered SAM records: 4.50h alignment, 6.44h alignment plus postprocessing and verification, 0.073GiB swap-out, and 42.31GiB minimum free disk. Including FASTQ preparation took6.83h. The raw checkpoint was81.54GiB, marked compressed parts78.69GiB, and final BAM47.23GiB; conservative preflight now allows roughly 230GiB including extraction, bounded intermediate merging and the safety reserve, more if keeping extracted FASTQs. Parts replace the raw checkpoint before merging, rather than accumulating huge sort-temp copies.

An explicit speed preference still permits the faster, over-budget concurrent GPU plan; it can swap heavily. Otherwise CPU remains possible if the staged plan cannot fit. Check the manifest's native_aligner_backend and the selected sort memory in the log/BAM program header rather than assuming a GPU-paced overnight run. The conservative CPU estimate may still be LOW; this is not a guarantee of RAM fit. Explicit bwa-mem3/--fast paths have different rules; see the hardware guide.

Earlier default changes#

Earlier measurements drove the changes below. The CPU-estimate allowance in the first item has since been removed; the other changes remain in use.

  • An earlier optimization retained Metal despite low RAM. It allowed a GPU plan within the CPU aligner's own estimate and lowered sort memory to 512M (#563, earlier GPU selection). It improved the old benchmark from about 11k to 41k reads/s, but the subsequent whole run exposed excessive swap traffic. The oversized CPU estimate no longer overrides the RAM budget (#747, low-memory realignment).
  • vcf snp and vcf indel used one core. They now call contigs in parallel when --threads is above 1, with identical records: 849 s became 211 s (#560).
  • deps check took 32 s warm (74 s cold), mostly asking Pixi to size the checkout. It now takes 9.8 s (#552).
  • realign's FASTQ extraction showed 0% for 23 minutes. It now reports how much of the input it has read, then how many reads it has written (#564).
  • realign's disk pre-flight was a warning even when the disk had room. It is now information (#556).

Earlier experiments, with their historical settings:

  • Threads. realign of 25M reads took 656 s at 4 threads and 637 s at 8: the GPU sets the pace (~44k reads/s), and more threads only add memory.
  • Sort memory. Streaming reads into the aligner (-m 512M or less) instead of extracting FASTQs saved disk, not time (664–666 s).
  • Variant caller. bcftools is the caller to use on a Mac.
    • GATK HaplotypeCaller runs on one core on arm64: chr20 was not half done after 44 minutes, which would be days for a genome.
    • Google's DeepVariant image is x86-64 only and can't run on Apple Silicon: Docker Desktop's emulation lacks the AVX instructions its TensorFlow needs. vcf deepvariant refuses it. It runs wgse-deepvariant when that is on PATH (no Docker; call_variants on the GPU), else only the native ARM64 image (deepvariant-arm64.md).

wgse-bwa or wgse-bwa-mem3#

On Macs with room for it, wgse-bwa-mem3 aligns 1.8 times as fast as wgse-bwa, for about 11 GiB of memory against 6 (Apple Silicon). On the same 16 GB M1, with its owner's desktop session open (12–13 GiB available), it doesn't fit (#609). Both aligners were from macos-aligners-14 (wgse-bwa 0.9.0, wgse-bwa-mem3 0.2.0 --compat=bwa-mem), aligning 5 million HG002 read pairs to hs38. Every completed run with -K 10000000 wrote the same records, from either aligner.

The follow-up thread study, issue #968 used 278,929 chr20 pairs and kept at least 6 GiB available. CPU wgse-bwa took 13.72 s at four threads and 9.14 s at eight; Metal took 3.30–3.31 s. The 1-second periodic responsiveness task had a worst observed scheduling/launch delay of 43 ms during CPU mapping and 17 ms during sort. All decoded records matched across thread counts with fixed -K 10000000. This did not reproduce an OS-thrashing problem from sort's extra workers. It does not establish safety under memory pressure: the much larger wgse-bwa-mem3 runs below are a separate memory-pressure failure. The accompanying 8P+2E M1 Pro study used four balanced rounds under normal desktop load: CPU mapping benefited from extra workers, Metal and markdup did not materially benefit, and sort at ten workers was slower than at eight without seconds-long scheduling stalls. Its tiny codec/calling gains are sensitive to background work on efficiency cores; see the thread-plan measurements and limitations.

  • wgse-bwa-mem3 thrashed. macOS compressed memory to make room, free memory fell to 36–39%, and the load average was seen at about 50. The Mac stopped answering SSH for about 25 minutes.
  • With the default batch size it was worse. No run finished in 900 s, and --metal at 8 threads got through only a tenth of the reads. wgse-bwa with its default batch size took the same time as with -K 10000000.
  • wgse-bwa is the aligner to use here. On the GPU it was 3.3 to 3.5 times as fast as wgse-bwa-mem3, at any thread count.
  • align picks it. With the defaults, align estimated 19.2 GiB for wgse-bwa-mem3 against 12.0–13.0 GiB available, kept wgse-bwa on the GPU, and took 209–211 s. Forced with --aligner bwa-mem3 it took 2,144 s (ten times as long), swap grew from 1.8 to 5.0 GiB, and the records were the same.

Historical Metal run, macos-aligners-16 and mimalloc#

#722 repeated the short-read pipeline on this Mac with main 992ee758, published wgse-bwa 0.12.1 (macos-aligners-16), samtools/bcftools 1.24, and the optional wgse-mimalloc installed through the documented tool setup. The existing HG002 35x, full-quality BAM (42.87 GiB, 835,260,805 indexed records) was used in place, without a staging copy. The target was the existing 195-contig GRCh38_no_alt.fa, not the 456-contig hs38a used for this issue's small-data trial. Desktop applications remained open.

The then-current settings were not overridden: four requested threads, Metal BWA, 512M sort memory per thread selected automatically, and the caller's default mimalloc mode. The normal disk refusal check passed; no force or preflight bypass was used. The four-thread setting is a worker request, not a cap on all OS threads: sampling saw up to 207 threads in an extraction samtools process, 39 in alignment's samtools, and 20 in wgse-bwa, including library/helper threads. Those are thread counts, not simultaneously busy CPU cores.

That historical sequence took 7 h 25 min, including a cold reference index (39 min), FASTQ extraction (22.5 min), and a deliberate alignment interrupt. It is a measured 35x run, not a measured 30x duration. The small slice's linear time projection was not a whole-genome guarantee.

Resume recovered the completed extraction. SIGINT after the first alignment heartbeat returned 130. The unchanged command then skipped extraction, reused the same 66.23 GiB FASTQ pair, and completed with 835,260,415 BAM records (832,735,204 mapped). The small-data test had already verified identical ordered SAM records between interrupted/resumed and uninterrupted runs; a second uninterrupted whole-genome run was not performed. The result manifests recorded wgse-bwa 0.12.1/metal, and both callers recorded bcftools_allocator: mimalloc.

RSS alone hides the memory cost. During resumed alignment, vm_stat recorded 1,113.72 GiB swap-in and 1,116.92 GiB swap-out traffic. These are cumulative system-wide traffic deltas, not simultaneously occupied swap or process-attributed bytes. Sampled occupied swap ranged from 1.21 to 3.70 GiB; memory pressure alternated between normal (1) and warning (2). This heavy swapping is a product bug tracked in #747, not evidence that the historical GPU defaults fit comfortably in 16 GiB. Default mimalloc calling and report added no swap-out traffic; the optional system-allocator SNP run coincided with 0.034 GiB of system-wide swap-out traffic. The conservative RAM estimate was 22.02 GiB at startup, versus 10.80 GiB available. Do not recalibrate that working-set estimate down to 8.30 GiB RSS: macOS compression and swapping kept the resident peak smaller.

Disk fit, but the margin mattered. Free space started at 210.36 GiB above the already-present input and reference and fell to 37.42 GiB. The measurement harness's own 25 GiB free-space guard, which is not part of realign, never fired; realign checks its disk requirement only at start-up. Sampled scratch peaked at 134.86 GiB; scratch plus results peaked at 166.15 GiB. The free-space fall also includes newly built reference indexes and other system activity, so it is not the same measurement. The completed BAM was 43.20 GiB; the SNP and indel VCFs contained 4,392,799 and 918,481 variants. Keep extra space for the desktop, swap and reference indexing rather than treating the observed peak as a minimum free-space recommendation.

report successfully wrote its artifacts, but this sequence did not run annotation, lineage or typing. Its clinical sections were not_run; this is a pipeline/resource measurement, not a populated clinical report or a new accuracy benchmark.

Recommendation and remaining options. Keep the conservative CPU fallback for this approximately 2×-over-budget whole-genome GPU plan when record identity and lower swap traffic matter more than speed. Do not describe it as swap-free or assume that a near-budget case needs the same trade-off.

  • Metal with K10M lowered BWA footprint from 9.795 to 7.366 GiB on the 70.7-million-read case, but changed MAPQ and duplicate flags. It is not an identity-preserving automatic fix, and no whole K10M run was performed.
  • Metal with K100M and sort256 preserved records and took 29.09 min versus 29.38 min for sort512 on that small case, while sort footprint fell from 2.342 to 1.222 GiB. The approved whole-genome comparison below retained Metal speed, but still moved 378.39 GiB of swap-out.
  • Restricting CPU fallback to only far over-budget estimates could keep faster Metal for modest overestimates, but no threshold has been calibrated. That threshold policy is not implemented. The owner-approved speed opt-in, --prefer-native-gpu / prefer_native_gpu = true, deliberately exposes the known GPU speed/swap choice. It tries normal GPU sort step-down first; an ineffective preference changes neither the manifest reason nor the completed alignment's journal key.

Advice for 16 GB Macs#

  • Use the RAM-adaptive policy rather than forcing the old GPU choice. The historical GPU run generated about 1.1 TiB of swap-out traffic per 35x genome, wearing the SSD; its LOW memory warning (about 22 GiB estimated against about 11 GiB available) predicted the risk. Automatic wgse-bwa selection now honors that budget and can choose CPU with 256M sort memory. The whole validation reduced traffic to 47.87 GiB, not zero, at 13 h 38 min rather than 5 h 24 min for alignment. See #747, low-memory realignment. Staged Metal subsequently retained the same records in 6.44h with 0.073GiB swap-out; it is now tried before CPU when the concurrent plan cannot fit.
  • Close what you can before realign and check its chosen backend. CPU fallback can take substantially longer than the old GPU measurements; more workers add memory and are not an automatic speed improvement.
  • Plan disk space before starting. For a 35x run with the input and reference already present, the normal refusal check requires about 204 GiB free. The conservative envelope is about 260 GiB if reference indexes must be built. Download space for the input comes on top. Leave additional headroom for swap and the desktop rather than planning around the observed 166 GiB scratch-plus-results peak. The normal refusal check and the advisory conservative resource envelope are different checks; a passing refusal check is not a reservation.
  • Install the macos-aligners builds (Apple Silicon). They provide CPU optimizations and GPU acceleration when the pipeline fits; installation is not a promise that a whole 35x run will use Metal.
  • Call with vcf snp and vcf indel (bcftools). They use the four performance cores and little memory.
  • Run the other commands as you like. They take minutes and stay well within 16 GB.
