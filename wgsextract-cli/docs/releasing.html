Releasing

pixi run package-smoke builds a source distribution and a wheel from it, checks that both contain the compact CLI help index, and runs discovery from the installed wheel. Builds generate the index without changing the checkout.

One vX.Y.Z release ships both the CLI and the WGS Extract desktop app (gui/), which bundles that same CLI release. Most of it is automated; this is the whole sequence, with what to check at each step.

1. The release#

Merging the release PR starts the release. The workflow creates the tag and publishes only after preflight passes.

  1. Bump the version on a branch named release-X.Y.Z:
   python scripts/bump_version.py X.Y.Z

It sets the version in pyproject.toml, pixi.toml and src/wgsextract_cli/__init__.py, and points the app's bundle at the same release with gui/scripts/bump-wgsextract-cli.py vX.Y.Z (the tag file gui/examples/WGSExtract/scripts/wgsextract-release-tag.txt, the bundle version that names the installers). The release workflow checks all four versions against the tag. It also moves the CLI site's current release (site_src/index.md and install.md) to the new version, and the same script points the app site (gui/site_src/index.md, docs.md and wgsextract.md) at the new release's installers and rebuilds gui/site/. The site deploys when the release PR merges, so its download links fail until preflight passes and the release is public. Those pages say what the release adds only through the release notes link, so they need no other edit. The v6 row of wgsextract.github.io, which sends new users to the app site, moves to the release on its own within the hour once the release carries the app (the App release watch workflow; see below).

  1. Write the release notes in docs/release-notes/vX.Y.Z.md, in the same PR: what users get, under ## Changed, ## New and ## Fixes, plus ## Deprecated when commands are deprecated, and ## Desktop app for app changes, ending with a compare link (.../compare/vPREVIOUS...vX.Y.Z). PRs record CLI changes under docs/release-notes/unreleased/ (deprecations must be announced there) and app changes under gui/docs/changelog/unreleased/. Assemble both sets of fragments with
   python scripts/release_notes.py assemble X.Y.Z

which writes the notes file from the fragments, grouped by section, with the title and a compare link from the newest older release tag. It also adds a dated release to gui/docs/CHANGELOG.md, records the new CLI installer target there, and deletes the fragments. Then add a short summary under the title. If a fragment lands on main before the release PR merges, the PR's checks fail: move its entries into the notes file (and the dated changelog entry for a GUI fragment) and delete it. A version bump that leaves fragments or has no dated desktop changelog entry fails the same way. Run assembly even for a release with no fragments. The deprecated commands are also listed in DEPRECATIONS in src/wgsextract_cli/commands/registry.py. A command deprecated in one minor release is removed in the next, so a release that reaches a deprecation's remove_in version removes the command. The PRs since the last release are git log --oneline vPREVIOUS..origin/main.

  1. Open a PR titled Release X.Y.Z and merge it once CI is green.

On the merge, release.yml runs lint, type checks, tests and the package smoke test on the merge commit. It then creates the protected vX.Y.Z tag to pin the exact candidate while main keeps moving.

Release dispatches the following workflows against that tag and checks the returned run IDs and commit SHA. All must finish successfully:

  • ubuntu_ci.yml, windows_ci.yml, macos_ci.yml, and linux_arm64.yml (full test suites; these workflows also run nightly on main).
  • linux_aligners.yml, macos_aligners.yml, linux_deepvariant.yml, macos_deepvariant.yml, and macos_clair3.yml (build/test only; no native tool releases).
  • gui-tauri-installer.yml (Windows install/uninstall lifecycle) and gui-distribution.yml (signed installers and latest.json as artifacts).
  • pharmcat_e2e.yml, gkl_windows.yml, gatk_windows.yml, and cli_smoke.yml (package and real-data benchmark smoke).
  • install_lab.yml, after GUI distribution succeeds. It receives the distribution run ID and exercises those installers against the candidate CLI from the tree, with Windows negative controls. The publicly pinned CLI install is tested after publication (section 3).

These workflows also accept manual dispatches for targeted diagnosis. The release-only checks do not run on PRs, in the merge queue, or on a nightly timer. The nightly OS suites continue to report regressions on main.

Once preflight passes, Release creates the draft, uploads the validated distribution's exact artifact, and publishes the installers and updater feed together. install.sh installs the latest published release; installed apps use its latest.json. The native Windows tools aren't part of it: pixi.toml pins their own packages (see packaging/windows/README.md).

Check the Release run on the merge commit and its linked preflight runs. If a check fails or times out, the candidate stays unpublished. For a transient failure, rerun the failed jobs on Release to start a new preflight, or dispatch release.yml from main to retry the current version's existing tag. If the tagged code is wrong, leave that tag unpublished; fix the code and cut a fresh version. Do not move a release tag. A release only becomes latest if no newer version is already published; if GitHub can't confirm that, the run stops without publishing.

The "Protect release tags" ruleset lets only admins, maintainers and deploy keys create v* tags, so the workflow pushes the tag with a deploy key: RELEASE_TAG_DEPLOY_KEY, a secret of the release-tag environment, which only main can use. To replace the key, add a new write deploy key and set the secret to its private key (gh secret set RELEASE_TAG_DEPLOY_KEY --env release-tag < key), then delete the old deploy key.

Without a notes file, even a green Release run leaves the draft with generated notes. Wait for the entire Release run to pass before editing and publishing it on GitHub. Don't mark an older version as latest. Do not push release tags by hand: old commits still have the workflow that published on tag pushes before preflight was introduced. Start or retry Release from main.

  1. Pin the output-contract baseline once the tag exists, in a follow-up PR: git fetch origin tag vX.Y.Z, then python scripts/output_contracts.py pin --release vX.Y.Z writes contracts/baselines/vX.Y.Z.json (the tag, its commit and a digest) from the tag's own files, and the PR removes any approved_breaks entries the new baseline absorbed. Later changes are compared with it; see output contracts.

2. What the app's release needs#

  • Secrets and variables. The app's build reads the Apple signing and notarization secrets (APPLE_CERTIFICATE_P12, APPLE_CERTIFICATE_PASSWORD, APPLE_SIGNING_IDENTITY, and APPLE_API_KEY_P8, APPLE_API_KEY_ID, APPLE_API_ISSUER_ID or APPLE_ID, APPLE_APP_SPECIFIC_PASSWORD, APPLE_TEAM_ID), the updater signing key (TAURI_SIGNING_PRIVATE_KEY, optional TAURI_SIGNING_PRIVATE_KEY_PASSWORD) and the TAURI_UPDATER_PUBKEY variable. A release's macOS build fails without the Apple secrets. App publishing fails before uploading assets if any expected platform lacks a uniquely matched updater artifact with a nonempty signature. See gui/devdocs/distribution.md.
  • Trying a change first. Run workflow on GUI distribution (or gh workflow run gui-distribution.yml --ref BRANCH) builds unsigned installers as run artifacts without releasing anything; the Install Lab can test them (section 3).
  • The main site's deploy key. The App release watch workflow updates the v6 row of README.md in WGSExtract/wgsextract.github.io with MAIN_SITE_DEPLOY_KEY, a secret of the main-site environment (limit that environment to main). Without it the workflow warns and the row stays put. To set it up (the first two commands, once) or replace it:
  gh api -X PUT repos/WGSExtract/wgsextract-cli/environments/main-site -F 'deployment_branch_policy[protected_branches]=false' -F 'deployment_branch_policy[custom_branch_policies]=true'
  gh api -X POST repos/WGSExtract/wgsextract-cli/environments/main-site/deployment-branch-policies -f name=main -f type=branch
  ssh-keygen -t ed25519 -N "" -C "wgsextract-cli main-site" -f main-site-key
  gh repo deploy-key add main-site-key.pub -R WGSExtract/wgsextract.github.io --allow-write -t "wgsextract-cli release watch"
  gh secret set MAIN_SITE_DEPLOY_KEY --env main-site < main-site-key
  rm main-site-key main-site-key.pub

Tags and earlier app releases#

The app's releases up to v0.6.6 were made in the former gui-for-cli repository (also tagged vX.Y.Z, with the same numbers as the CLI release each bundled), and stay there. From the first release after v0.6.6, the app has no tags or releases of its own: it ships in this repository's vX.Y.Z release.

Apps up to v0.6.6 looked for updates in gui-for-cli's latest release. Only developers had those builds, and releases no longer copy their latest.json there, so those installs don't update themselves: install the current app instead. Apps from v0.8.5 on update from this repository's latest release.

3. Proof it reached users#

Within the hour of the app joining the release, App release watch (app_release_watch.yml) starts a full Install Lab run named Install Lab: app vX.Y.Z: Linux, macOS and Windows, with the CLI from this tree and with the CLI release the app pins, plus the negative controls. To start it at once: gh workflow run app_release_watch.yml.

The pinned jobs are the ones that matter: they set up the app exactly as a user's machine does, with the CLI release it bundles. The Windows app jobs only collect evidence; windows-judge checks it (and the negative controls), so the evidence the release works is the pinned jobs and windows-judge passing. See install_testing.md for what the lab checks, and for trying an app fix before releasing it (gh workflow run install_lab.yml -f app_run=<GUI distribution run id>).

Optional tool releases#

Native tool builds are released separately from the CLI, as prereleases that never become the latest release:

  • Windows tools (windows-tools-N): Actions > Windows Tools > Run workflow. See windows.md.
  • macOS aligners (macos-aligners-N): Actions > macOS Aligners > Run workflow. It publishes the Apple Silicon wgse-bwa, wgse-bwa-mem2, wgse-bwa-mem3 and wgse-minimap2 tarballs built from native/ (see native/README.md). Each package carries its own version, printed by --version: bump its WGSE_*_VERSION in the corresponding native/<aligner>/CMakeLists.txt and, where present, its conda recipe when it changes.
  • Linux aligners (linux-aligners-N): Actions > Linux Aligners > Run workflow. It publishes the wgse-bwa (x86-64 and ARM64), wgse-bwa-mem3 and wgse-minimap2 (x86-64) conda packages built from native/ by packaging/wgse-bwa, packaging/wgse-bwa-mem3 and packaging/wgse-minimap2, with their CUDA backends on x86-64. Bump WGSE_BWA_VERSION in native/bwa/CMakeLists.txt, WGSE_BWA_MEM3_VERSION in native/bwa-mem3/CMakeLists.txt or WGSE_MINIMAP2_VERSION in native/minimap2/CMakeLists.txt together with the recipe's version.
  • macOS DeepVariant (macos-deepvariant-N): Actions > macOS DeepVariant > Run workflow. It publishes the Apple Silicon wgse-deepvariant tarball built from native/deepvariant/ and its WGS weights converted from Google's image, with a SHA256SUMS (see native/deepvariant/README.md). Bump WGSE_DEEPVARIANT_VERSION in native/deepvariant/CMakeLists.txt when the package changes.
  • Linux DeepVariant (linux-deepvariant-N): Actions > Linux DeepVariant > Run workflow. It publishes the Linux x86-64 wgse-deepvariant conda packages (CUDA and CPU-only call_variants) built from native/deepvariant/ by packaging/wgse-deepvariant, and the WGS weights, with a SHA256SUMS. Bump WGSE_DEEPVARIANT_VERSION and the recipe's version together, then point pixi.toml's deepvariant feature at the new CUDA package's URL and sha256 and run pixi lock.
