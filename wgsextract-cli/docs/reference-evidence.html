Reference evidence (gVCF)

A variant VCF lists the places a genome differs from the reference. It can't say whether a base it doesn't list was read confidently as reference, read poorly, or not read at all. Polygenic scores, PharmCAT and confidence labels need the difference: treating every missing base as reference turns a coverage gap into a confident genotype.

--reference-evidence gvcf asks a caller to also write a gVCF, which records every base it assessed, beside its variant VCF. The variant VCF is unchanged, except that GATK genotypes it from the gVCF (see GATK). It is opt-in (reference_evidence = "gvcf" in config.toml makes it the default) because it costs time, memory and disk.

analyze follows the config.toml setting: its SNP step writes the gVCF (its indel step doesn't repeat it), and a rerun repeats the SNP step when the gVCF or its index is missing.

Outputs#

The gVCF and its index are separate outputs in the result manifest: role reference_evidence (with the provenance below as its metrics) and reference_evidence_index. The gVCF is written under a temporary name and renamed into place, then its index, so a failed run never leaves a partial gVCF or an index that describes another file.

The gVCF's ##wgseReferenceEvidence header (schema wgsextract.reference_evidence/1) records how it was made:

FieldMeaning
Engine, VersionThe caller and its version.
QualityModelgq: reference blocks carry a genotype quality. depth_only: they carry only depth (bcftools).
BandsThe depth (bcftools) or GQ bands its blocks are grouped by.
MinMQReads below this mapping quality are left out of the evidence.
RegionThe bases the run assessed, as contig:start-end items (a BED or literal --region, resolved); empty for the whole genome.
Ploidy, Sex, PloidyPolicyThe ploidy rules and sex used, and a digest of both.
PloidyZeroBases with ploidy 0 for this sample, such as a woman's chrY.

bcftools#

The gVCF comes from its own pileup of SNPs and indels together. vcf snp's SNP-only pileup can't be reused: it reports indel sites as reference (420 of 3,007 GIAB truth variants in a 2 Mb test). Its blocks are grouped by minimum depth with bands 0,5,10,20, the smallest of those tested, and carry no GQ, only DP and MIN_DP. Reads below mapping quality 20 are left out, as GATK's HaplotypeCaller does by default, so reads that map equally well elsewhere don't make a repeat look like confident reference. Its variant records come from that pileup too; the call set is still snps.vcf.gz/indels.vcf.gz. Each contig with reads is called in its own process, so its records don't depend on --threads.

Measured on HG002 (35x Illumina, GRCh38) against GIAB v4.2.1:

Regionvcf snpwith the gVCFgVCF + index
chr20:10-12 Mb, 1 thread13.2 s24.4 s0.23 MB
chr20, 2 threads240 s468 s7.8 MB (about 0.4 GB for a genome)

The variant VCF was identical with and without it. Of the 82,588 truth variants in chr20's confident regions, 432 sit on bases the gVCF calls callable reference, variants bcftools missed (335 SNVs and 97 indels).

DeepVariant#

DeepVariant writes the gVCF in the same run as its VCF, which is unchanged: Google's image or a local run_deepvariant and wgse-deepvariant with --output_gvcf, Parabricks (--gpu) with --gvcf. Its blocks carry GQ, in DeepVariant's bins of 5, and MIN_DP. It writes bases no read covers as 0/0 blocks with GQ 0 and MIN_DP 0, which read as uncovered, and its RefCall and NoCall records as filtered. Only the gVCF's header changes when it is published (bcftools reheader), so every record stays as DeepVariant wrote it. Bases a sex/PAR ploidy of 0 leaves out of calling (a woman's chrY) are recorded in PloidyZero. Parabricks calls a man's haploid chrX and chrY apart from the rest and its gVCF is gathered from the parts (see Sex and PAR); wgse-deepvariant requires 0.4.0 or later for non-diploid policies. Like Google's pipeline it accepts PAR intervals directly, preserving one resumable run; its reference blocks split at PAR boundaries and use haploid likelihoods outside PAR. Haploid GT and PL retain Google's diploid encoding, with heterozygous likelihoods suppressed. The readers use the published ploidy intervals, not GT length, for haploid depth thresholds; PAR remains diploid. The variant-only VCF carries the same policy under ##wgsePloidyPolicy (not a reference-evidence declaration). PAR BEDs describe the full policy on the selected haploid contigs, even for a bounded selection, so deletions reaching into PAR keep diploid treatment. wgse-deepvariant's diploid gVCF agrees with Google's in every field the states read; before 0.3.1 its variant records lacked the PL values of genotypes with <*> (#999).

The gVCF and its index are outputs of the postprocess_variants stage: if that stage is interrupted, a rerun repeats it alone. Its stages' work is deleted once the run finishes, so a gVCF deleted later reruns every stage, as do turning --reference-evidence on or off, which changes what make_examples writes, and a change to the gVCF's provenance alone (such as a wider --region on a woman's chrY). A run that keeps no stage gets the full preflight check.

Memory: Google's postprocess_variants streams each partition's reference records into the gVCF, so it needs no more memory (chr20 as one partition: 1.14 GiB either way). wgse-deepvariant keeps every contig's calls until it writes the gVCF, so its preflight allows about 20 GiB for a whole genome, against 5 GiB without; on a smaller machine call a --region, or use Google's image (see resource_estimates.md).

Measured on HG002 (35x Illumina, GRCh38) chr20, 8 threads, against GIAB v4.2.1:

EngineVCF onlywith the gVCFgVCF + index
Google's image, CPU859 s1,030 s20.8 MB (about 1 GB for a genome)
wgse-deepvariant, CPU500 s575 s19.4 MB
Parabricks, RTX 309078 s99 s21.0 MB

Times are from a shared host (load 9-20 on 12 cores); on a quieter one Google's image took 943 and 989 s. Parabricks' row is pbrun with the same options, run directly.

The variant VCFs were identical with and without the gVCF. Of the 82,588 truth variants in chr20's confident regions, 116 sit on bases the gVCF calls callable reference, against bcftools' 432.

GATK#

HaplotypeCaller writes the gVCF (-ERC GVCF), and GenotypeGVCFs genotypes the variant VCF from it, so one HaplotypeCaller run makes both. Its blocks carry GQ and MIN_DP, with <NON_REF>, banded by GQ at 10,20,30,60: GATK's default (one band per GQ below 60) made a genome's gVCF about 6.5 GB, these about 1.4 GB, with the same bases at GQ 20 or more. Reads below mapping quality 20 are left out, GATK's default. Parabricks' HaplotypeCaller (--gpu) and Ultima's --scatter aren't supported with the gVCF; a run asking for both stops before calling.

Measured on HG002 (35x Illumina, GRCh38) against GIAB v4.2.1, 4 threads:

RegionVCF onlywith the gVCFgVCF + index
chr20:10-12 Mb25.5 s38.4 s0.76 MB
chr201,374 s1,432 s28.3 MB (about 1.4 GB for a genome)

HaplotypeCaller took the same time either way; GenotypeGVCFs added 17 s and cutting and publishing the gVCF 4 s. GenotypeGVCFs' VCF had 134,083 records against HaplotypeCaller's 134,073 without the gVCF: it genotypes each site from the gVCF's likelihoods, so a few borderline sites differ. Of the 82,588 truth variants in chr20's confident regions, 102 sit on bases the gVCF calls callable reference (DeepVariant 116, bcftools 432). GATK also writes blocks over reference N, with MIN_DP 0, so they read as uncovered.

Clair3#

Clair3 writes the gVCF (--gvcf) in the same run as its VCF, whose calls and filters it doesn't change, on the CPU and in HKU's GPU image (--gpu). Its blocks carry GQ, in Clair3's bins of 5, and MIN_DP; reads below mapping quality 5 (Clair3's default) are left out. Its pileup step is much slower with it, so a run that asks for it warns (clair3_gvcf_cost) and its preflight scales the time it reports: about 2.4x on the CPU and 4.3x on the GPU. In that 5 Mb measurement the CPU path was faster than --gpu with the gVCF, which a --gpu run's warning reports; larger runs weren't measured, and it still calls on the GPU. Clair3 skips contigs the index places no reads on, and with none left writes no gVCF; their bases read as uncovered. A missing gVCF when a called contig has reads fails the run. Without a --region it calls chr1-22, X and Y, so the gVCF's Region lists those and other contigs read as not_assessed.

Measured on HG002 ONT R10.4.1 chr20:10-15 Mb, 4 threads: on the CPU 75 s for the VCF and 179 s with the gVCF (2.4x); with --gpu on an RTX 3090 106 s and 452 s (4.3x). The gVCF was 1.6 MB. The calls and filters were identical.

Clair3 builds a reference base's depth and GQ from the reads that show a base there; a read that deletes the base counts for neither. A deletion it saw but didn't call is a no-call (or a filtered record) at its first base, followed by confident 0/0 blocks over the deleted bases, with the deleting reads missing from their depth (#1028). So in a Clair3 gVCF (its Engine, or a ##source=Clair3 line), reference bases directly after a no-call or filtered record, within 10 bases of it, read as low_quality_reference while their depth stays below 70% of that record's. Consecutive or overlapping no-call and filtered records use the deepest depth and the furthest end of that anchor chain; disjoint anchors separated by reference start separate chains. Queries include the complete contributing chain, so a point lookup and a full-region scan agree. Overlapping calls keep their own state, regardless of reference-block boundaries. In the initial qualification, of the 7,055 truth variants in the confident regions, 41 (40 deletions) had a base of their REF on callable reference before this rule (2 at their position) and 3 after; it took 0.4% of the callable bases (4,879,943 to 4,862,257).

Sex and PAR#

GATK, Clair3 and Parabricks DeepVariant call a man's haploid chrX and chrY apart from the diploid rest (see caller-ploidy.md), so the gVCF is written in parts. Each part's blocks are cut at its edges (a block cut at its start begins on its own reference base, read from the FASTA or, for a gzip one, its decompressed copy) and the parts are gathered in reference order, so every base has one record in the ploidy it was called with: 0 on a man's chrX, 0/0 in its PAR (DeepVariant writes 0/0 in both). Any other record belongs to the part its POS is in; one starting before the selection, such as a deletion whose REF reaches into it, is kept where it covers the selected bases, once. Bases the policy gives ploidy 0, such as a woman's chrY, aren't called and are recorded in PloidyZero.

vcf gatk, vcf clair3 and Parabricks DeepVariant keep no step journal: a rerun calls again, with or without the gVCF.

Evidence states#

wgsextract_cli.core.reference_evidence reads a gVCF (one written here, or another caller's) and puts every base in one state. An explicit provenance quality model wins; otherwise a recorded bcftools -g/--gvcf option selects depth-only blocks, even if variants declare GQ. Other files use their FORMAT/GQ declaration. Filenames containing -g are not options. Where records overlap, the state higher in this table wins.

StateMeaning
excluded_by_policyPloidy 0 for this sample (PloidyZero): not expected to exist.
variantInside the REF span of a called non-reference allele.
filteredA record with a failing FILTER (DeepVariant's RefCall, for example) or sample filter (FORMAT/FT).
no_callA missing genotype (. or ./.).
low_quality_referenceReference, but with depth below confidence_min_depth (halved for a haploid call) or, for the gq model, GQ below confidence_min_gq; in a Clair3 gVCF, also the bases a deletion it didn't call may remove (see Clair3).
uncoveredAssessed, but no reads: no record (bcftools, Clair3, or DeepVariant over reference N) or a block with MIN_DP 0 (DeepVariant, GATK).
callable_referenceReference, with enough depth (and GQ).
not_assessedOutside the region the caller assessed.

The thresholds are the confidence_* settings shared with variant confidence labels.

END-tagged reference blocks, including blocks clipped to a single base, need an explicit FORMAT/MIN_DP or INFO/MIN_DP depth floor. A block's DP alone does not establish depth throughout the block: without a minimum, reference evidence is low_quality_reference, and microarray export reports missing depth at enabled depth thresholds. Explicit single-site calls can still use DP. This also applies if a tool removed MIN_DP from an otherwise valid gVCF; do not strip that field when transferring reference evidence.

Commands that read it#

A command given a variant VCF finds its gVCF through the result manifest of the run that wrote the VCF: a manifest in the VCF's folder, or one its sample workspace recorded, that lists the VCF and a reference_evidence output, both unchanged since (same recorded fingerprint; a manifest without fingerprints isn't trusted), the gVCF indexed. A server job follows only manifests and files inside the folders it allows. Without one, the command works as before.

  • score pgs counts a scoring site the VCF doesn't list as homozygous reference only where the gVCF calls it callable_reference (an indexed --ref checks the alleles). Anywhere else the site stays missing, counted under its state's name in match_counts; details.reference_evidence names the gVCF and counts the scored sites in each state. A gVCF given as the input itself is read the same way, its explicit 0/0 records included. See pgs.md.
  • vcf pharmcat gives a PharmCAT definition the VCF doesn't list a reference genotype only where every base of it is callable_reference with one ploidy; otherwise it is passed as a no-call (so --absent-to-ref can't make it reference) with the state as its PGX_STATE. See variant-confidence.md. An explicit BAM/CRAM can replace this evidence for a variants-only input; see Pharmacogenomics and repeat typing.
  • vcf clinvar, vcf gnomad --max-af and analyze add the gVCF's state at the sites they checked to their confidence details (details.confidence[].reference_evidence): at the calls they labelled (calls), and for vcf clinvar and analyze at every ClinVar pathogenic/likely pathogenic site (clinvar_pathogenic_sites), so a site the sample doesn't carry reads as confident reference, uncovered, low-quality, filtered or not assessed. Sites that are neither a call nor callable reference (policy exclusions aside) raise a reference_evidence_unassessed_sites warning. A site's state is callable_reference only when every base of it is. See variant-confidence.md.
  • vcf callability classifies every base of a gene list's coding exons and calls an exon callable only when every base is callable_reference or a call, outside known short-read limitations; the report then tells genes with nothing reported from genes it could not read. See exon-callability.md.
  • The ancestry projection (qc ancestry on a VCF, and score pgs's PCA projection) fills an ancestry site the VCF doesn't list as hom-ref only where the gVCF calls it callable_reference, instead of assuming every missing site of a whole-genome variants-only VCF is reference. A variants-only VCF of part of the genome is then usable too, and a gVCF given as the input itself. The missing sites' states are reported (ancestry_missing_sites_<state> metrics, ancestry_calibration.pca_missing_site_states). See ancestry.md.

Measured on HG002 chr20 (35x Illumina), with PGS000018 (CAD, 1.75 million sites, about 44,000 on chr20): score pgs matched 12,723 sites from the variant VCF alone and 44,307 with bcftools' gVCF (31,584 more callable reference sites; 10 low-quality), 44,185 with DeepVariant's (31,475 more; 56 low-quality, 31 filtered, 36 no-call, 12 uncovered). Inside GIAB v4.2.1's confident regions, 30,771 of the 30,774 sites bcftools' gVCF made homozygous reference agree with the truth set, and all 30,694 of DeepVariant's. Reading the gVCF at the 1.75 million sites added 30-50 s to the run.
